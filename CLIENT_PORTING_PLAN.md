# План портирования клиента: Flash (AS2) → HTML5

> **Статус: план исполняется** (Фаза 0 и Фаза 1 закрыты, Фаза 2 в
> процессе — см. чеклист ниже). Составлен по просьбе владельца проекта
> после обсуждения рекомендаций Gemini (`dblog.txt`, не в git) и проверки
> их технических предпосылок против реального кода
> `old-sphere/SPHERE_client/`. Общая методология Gemini (разделить
> графику/код, не пытаться авто-конвертировать, выносить UI за пределы
> Canvas) разумна и учтена ниже, но два её ключевых технических допущения
> были неверны для этого конкретного проекта — см. §0.
>
> **Зачем это вообще нужно (уточнение владельца, 2026-09-04):** сайт уже
> сейчас использует Ruffle (WASM-эмулятор Flash) — игра играбельна и без
> этого плана. Цель порта — не играбельность, а **разблокировать
> дальнейшее развитие**: на текущем AS2/Flash-коде нельзя удобно обновлять
> графику, добавлять фичи и т.д. Этот клиент — первый шаг более длинной
> траектории: новый клиент → (в перспективе) новый сервер → новый портал.
> Из этого следует практический вывод для решений ниже: там, где встаёт
> выбор между «точно как в старом клиенте» и «удобнее для дальнейшего
> расширения», предпочтение — по умолчанию за поддерживаемостью, а не за
> слепым копированием AS2-организации кода 1:1.

## 0. Что скорректировано относительно исходных рассуждений Gemini

1. **Клиент на AS2, не AS3.** Проверено: нигде в игровом коде нет `package`/
   `import flash.*`, используется классический `getURL()`, прототипный
   стиль классов. Единственное исключение — `DS_ANALYZER/analiz.as`,
   отдельный слитый инструмент разработчика для баланс-анализа (реально
   AS3), не часть игрового клиента. Из этого следует: инструменты вроде
   `as3hx`/`AS3toTypeScript` (заточены под AS3) не применимы напрямую —
   готового автоконвертера AS2→X такого качества не существует. Это не
   меняет вывод Gemini «не пытайтесь автоконвертировать» — только убирает
   один из предложенных путей ускорения.
2. **Основной игровой протокол — НЕ бинарные сокеты/AMF3.** Подтверждено в
   [protocol-client-server.md](docs/protocol-client-server.md) и лично
   перепроверено в `reqvestdata.as`: обмен — простой `POST xmldata=<xml>`
   на `ds/useraction.php`, ответ — текстовая `LoadVars`-строка с XML
   внутри. Это огромное упрощение: порт транспортного уровня — это
   `fetch()`/`XMLHttpRequest`, без WebSocket/AMF-десериализации.
3. **У чата — реальный отдельный сокет** (`chatclass.as`/`chatmodul.as`,
   `XMLSocket` на `debug.link.chatServer:2561+offset`) — здесь Gemini был бы
   прав насчёт WebSocket. **Не актуально: чат в ремастер не переносится**
   (решение владельца, см. §4) — сеть в этом плане ограничена только
   основным игровым протоколом (п.2).
4. **Реальных `.fla`-исходников много** (150+, не только компилированные
   `.swf`) — включая ключевые: `interface_v10.fla`/`interface_v11.fla`
   (основной интерфейс), `build_bio-lib.fla`/`build_psi-lib.fla`/
   `build_tech-lib.fla` (здания по расам), `war_units.fla`, `tree_scients/
   *.fla` (дерево наук), `artefact.fla`, `warbkg.fla`. Экспорт графики через
   Adobe Animate (шаг 1 у Gemini) реалистичен, не требует повторной
   декомпиляции `.swf`.

## 1. Выбор технологического стека

**Рекомендация: TypeScript + PixiJS для карты/боя, обычный HTML/CSS (или
лёгкий фреймворк) для меню.** Не Haxe/OpenFL — его главное преимущество
(`as3hx`-конвертация AS3-кода) для нас не работает, т.к. исходник на AS2, а
без этой автоматизации остаётся только сходство API, которое не
перевешивает более широкую экосистему/кадровый резерв TypeScript. Phaser —
запасной вариант, если понадобится готовый менеджер сцен/камеры, но для
экономической стратегии (не экшена) это, вероятно, избыточно.

Обоснование раздельного подхода "canvas для карты + HTML для меню":
собственный аудит [client-side-computed-logic.md](docs/client-side-computed-logic.md)
показал, что подавляющее большинство из 128 файлов клиента — это меню/окна
(альянс, почта, наука, торговля, кабинет и т.д.), которые в основном просто
отображают то, что прислал сервер (категория А/Б, 112 из 128 файлов). Это
идеально ложится на обычную HTML/CSS-вёрстку/компоненты (Vue/Svelte/React —
на усмотрение) — быстрее в разработке и легче тестировать, чем рисовать
формы внутри Canvas. Прецедент уже есть в самом проекте: личный кабинет
(`UC`) уже живёт вне Flash-клиента отдельным веб-приложением
([user-cabinet.md](docs/user-cabinet.md)). PixiJS (WebGL, концепция дерева
отображения близка к Flash Sprite/DisplayList) — только для реально
графической части: карта/соты (`sota.as`, 1713 строк — видимо, основной
класс сетки/карты), позиционирование построек, боевая анимация.

    `index_login.php`. Ниже — весь путь расследования и настоящая причина.
    - **Ранняя гипотеза (rate-limiting/антибот на повторные логины
      тестовым аккаунтом) — проверена и ОПРОВЕРГНУТА.** Полный текстовый
      поиск по живому `SessionErrors.log` (6.7 МБ, весь файл, через
      `ds/utils/LogView.php`) на свой публичный IP — ноль совпадений: ни
      `"Cant find SID"`, ни `"Mismatch session UA"` от меня там нет.
    - **Настоящий механизм редиректа найден и подтверждён чтением кода.**
      `ds_error(...)` — не отдельная функция, это вызов `DS_Error(...)`
      (PHP регистронезависим к именам функций; поиск `grep -i function
      ds_error` вместо `grep function ds_error` — определение в
      `ds/include/ErrorHandlers.inc.php:211`). `DS_Error()` при
      `$GLOBALS['HI_SECURITY_FLAG']==1` вызывает
      `GE_Login::execLogout()` (`ErrorHandlers.inc.php:227-230`), а тот —
      `SU_GameSessionWork::SessionDestroy()` + `GE_Login::_redirect()`
      (`Header("Location: ".GAME_HOST."/ds/index_login.php")`,
      `GE_Login.class.php:301-314`). `index_start.php:3` ставит
      `$GLOBALS['HI_SECURITY_FLAG']=1` безусловно в начале файла — то есть
      **любой** `ds_error()`/провалившийся `assert()` где угодно в цепочке
      `GE_ControlStart` → `GE_ExecStartGameEnter::Exec()` (там их много:
      строки 63, 68, 77-100, 115-118, 148-151 —
      `GE_ExecStartGameEnter.class.php`) полностью разлогинивает и
      редиректит на форму логина. Это объясняет именно то поведение,
      которое видел браузер (`res.url` после авто-следования редиректов
      останавливается на `index_login.php`, `res.status===200` — это уже
      страница логина, а не исходный 302).
    - **Гипотеза про `session.cookie_domain`/vite-прокси — тоже
      проверена и ОПРОВЕРГНУТА.** `SU_GameSessionWork::_setDomain()`
      (`SU_GameSessionWork.class.php:168-195`) при
      `HTTP_HOST=='destinysphere.ru'` действительно делает
      `ini_set('session.cookie_domain','destinysphere.ru')`, а
      `vite.config.ts`'s `changeOrigin:true` действительно подменяет
      исходящий `Host` на `destinysphere.ru` — на бумаге это выглядело как
      кандидат (браузер получает ответ от `localhost`, `Set-Cookie` с
      чужим `Domain` был бы им отброшен). Но `_setDomain()` вызывается
      только внутри `SessionContinue()`, а не `SessionStart()` (логин), и
      практическая проверка (`client/scripts/debug-cookies.ts`, прямой
      Node-запрос через тот же `vite`-прокси на `localhost:5184`, реальным
      тестовым аккаунтом) показала, что `Set-Cookie` для `PHPSESSID`
      **не содержит `Domain=` вообще** ни напрямую, ни через прокси — и
      весь цикл login→enterWorld через прокси **успешно завершился 302 на
      `ds/index.php`**, идентично прямому запросу. Прокси и cookie-домен
      не виноваты.
    - **Настоящая причина найдена** (`client/scripts/debug-network.ts`,
      перехват реальных заголовков через CDP `Network.*ExtraInfo`, а не
      только `res.url`/`res.status` из page-context `fetch()`): выяснилось,
      что `enterWorld()` **на самом деле успешен** — сервер честно отдаёт
      `302 → ds/index.php?ck=...&VERS=...&sport=...&PHPSESSID=...`.
      Проблема на шаг позже: браузерный `fetch()` с `redirect:'follow'`
      автоматически идёт по этому редиректу дальше, ЭТО и есть запрос,
      который зацикливается на логин. `ds/index.php:84-98` проверяет
      `HTTP_REFERER` по белому списку подстрок (`index_start.php`,
      `index_queue.php`, `detect_player.php`, `flash/ds3` и др.) — без
      совпадения редиректит на `index_login.php`. Настоящий Flash-клиент
      проходил эту проверку через `flash/ds3` (referrer страницы,
      встраивающей `.swf`); наш `fetch()` в редирект-цепочке шлёт Referer
      = адрес самой SPA-страницы (`localhost:5184/?live=1`), который не
      совпадает ни с чем из списка. Мой более ранний Node-репро
      (`debug-cookies.ts`) это не поймал, потому что там редирект
      проверялся только по заголовку `Location` первого прыжка, без
      реального перехода на `index.php`.
    - **Исправлено**: `GameSession.enterWorld()`
      (`client/src/protocol/gameProtocol.ts`) теперь явно передаёт
      `referrer: <origin>/ds/index_start.php` в `fetch()` — это
      распространяется на весь redirect-chain одного `fetch()`-вызова,
      включая финальный прыжок на `index.php`. Живой повторный тест
      (`debug-network.ts`) подтвердил: `GET index.php?ck=...` теперь
      `200 OK` (не редирект), дальше `useraction.php` → `200`, `refresh`
      с реальными `location=HOME`, `id_comb=ERD_1_147_6`,
      `sota.length=217`.
    - Побочные находки: **все три** более ранние гипотезы (антибот/
      rate-limiting, `session.cookie_domain`/прокси, повторный вызов
      `main()`) были неверны — реальная причина не имела отношения ни к
      сессии, ни к прокси, ни к самому `enterWorld()`. `screenshot.ts`/
      `debug-network.ts` чинились попутно: `page.goto(waitUntil:
      'networkidle0')` никогда не срабатывал (Vite HMR держит открытый
      WebSocket) — заменено на `'load'` (готовность страницы всё равно
      определяется через `window.__renderDone`, не через сеть).
    - `main.ts` по-прежнему не логинится автоматически на каждую
      перезагрузку (только по `?live=1`) — это осознанное решение не
      дёргать живой тестовый аккаунт на каждый reload, а не воркэраунд
      багу (бага больше нет).
- [x] **Выходной критерий фазы выполнен** (2026-09-04, живой скриншот):
      собственная колония тестового аккаунта отрисована настоящими

      самый `?live=1` путь через `login()`→`enterWorld()`→`useraction.php`.

   не принимает значение 3** — то есть `ZOND_<раса>_3` в ассетах клиента

   `referrer` явно в `GameSession.enterWorld()`. Подробности — см. Фаза 2,
   п. про `enterWorld()` выше.

## 6. Условие перехода на запасной план

Решение владельца (2026-09-03): пробуем этот план (перенос только клиента,
бэкенд не трогаем) как основной путь. Запасной вариант — сервер с нуля на
Go, возможно в параллель силами Виталика (соавтор проекта, уже
неформально прикидывает архитектуру).

**Триггер перехода на запасной план** — если ранний тестовый шаг Фазы 1
(п. 5 списка задач Фазы 1: минимальный скрипт логин+команда+разбор ответа
от НЕ-Flash клиента) провалится или риски анти-replay/антибот-механизма
(открытые риски выше, п.2) окажутся блокирующими — не тратить время на
попытки обойти это внутри текущего плана, а сразу сигнализировать
владельцу, что пора переходить к параллельной разработке сервера на Go,
а не пытаться героически чинить протокол-совместимость.
