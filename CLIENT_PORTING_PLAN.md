# План портирования клиента: Flash (AS2) → HTML5

> **Статус: план для обсуждения, ничего не реализовано.** Составлен по
> просьбе владельца проекта после обсуждения рекомендаций Gemini
> (`dblog.txt`, не в git) и проверки их технических предпосылок против
> реального кода `old-sphere/SPHERE_client/`. Общая методология Gemini
> (разделить графику/код, не пытаться авто-конвертировать, выносить UI за
> пределы Canvas) разумна и учтена ниже, но два её ключевых технических
> допущения были неверны для этого конкретного проекта — см. §0.

## 0. Что скорректировано относительно исходных рассуждений Gemini

1. **Клиент на AS2, не AS3.** Проверено: нигде в игровом коде нет `package`/
   `import flash.*`, используется классический `getURL()`, прототипный
   стиль классов. Единственное исключение — `DS_ANALYZER/analiz.as`,
   отдельный слитый инструмент разработчика для баланс-анализа (реально
   AS3), не часть игрового клиента. Из этого следует: инструменты вроде
   `as3hx`/`AS3toTypeScript` (заточены под AS3) не применимы напрямую —
   готового автоконвертера AS2→X такого качества не существует. Это не
   меняет вывод Gemini «не пытайтесь автоконвертировать» — только убирает
   один из предложенных путей ускорения.
2. **Основной игровой протокол — НЕ бинарные сокеты/AMF3.** Подтверждено в
   [protocol-client-server.md](docs/protocol-client-server.md) и лично
   перепроверено в `reqvestdata.as`: обмен — простой `POST xmldata=<xml>`
   на `ds/useraction.php`, ответ — текстовая `LoadVars`-строка с XML
   внутри. Это огромное упрощение: порт транспортного уровня — это
   `fetch()`/`XMLHttpRequest`, без WebSocket/AMF-десериализации.
3. **У чата — реальный отдельный сокет** (`chatclass.as`/`chatmodul.as`,
   `XMLSocket` на `debug.link.chatServer:2561+offset`) — здесь Gemini был бы
   прав насчёт WebSocket. **Не актуально: чат в ремастер не переносится**
   (решение владельца, см. §4) — сеть в этом плане ограничена только
   основным игровым протоколом (п.2).
4. **Реальных `.fla`-исходников много** (150+, не только компилированные
   `.swf`) — включая ключевые: `interface_v10.fla`/`interface_v11.fla`
   (основной интерфейс), `build_bio-lib.fla`/`build_psi-lib.fla`/
   `build_tech-lib.fla` (здания по расам), `war_units.fla`, `tree_scients/
   *.fla` (дерево наук), `artefact.fla`, `warbkg.fla`. Экспорт графики через
   Adobe Animate (шаг 1 у Gemini) реалистичен, не требует повторной
   декомпиляции `.swf`.

## 1. Выбор технологического стека

**Рекомендация: TypeScript + PixiJS для карты/боя, обычный HTML/CSS (или
лёгкий фреймворк) для меню.** Не Haxe/OpenFL — его главное преимущество
(`as3hx`-конвертация AS3-кода) для нас не работает, т.к. исходник на AS2, а
без этой автоматизации остаётся только сходство API, которое не
перевешивает более широкую экосистему/кадровый резерв TypeScript. Phaser —
запасной вариант, если понадобится готовый менеджер сцен/камеры, но для
экономической стратегии (не экшена) это, вероятно, избыточно.

Обоснование раздельного подхода "canvas для карты + HTML для меню":
собственный аудит [client-side-computed-logic.md](docs/client-side-computed-logic.md)
показал, что подавляющее большинство из 128 файлов клиента — это меню/окна
(альянс, почта, наука, торговля, кабинет и т.д.), которые в основном просто
отображают то, что прислал сервер (категория А/Б, 112 из 128 файлов). Это
идеально ложится на обычную HTML/CSS-вёрстку/компоненты (Vue/Svelte/React —
на усмотрение) — быстрее в разработке и легче тестировать, чем рисовать
формы внутри Canvas. Прецедент уже есть в самом проекте: личный кабинет
(`UC`) уже живёт вне Flash-клиента отдельным веб-приложением
([user-cabinet.md](docs/user-cabinet.md)). PixiJS (WebGL, концепция дерева
отображения близка к Flash Sprite/DisplayList) — только для реально
графической части: карта/соты (`sota.as`, 1713 строк — видимо, основной
класс сетки/карты), позиционирование построек, боевая анимация.

## 2. Что уже есть готового — и экономит значительную часть работы

Не нужно заново читать AS2-исходники для большей части функциональности —
за эту сессию уже написана функциональная спецификация клиента на русском:

- [client-combat-ui.md](docs/client-combat-ui.md) — боевой/военный UI
  (армии, бой, шпионаж, зонды, щиты).
- [client-economy-social-ui.md](docs/client-economy-social-ui.md) —
  экономика, альянсы, наука, личный кабинет.
- [client-engine-and-protocol.md](docs/client-engine-and-protocol.md) —
  ядро (`parser.as`, `reqvestdata.as`, `loader.as`, `game.as`, `window.as`),
  сверено с протоколом.
- [client-side-computed-logic.md](docs/client-side-computed-logic.md) —
  какие 16 из 128 файлов реально считают что-то сами (не просто
  отображают присланное сервером) — со ссылками на формулы построчно. Это
  единственное место, которое ОБЯЗАТЕЛЬНО переносить формула-в-формулу, а
  не просто пересказывать по смыслу.
- [protocol-client-server.md](docs/protocol-client-server.md) — протокол
  строго со стороны PHP (что сервер ожидает/отдаёт).

### Фаза 1 — «Тонкий» сетевой клиент (объём: мало-средне, но критичный путь)

- [ ] Поднять пустой TypeScript-проект (сборка на выбор — Vite и т.п.).
- [ ] Реализовать отправку `POST xmldata=<xml>` на `ds/useraction.php` через
      `fetch()`.
- [ ] Воспроизвести точно (не «примерно так же»):
  - [ ] Сессия/анти-replay ключ — отдельные top-level поля формы, НЕ внутри
        XML ([protocol-client-server.md](docs/protocol-client-server.md)).
  - [ ] SIDIX/SIDID-механизм сессии
        ([client-engine-and-protocol.md, §2.2](docs/client-engine-and-protocol.md)).
  - [ ] Сервер молча вырезает XML-сущности (`&amp;`, `&lt;` и т.п.) из
        присланной строки до парсинга — кодировать соответствующим образом,
        иначе часть запросов будет молча биться.
  - [ ] Разбор ответа: не XML-документ целиком, а `LoadVars`-строка вида
        `mark=value&mark=value`, где отдельные значения — XML-фрагменты.
- [ ] Написать минимальный тестовый скрипт (можно даже не в браузере, Node
      подойдёт) — залогиниться, отправить одну простую команду, распарсить
      ответ. **Сделать это ДО вложения серьёзных усилий в остальные фазы** —
      см. открытый риск №2 в §5 (не проверено, не забанит ли сервер
      не-Flash User-Agent/другую антибот-эвристику).
- [ ] Реализовать общий диспетчер команд (аналог `parser.as`/
      `reqvestdata.as`/`xmlparsers.as` —
      [client-engine-and-protocol.md](docs/client-engine-and-protocol.md))

      каждом месте использования.
- [ ] Выходной критерий фазы: можно залогиниться под тестовым аккаунтом,
      получить список миров/колоний, отправить произвольную команду и
      получить распарсенный, типизированный ответ — без единого пикселя
