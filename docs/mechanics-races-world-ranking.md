## 1. Структура мира: кольца → комплексы → соты → ячейки

Иерархия (от крупного к мелкому): **мир (`DS_World`) → кольцо (`DS_Ring`) →
комплекс сот (`DS_CombComplex`) → сота (`DS_Comb`, 6 штук на комплекс) →
ячейка (`DS_Cell`, 3 типа на соту)**. Ни одного класса `DS_CellTemplate`/
`DS_CellTemplateElement` в `ds/classes` **нет** — это не PHP-классы, а
таблицы БД (`ds_celltemplate`, `ds_celltemplateelement`), к которым
обращаются напрямую через SQL из `WorldUtils` и других файлов; в задании
предполагалось, что это классы — по факту это чистые справочники в БД.

### 1.1 Кольца (`ds_ring` / `DE_Ring`, `DS_Ring`, `DS_RingFactory`)

Кольцо описывается `id_ring`, `ringnumber`, `ringname`, и **вычисляемым**
`complexcount = MAX(ds_combcomplex.complexnumber)` для этого кольца
(`ds/classes/DS/DS_Ring.class.php:44-63`) — то есть количество комплексов на
кольце **не хранится как отдельное поле и не ограничено конфигом**, а
представляет собой просто «максимальный созданный номер комплекса»: сколько
комплексов администратор реально создал через `createCombComplex()`, столько
и есть. Жёсткого потолка «комплексов на кольцо» в коде нет.

Прямое соответствие номер кольца → раса/имя найдено в
`ds/classes/TMP/TMP_ControllClearComplex.class.php:121`:

```php
$rings = array(1 => 'VORANIA', 2 => 'LIENSU', 3 => 'PSOLAO', 4 => 'MELSION');
```

Это **точное подтверждение** тезиса из Википедии (3 кольца закреплены за
расами, 4-е общее):

| `ringnumber` | `ringname`/константа | Раса | Комментарий |
|---|---|---|---|
| 1 | VORANIA | Воранеры | базовое кольцо расы (`ds_racehasbasering`) |
| 2 | LIENSU | Лиенсу | базовое кольцо расы |
| 3 | PSOLAO | Псолао | базовое кольцо расы |
| 4 | MELSION (`ringname = 'RING_COLONIZE'`) | общее | кольцо колонизации, доступно всем расам |

Привязка расы к «домашнему» кольцу — через таблицу `ds_racehasbasering`
(`ringnumber` ↔ `id_race`), читается, например, в
`WorldUtils::addNewInstance()` (`ds/classes/WorldUtils.class.php:341-358`) —
при регистрации по `id_race` находится `ringnumber`, и уже на это кольцо
подбирается свободная сота. Кольцо 4 (Мелсион) в этой же функции явно
исключено из проверки зарезервированных сот (`r.ringnumber != 4`, строка
293) — то есть логика резервирования сот действует только для «домашних»
рас-колец, а не для кольца колонизации. Внутриигровой FAQ прямо называет
Мелсион «кольцом для колоний» и уточняет: «на первом уровне оно пустует»
(`ds/help/faq.php:1225`) — то есть на молодых игровых мирах 4-е кольцо
изначально не заселено, колонии там появляются по мере колонизации игроками.

### 1.2 Комплексы (`ds_combcomplex` / `DS_CombComplex`)

Создаются массово через `WorldUtils::createCombComplex($worldid, $ringnum,
$complextypeid, $count)` (`ds/classes/WorldUtils.class.php:33-203`): находит
`id_ring` по номеру, берёт текущий максимальный `complexnumber` на кольце и
вставляет `$count` новых строк `DS_CombComplex` с инкрементирующимся
номером (строки 79-92), одной SQL-транзакцией (`begin`/`commit`,
`STATEMENT_TIMEOUT` отключён).

Тип комплекса (`id_complextype`, справочник `ds_combcomplextype`) — найдены
два строковых значения кода `complextype`:

| `id_complextype` (найдено численно) | `complextype` (строка) | Где встречается |
|---|---|---|
| 1 | `HABITABLE` (предположительно — численно подтверждён только id=1, строковое имя `HABITABLE` встречается отдельно как противоположность `COLONIZEABLE`) | `SU_UpdateRanking.class.php:200` — рейтинг считается только для `id_complextype=1` (обычные, не колонизируемые, комплексы) |
| 2 | `COLONIZEABLE` | `UA_Colonize.class.php:225-233` — подсчёт «числа колоний игрока» фильтрует именно `complextype = 'COLONIZEABLE'`; `SU_ServerLoadStat.class.php:267` использует `id_complextype = 2` |

Т.е. администратор при создании кольца вызывает `createCombComplex` дважды:
один раз с `complextypeid=1` (обычные комплексы расы) на кольцах 1-3, и
`complextypeid=2` на кольце 4 (Мелсион) — колонизируемые комплексы.
Прямого кода, который бы это явно так делал, не найдено (это admin-панель
вне `ds/classes`), но связка типов и того, где они фильтруются, — прямая.

### 1.3 Соты (`ds_comb` / `DS_Comb`, `DE_Comb`)

Внутри комплекса ровно **6 сот** (жёстко зашито циклом `for ( $e=1; $e<=6;
$e++ )` в `createCombComplex`, `WorldUtils.class.php:110`), с полями
`id_combcomplex`, `combnumber` (1-6), `combscore` (изначально 0). У соты
есть флаг `is_capture` (сота захвачена/захватываема военным путём — колония
другого игрока в процессе захвата, см. `ME_CaprureColony.class.php`,
`UA_Attack.class.php:208-209`), который исключает соту из обычного пула
свободных сот для заселения (`DS_Comb::GetMinCombIDForPlacementOnRing`,
`ds/classes/DS/DS_Comb.class.php:614-660`, условие `c.is_capture = 'f'`).

### 1.4 Ячейки (`ds_cell` / `DE_Cell`, `DE_CombCells`) — три типа, числа 217/28/217

Для каждой соты `createCombComplex` создаёт ячейки трёх типов
(`WorldUtils.class.php:138-174`):

| `id_celltype` | Кол-во ячеек | Название (из кода/FAQ) | Назначение |
|---|---|---|---|
| 1 | **217** | «домашняя» (HOME) | стартовая застройка, доступна сразу после регистрации |
| 2 | **28** | «центральная» (CENTRAL) | открывается после постройки/открытия Центральных Ворот (`CENTRAL_GATE`); военные здания, МККТ, фабрики юнитов |
| 3 | **217** | «нейтральная» (NEUTRAL) | открывается вместе с центральной; лагеря археологов, паруса-уловители энергии |

Расшифровка типов **подтверждена напрямую** двумя независимыми источниками
(в предыдущей версии `game-engine.md` это было отмечено как
неподтверждённая гипотеза — теперь расшифровано):

1. Doc-комментарий в самом коде,
   `ds/classes/DE/DE_CombCells.class.php:17`: *«ID части соты. 1 - домашка,
   2 - центральная, 3 - домашка»* (второе «домашка» для типа 3 — по всей
   видимости, опечатка/копипаст в комментарии; далее по названиям зданий и
   тексту FAQ тип 3 совершенно однозначно «нейтральная», не «домашняя»).
2. Внутриигровой FAQ прямым текстом описывает три части соты именно этими
   тремя названиями и их назначением: раздел «2.2. Как правильно застроить
   центральную соту» (`ds/help/faq.php:1336-1359`, военные заводы, МККТ,
   Колонизационный Центр), и раздел про нейтральную соту — «Лагерь
   археологов… После того как ваша домашняя сота и центральная будут
   полностью застроены, принимайтесь за нейтральную» (`faq.php:1163-1170`).

**Ключевая деталь про тип 2 (центральная, 28 ячеек):** число 28 — это
ячейки, принадлежащие **одной** соте, но клиент отображает их не как
изолированный блок 28 ячеек, а встроенными в общую мозаику **всех 6 сот
комплекса** размером в те же 217 «слотов», что и домашняя/нейтральная
части. Это реализовано классом `ds/classes/GB/GB_CombCentralViewMask.class.php`:
статическая маска из 217 элементов с разметкой `[тип]-[номер в клиентской
системе]-[номер в серверной системе]`, где тип — `E` (граница между
секторами разных сот), `F` (туман, скрывающий чужие соты комплекса) или `Z`
(ячейка **своей** соты, ровно 28 таких `Z`-ячеек). Отображение конкретной
соты в мозаике зависит от её `combnumber` (1-6) — маппинг делается через
`UA_Refresh3.class.php:213-268` (шесть предвычисленных масок `$mask[1]`…
`$mask[6]`, ротация `$d = 5 - $this->combnumber`). Итог: «центральная сота»
геймдизайнерски — это **общее для всех 6 соседей по комплексу пространство**,
в котором у каждого игрока реально застраиваемо только 28 клеток, а
остальные ~189 слотов в интерфейсе — либо декоративная граница, либо
затуманенные чужие территории.

### 1.5 Шаблоны грунта и стартовые здания (`applyTemplate`, `setBeginningBuildings`)

`WorldUtils::applyTemplate($id_comb)` (`WorldUtils.class.php:206-257`) для
каждого из 3 `celltype` выбирает случайный `ID_CellTemplate` из
`ds_celltemplate` (WHERE `id_celltype = …`), раскладывает типы грунта по
ячейкам через `ds_celltemplateelement` (`UPDATE ds_cell SET id_groundtype =
… WHERE cellnumber = t.cellnum`), и вызывает `setBeginningBuildings()` для
того же шаблона/типа.

`setBeginningBuildings($templateid, $id_comb, $celltype)`
(`WorldUtils.class.php:762-1018`) ставит здания, которые в шаблоне отмечены
`ID_Building IS NOT NULL` (т.е. не все 217/28/217 ячеек с самого начала
имеют здание — большинство пустые под застройку игроком). Особый случай —
кольцо колонизации (`ringname == 'RING_COLONIZE'`, строка 783): здание
`CENTRAL_GATE_WRECK` (руины Центральных Ворот, то, с чем стартует обычный
новый игрок) подменяется на уже активные `CENTRAL_GATE` — то есть **колонии
сразу стартуют с открытыми воротами** (доступ к центральной и нейтральной
сотам), а обычная домашняя сота новичка — с закрытыми (руинами), которые
нужно отстроить. Для не-колонийных зданий дополнительно: прибавляется
`TURN_PRODUCTION`/`TURN_UPKEEP`/`MAX_AMOUNT` здания к атрибутам соты,
проставляются флаги `DESTROYABLE`/`DEACTIVEABLE` (если явно не выставлен
флаг `BEGINNING_FLAG` у здания), и для здания `SHELTER` (Убежище) отдельно
переносится `STORAGE_FACTOR`/`STORAGE_FACTOR_ABSOLUT` (лимит хранения
ресурсов).

## 2. Настройки мира (`DE_WorldSettings`, таблица `ds_gamemodifier`)

`DE_WorldSettings` (`ds/classes/DE/DE_WorldSettings.class.php`) — простой
key-value кэш: конструктор грузит **весь** справочник `ds_gamemodifier`
(`SELECT * FROM ds_gamemodifier`, строка 74 — условие `WHERE id_world = …`
закомментировано в самом коде) в ассоциативный массив
`modifiername → value` и кэширует его в `GLOBAL_CACHE`; `get($name)`
возвращает значение или `0`, если модификатора нет. Поскольку каждый мир
физически живёт в **отдельной БД** (см. `multi-world-architecture.md`),
закомментированный `WHERE id_world` не проблема — таблица и так одна на
БД/мир, глобальный `SELECT *` корректен в этой архитектуре.

Это не единственная система настроек в проекте: `DE_GlobalSettings`
(`ds/classes/DE/DE_GlobalSettings.class.php`) — соседний, но **независимый**
key-value справочник (`DS_Misc::GetGlobalSettings()`), общий для всего
портала/кластера БД, а не для одного мира — в этот раздел он не входит.

Полный список имён модификаторов мира, вычитанных как `->get('ИМЯ')` по
всему `ds/classes` (≈140 штук; часть подтверждена конкретной формулой в
этом документе — отмечено ✓, остальные — только по имени, без
прочитанного кода использования):

> **читает** этот ключ (`UA_Colonize.class.php:212-219`, §5.3 ниже), то есть

> на практике значение всегда остаётся `0` (эффект отсутствует, т.е.
> `MAX_COLONIES_PREMIUM_DELTA` — мёртвый функционал в реальной эксплуатации,
> а не только в этом архиве кода), либо что пометка `Not used` в каталоге
> устарела/ошибочна, либо что бонус выставляется каким-то другим путём, не
> через этот ключ. Не установлено, какая из версий верна — стоит прямо
> уточнить у владельца проекта, работал ли когда-либо этот бонус на практике,
> прежде чем закладывать его в баланс ремастера.

## 3. Расы

### 3.1 Общий механизм: расовые атрибуты полностью в БД, не в PHP

Раса (`DE_Race`, `ds/classes/DE/DE_Race.class.php`) — тонкая обёртка над
строкой `ds_race` (`id_race`, `racename`, `id_localizedname`). Все игровые
эффекты расы вынесены в attribute-value модель: `DE_RaceAttributes`
(`ds/classes/DE/DE_RaceAttributes.class.php`) при создании тянет **все**
строки `ds_racehasattribute` для расы (`DS_Race::GetRaceAtrributes()`,
`ds/classes/DS/DS_Race.class.php:34-72`) и раскладывает их в массив
`[typename][attributename] = value`. Типов атрибутов как минимум два:
`BONUS_ABSOLUTE` и `BONUS_RELATIVE` (используются в бою, см. §3.4), плюс,
судя по `WorldUtils::setCombResource` (`WorldUtils.class.php:691-707`),
расовые бонусы могут добавляться прямо к **стартовым ресурсам** соты через
тот же механизм (`UPDATE ds_combhasresource SET value = value + t.val FROM
(SELECT id_attribute, value FROM ds_racehasattribute WHERE id_race = …)`).

**Важно для ремастера:** конкретные числовые значения `ds_racehasattribute`
живут в БД мира, которой в этом архиве кода нет — PHP лишь читает их
универсальным SQL-запросом. Поэтому ниже в §3.2 числа взяты не из БД (её
нет), а из **текстового FAQ игры** (`ds/help/faq.php`), который для игроков
прямо перечисляет проценты — и это единственный источник точных чисел,
доступный в архиве.

подтверждены числами из живой БД (таблица и врезка выше) для всех трёх
рас — раньше этот абзац утверждал, что проценты «не найдены нигде в
текстовых источниках архива»; это устарело.

Это даёт числовой ответ на вопросы, которые ниже в разделе «Открытые
вопросы» были помечены как неподтверждённые: у Воранеров числовой боевой
профиль оказывается «сильная атака (+10%), нулевая защита (+0%)» —
прямо противоположное направление тому, что «слабы в обороне» можно было
бы прочитать буквально, но согласуется с лором «сильны в нападении»;
«слабость Воранеров в археологии» подтверждается как **+0%** (не
отрицательное число, а именно отсутствие бонуса на фоне +8% у Псолао/+5%
у Лиенсу — после находки БД разрыв Псолао/Воранеры по археологии меньше,
чем казалось по вики: 8 пунктов, а не 10, см. врезку выше); «быстрое
размножение» Лиенсу подтверждается числом — **+5% к приросту населения**
(и заметно самый большой бонус к еде, +22%, что согласуется с лором
«поставщики еды»). Числа Лиенсу вообще самые «ровные» (5% почти по всем
боевым/непрофильным категориям) — согласуется с описанием в FAQ как расы
без явного профильного ресурсного бонуса, но с равномерно распределёнными
небольшими бонусами.

### 3.4 Применение расовых бонусов в бою — формулы (код, а не FAQ)

`GL_BattleBonuses::_countBonuses()` (`ds/classes/GL/GL_BattleBonuses.class.php:65-136`)
для владельца соты/армии собирает 4 категории бонуса — `ATTACK`, `DEFENCE`,
`DAMAGE`, `HITPOINTS` — каждая как объект `DE_Bonus`, куда **аддитивно**
добавляются вклады трёх источников: расовые атрибуты игрока
(`raceAttributes`), атрибуты активной религии (`religionAttributes`, см.
§4) и артефакты военной базы соты (`warArtefactsCollection`). Каждый вклад
имеет **абсолютную** (`BONUS_ABSOLUTE`) и **относительную**
(`BONUS_RELATIVE`) составляющую (`_addBonus()`, строки 138-159).

Итоговое применение бонуса к характеристике юнита — в
`DE_UnitsGroupWarPower` (`ds/classes/DE/DE_UnitsGroupWarPower.class.php`),
и здесь важна **асимметрия** между атакой и защитой:

- **Атака / урон / хитпоинты** — простое сложение относительных бонусов, а
  затем прибавление абсолютного:
  `attack = base*(1 + Σ relative) + absolute` (`getAttack()`, строки
  75-88; аналогично `getDemage()` строки 121-132, `getHitpoint()` строки
  164-177).
- **Защита** (старое поле `defend`, вероятность-подобная величина 0..1) —
  **регрессивное** (убывающая отдача) применение бонусов по цепочке:
  `defend = (1 - defend) * bonus + defend`, применяется по очереди для
  каждого относительного бонуса (`getDefend()`, строки 92-112, с
  комментарием в коде: *«При использовании защитного поля защита и,
  соответственно, регрессия, не используется»*). Есть и новая версия —
  `getDefenceField()` (строки 138-152): величина защиты сначала переводится
  в «защитное поле» (`1/(1-defend) - 1`), а бонусы к нему уже применяются
  **просто аддитивно** — то есть регрессия остаётся встроена в саму замену
  переменной, а не в порядок сложения бонусов.

Эта асимметрия **прямо подтверждена и текстом внутриигрового FAQ**
(`ds/help/faq.php:2408-2412`), причём формулировка почти дословно совпадает
с кодом: *«Все бонусы (расовые и религиозные) и артефакты считаются в
цепочке, по регрессии. Защита (относительный параметр). Регрессия
начинается с параметров юнита, т.е (1-защита юнита)\*значение параметра.
Урон и броня, нападение. Расчитываются по старому, т.е + к показателям
юнита»* — то есть игровой дизайн **намеренно** делает защитные бонусы менее
эффективными при стакинге, чем атакующие. Если у расы/религии одновременно
есть, скажем, +X% защиты и +X% атаки, эффективный прирост защиты при
прочих равных условиях меньше номинального X%, а атаки — равен номинальному
X%.

Класс `DE_Bonus` (`ds/classes/DE/DE_Bonus.class.php`) формально
предоставляет оба варианта агрегации — `getSummRelativeBonus()` (простая
сумма) и `getSummRegressivRelativeBonus()` (регрессия с сортировкой бонусов
по убыванию перед накоплением) — но по факту в живом
`DE_UnitsGroupWarPower::getDefend()` используется **инлайновая**
регрессивная реализация без сортировки (по порядку добавления бонусов —
раса, затем религия, затем военная база), а не вызов
`getSummRegressivRelativeBonus()` напрямую.

## 4. Религия

Религия в игре **не привязана к расе** механически: выбор религии
(`ds_userhasreligion`, ключ по `id_userinstance`, не по `id_race`) — это
отдельная опция для любого игрока любой расы, реализованная через
здание-Храм. Числовой набор бонусов задаётся точно тем же attribute-value
механизмом, что и раса (`ds_religionhasattribute`,
`DE_ReligionAttributes::CreateFromReligionID()`,
`ds/classes/DE/DE_ReligionAttributes.class.php`) — и точно так же
подмешивается в боевые бонусы (`GL_BattleBonuses`, §3.4) и в стартовые
ресурсы колонии (`WorldUtils::setReligionBonuses()`,
`WorldUtils.class.php:715-759` — применяется только при **колонизации**, не
при первичной регистрации).

**Ровно две религии** (FAQ прямым текстом: «одной из двух религий»,
`faq.php:784`), с зеркально противоположными профилями — экономика/защита
против экономика/атака. Храмы визуально «скинуются» под расу (найдены
файлы `tech_cloud_enders_temple`, `tech_rushers_temple`,
`bio_cloud_enders_temple`, `bio_rushers_temple`, `psi_cloud_enders_temple`,
`psi_rushers_temple` — `tech`=Воранеры, `bio`=Лиенсу, `psi`=Псолао), но
**каждая раса имеет доступ к обеим религиям** — то есть религия не
race-locked.

**Жизненный цикл выбора религии** — конечный автомат из трёх статусов
(`ds_religionstatus.statusname`, читается в
`ds/classes/PN/PN_ReligyPanel.class.php:126-141`):

```
(нет религии) → RELIGI_STATUS_CONNECT → RELIGI_STATUS_ACTIVE → [RELIGI_STATUS_KICK] → (нет религии)
```

- `RELIGI_STATUS_CONNECT` — переходный статус «принятие» (таймер, показан
  процент/дата завершения).
- `RELIGI_STATUS_ACTIVE` — полностью активна.
- `RELIGI_STATUS_KICK` — переходный статус «отказ» (тоже с таймером).

Переход в обе стороны занимает **4 суток** (`faq.php:1205`: «включение/
отключение = 4 суток»). Асимметрия применения бонусов во время перехода —
подтверждена и кодом, и текстом: `DE_ReligionUserInstanceAttributes`
(`ds/classes/DE/DE_ReligionUserInstanceAttributes.class.php:31-44`)
пропускает («continue») любой атрибут со значением `> 0`, если статус **не**
`RELIGI_STATUS_ACTIVE` — то есть **позитивные** бонусы применяются только
после полного завершения перехода, а **негативные** (отрицательные
значения атрибутов) действуют с самого начала процесса принятия. FAQ
формулирует это игроку так: *«Как только вы нажмете на кнопку принятия
религии, включатся отрицательные бонусы, но после окончательного принятия
включатся и положительные»* (`faq.php:1207`).

Храм требуется как условие выбора религии
(`ds_religionneedsbuilding`/`ab.active = true`, см. запрос в
`PN_ReligyPanel::getPanel()`, `ds/classes/PN/PN_ReligyPanel.class.php:60-93`)
и, по FAQ, действует **на домашнюю соту и все колонии сразу**, поэтому
храм достаточно построить один раз в одном месте (`faq.php:1209`).

**Дополнение с портала** (`https://destinysphere.ru/?p=buildings_voraner`,
`?p=buildings_liensu`, `?p=buildings_psolao`,
`ds/help/?name=INFO_GAME_MAIN`, глава 2.4). Числа бонусов обеих религий на
портале **дословно совпадают** с уже приведёнными выше по `faq.php`
(Нанокристаллы+10%/Защита+10%/Броня+15% против Кадериум-15%/Продиум-5%/
Нападение-15%/Урон-15% для Созерцателей; зеркально для Штурмовиков) —
независимый третий источник для тех же цифр. Каталог зданий **каждой** из
трёх рас (страницы `buildings_voraner`/`buildings_liensu`/`buildings_psolao`)
содержит **оба** храма с идентичным текстом описания — прямое player-facing
подтверждение тезиса «религия не race-locked», который в этом разделе выше
был выведен только косвенно (по именам файлов текстур). Мануал добавляет и
факт, не встречавшийся ни в PHP-коде, ни в `faq.php`: **храмы также
требуются для реинкарнации погибших** (`INFO_GAME_MAIN`, глава 1.8) —
механика реинкарнации в этот документ не входит, см.
`docs/mechanics-reincarnation.md`. Внутренние строковые коды религий
(`cloud_enders`/`rushers`) портал не подтверждает и не опровергает — на
всех просмотренных страницах фигурируют только русские названия
«Созерцатели»/«Штурмовики», поэтому соответствующий пункт в разделе
«Открытые вопросы» ниже остаётся открытым.

## 5. Создание персонажа и колонизация

### 5.1 Регистрация в новом мире — `WorldUtils::addNewInstance()`

`ds/classes/WorldUtils.class.php:269-655`, полный список того, что получает
новый игрок:

1. **Подбор соты.** Если у пользователя есть **зарезервированная** сота на
   не-Мелсион кольце (`ds_reservedcomb`, join на `ringnumber != 4`, строки
   281-337) — используется она, а раса определяется **по кольцу** этой

7. **Стартовые науки**: всё, что подходит под SQL-регексп `sciencename ~
   '_1$'` (строка 505) — то есть **1-й уровень каждой ветки наук**
   выдаётся сразу как «уже изученный» (`inresearch = false`), без

8. **Стартовые ресурсы и расовый бонус** — `setCombResource()` (§5.1.1

9. **Сброс ландшафта** соты (ещё раз применяется случайный шаблон грунта —

    сообщений: `PRIVATE`, `COMB_COMPLEX`, `GAME_MASTER`, `GAME_HELPER`

13. После `commit()` — переключение на «портальную» БД (`dbId=0`) и
    регистрация в глобальной таблице `ds_userinstancecollection` +
    декремент `ds_worldcollection.max_users` (строки 611-652) — это уже
    межмировая бухгалтерия, синхронизирующая список миров в центральной БД.

Расовые бонусы к артефактам/археологии **не** выдаются на старте отдельно —
они действуют постоянно как часть боевых/археологических формул (§3.4,
§6.4), а не как одноразовая выдача при регистрации.

#### 5.1.1 `setCombResource($id_comb, $id_race)` — формула стартовых ресурсов

`WorldUtils.class.php:658-712`. Две последовательные операции:

```
value += (ds_resource.startamount + COALESCE(ds_start_resource.amount, 0))   -- база + опциональный оверрайд конкретного мира
value += ds_racehasattribute.value   -- для той же ячейки CURRENT_AMOUNT, где id_race = выбранная раса
```

То есть стартовое количество каждого ресурса — это (а) глобальная базовая
величина `ds_resource.startamount`, (б) плюс опциональная **надбавка,
специфичная для конкретного мира** (`ds_start_resource` — отдельная от
`ds_gamemodifier` таблица переопределений именно стартовых ресурсов на
уровне мира), (в) плюс расовый бонус к ресурсу (`ds_racehasattribute` с
типом `CURRENT_AMOUNT`) — это тот же канал, что даёт Воранерам +17%
Кадериума и т.п. (§3.2), просто здесь не относительный, а абсолютный
довесок к стартовому количеству.

1. Если `RANDOM_COMB_FOR_NEW_INSTANCE` включён (или передан флаг
   `$useRandomNow`) **и** заданы `RANDOM_COMB_MIN_COMPLEX <
   RANDOM_COMB_MAX_COMPLEX` — считает число свободных сот в диапазоне
   номеров комплекса (`DS_Comb::GetCountFreeCombsInComplexRange()`,
   `ds/classes/DS/DS_Comb.class.php:663-710`, критерии свободы: `id_userinstance
   IS NULL`, `is_capture='f'`, нет записи в `ds_reservedcomb`).
2. Если такие соты есть — берёт случайный **смещение** (`rand(0,
   randomCombCount)`) и выбирает соту по этому смещению
   (`GetFreeCombIdInComplexsRangeByRaceAndRandomOffset()`, строки 718-762,
   `LIMIT 1 OFFSET $offset`).
3. Иначе (рандом выключен или нет подходящего диапазона) — берёт **первую
   по возрастанию `id_comb`** свободную соту на всём кольце
   (`GetMinCombIDForPlacementOnRing()`, строки 614-660) — то есть без
   рандома игроков просто «набивают» соты по порядку создания.

Любопытная деталь именования: в
`GetCountFreeCombsInComplexRange`/`GetFreeCombIdInComplexsRangeByRaceAndRandomOffset`
формальный параметр называется `$id_race`, но в SQL сравнивается с
`r.ringnumber` — то есть по факту это **номер кольца**, а не ID расы;
имя параметра — исторический пережиток (кольца 1-3 действительно совпадают
по смыслу с «базовым кольцом расы», поэтому путаница в имени не приводит к
багу, но вводит в заблуждение при чтении кода).

### 5.3 Колонизация действующим игроком — `UA_Colonize` / `EH_Colonize`

В отличие от регистрации, колонизация — это **связка** пользовательского
действия и асинхронного события:

**`UA_Colonize`** (`ds/classes/UA/UA_Colonize.class.php`) — валидация
запроса на колонизацию:
- Имя колонии — те же правила, что у имени соты при регистрации (3-20
  симв., запрещённые символы, уникальность), строки 36-46.
- Нельзя колонизировать **с** соты, которая сама является захватываемой
  колонией (`getIsCapture()`, строка 49).
- Требуется активный `CENTRAL_GATE` на исходной соте (строки 190-209) —
  «домашние ворота» должны быть открыты, чтобы отправить экспедицию.
- Модуль колонизации — отдельный тип юнит-контейнера
  (`ds_unitorcontainertype.containertypename = 'COLONIZATION'`, строки
  172-187), должен быть свободен (`inaction = false`).
- Лимит колоний: `MAX_COLONIES` (+`MAX_COLONIES_PREMIUM_DELTA` для
  премиум-игроков, `$_SESSION['profi_game']`), считается по фактическому
  числу сот игрока в комплексах с `complextype = 'COLONIZEABLE'` и
  `is_capture='f'` (строки 212-248).

  **Иллюстративные значения `MAX_COLONIES` по текущим мирам** (источник:
  `https://destinysphere.ru/?p=game_option`, живые данные 2026 года — это
  дополняет, а не заменяет вики-снимок 2014 года из §3.2/§6.1 выше, снятый
  с другого мира и в другой момент времени):

  | Мир | Тип мира | `MAX_COLONIES` |
  |---|---|---:|
  | Змееносец | каждый против каждого | 5 |
  | Орион | каждый против каждого | 3 |
  | Феникс | каждый против каждого | 3 |
  | Ворон | каждый против каждого | 2 |
  | Волк | каждый против каждого | 2 |
  | Стрелец | каждый против каждого | 2 |
  | Эридан | раса против расы | 4 |
  | Пегас | раса против расы | 3 |
  | Водолей | раса против расы | 2 |
  | Лев | раса против расы | 2 |
  | Терра Нова | раса против расы | 1 |

  Разброс 1-5 в целом подтверждает диапазон «от двух до пяти», который
  портальный мануал (`INFO_GAME_MAIN`, глава 1.8) называет общим правилом
  — с одним найденным исключением ниже этого диапазона: мир Терра Нова

  **Телец** и **Дракон** колонизация на 1-м уровне развития мира вообще
  запрещена; ни Телец, ни Дракон не встретились в снятой на дату
  архивации таблице `game_option` — вероятно, эти миры уже закрыты или
  переименованы.

  **Точные значения на 4 дополнительных живых мирах (источник: БД,
  live-запрос, 2026-09-02)** — прямой SQL-запрос к `ds_gamemodifier`, не
  портальная страница:

  | Мир (по внутреннему `dbId`) | `MAX_COLONIES` |
  |---|---:|
  | Чёрная дыра (`hell`) | **9** |
  | Сфера Парусов (`phoenix`) | 2 |
  | Сфера Змееносца (`premium`) | 5 |
  | Сфера Гончих Псов (`turnir`, турнирный) | 2 |

  Наблюдения: «Сфера Змееносца» (`dbId=premium`) даёт `MAX_COLONIES=5` —
  дословное совпадение со строкой «Змееносец» в портальной таблице выше,
  разумно предположить, что это один и тот же мир под двумя разными
  ярлыками (внутренний `dbId` и портальное имя). «Чёрная дыра» —
  **выброс за пределы диапазона портальной таблицы**: `MAX_COLONIES=9`
  заметно выше любого из 11 миров `game_option` (максимум там — 5) и
  выше диапазона «от двух до пяти» из мануала `INFO_GAME_MAIN`, то есть
  этот диапазон не универсален для всех миров архива. Отдельно стоит
  предостеречь от путаницы: `dbId=phoenix` называется по-английски как
  «Феникс», но реальное русское имя мира в БД — **«Сфера Парусов»**
  (`MAX_COLONIES=2`), которое отличается от мира «Феникс»
  (`MAX_COLONIES=3`) из портальной таблицы выше — судя по всему, это два
  разных мира, несмотря на созвучное происхождение технического `dbId`;
  не стоит путать одно с другим.
- Цель — либо явные координаты (`кольцо.комплекс.сота`), либо `rand` —
  тогда цель выбирается тем же `GL_GetCombForPlacement::Get()`, что и при
  регистрации (строки 105-125).

**`EH_Colonize`** (`ds/classes/EH/EH_Colonize.class.php`) — асинхронный
обработчик события перемещения модуля колонизации, с явным комментарием в
коде (капсом): *«ПРОШУ ОТМЕТИТЬ ЧТО ЭТО ЕДИНСТВЕННОЕ МЕСТО ГДЕ МЕНЯЕТЬСЯ
ПРИНАДЛЕЖНОСТЬ СОТЫ ИГРОКУ В ПРОЦЕССЕ ИГРЫ!!!»* (строки 94-96) — то есть
смена владельца соты вне регистрации нового аккаунта происходит **только**
здесь. По прибытии модуля на целевую соту (`Stage == 1` при завершении
таймера):
1. `ds_comb.id_userinstance` = игрок, `combscore = 0`.
2. Вызываются те же `WorldUtils::setCombResource()` и
   `WorldUtils::setReligionBonuses()`, что и при обычной регистрации —
   колония получает стартовые ресурсы расы **и** активные бонусы религии
   игрока (в отличие от регистрации, где `setReligionBonuses` не
   вызывается — на старте игрок религию ещё не может иметь).
3. Создаётся пустой контейнер домашней армии колонии (как при регистрации).
4. Грунт колонии ещё раз рандомизируется по шаблону (сброс терраформации).
5. Если это **вторая** колония игрока (считая домашнюю соту — т.е. первая
   реальная колония), и у игрока есть реферер — рефереру начисляется
   `COLONY_OPEN_SUM` серебряных кредитов (константа читается через
   `UC_PaymentGC::GetParam('COLONY_OPEN_SUM')` — это отдельная система
   платёжных констант, не `DE_WorldSettings`).

Если колонизация отменена в пути (`Stage == 2`) — модуль просто
возвращается домой, владелец соты не меняется.

### 5.4 Специализация застройки колонии (player-facing, источник — портал)

> Источник: `ds/help/?name=INFO_GAME_MAIN`, главы 4.2-4.3. Дополняет §5.1-5.3
> выше конкретными player-facing деталями о том, *зачем* и *как* игроки
> используют колонии, а не только техническими фактами о том, как колония
> создаётся.

В обычной (не захватываемой, см. §5.5) колонии строятся те же типы зданий,
что и в домашней соте — процесс идёт быстрее, поскольку нужные уровни наук
уже изучены на момент колонизации. Портал описывает частичную и полную
специализацию застройки:

- **Неполная специализация** — домашняя сота колонии застраивается
  зданиями одного профильного ресурса без терраформинга, а
  центральная/нейтральная часть остаётся под непрофильные здания
  (археологи, продиум, фабрики и т.д.). Портал называет это «началом пути»
  к полной специализации — на этом этапе легче удерживать неотрицательный
  баланс энергии.
- **Полная специализация** — максимально возможное число добывающих
  зданий одного ресурса и в домашней, и в центральной сотах, с
  терраформингом травы в землю (место под профильные здания) и воды в
  песок (обеспечение энергией); Башня артефактов заполняется исключительно
  профильными артефактами. Портал даёт конкретную иллюстративную цифру:
  для эффекта требуется порядка **580 локальных артефактов** на профильный
  ресурс. Полная специализация, по тексту портала, целесообразна только на
  поздних этапах игры, когда бонусы науки и артефактов уже позволяют
  добывающим зданиям выйти на максимальную отдачу.

Другие типовые сценарии использования колоний, перечисленные порталом:
колония под один ресурс; колония, полностью занятая под археологию
(порядка **70 тысяч** археологов при полной застройке); колония научных
центров под интенсивное изучение конкретной дисциплины; равномерное
развитие без специализации; военно-промышленный комплекс (ВПК) — колония
из военных заводов с постоянной пересылкой ресурсов на неё и непрерывной
тренировкой юнитов; полный терраформинг поверхности под нужный тип
грунта.

Рекомендованное число рабочих по расе, приведённое порталом (Воранеры
8-15 тыс., Псолао 4-6 тыс., Лиенсу 20-30 тыс.), дословно совпадает с уже
приведённой в §3.3 таблицей из `faq.php` — независимое подтверждение тех
же чисел третьим источником.

### 5.5 Захватываемые колонии (player-facing, источник — портал)

> Источники: `https://destinysphere.ru/?p=colonies`,
> `ds/help/?name=INFO_GAME_MAIN` главы 4.4-4.5. Это отдельный **вид**
> колонии (не альтернатива обычной из §5.3-5.4) — определяется флагом
> `is_capture`/`DE_Comb::getIsCapture()`, уже встречавшимся в §1.3 выше
> (`ds_comb.is_capture`) и в `mechanics-buildings.md` (`ds_disabledbuilding_colony`,
> спецбонусы `BONUS_COLONY_ATTACK`/`BONUS_COLONY_DAMAGE` в §2.2 настроек
> мира) — здесь эти код-подтверждённые факты дополняются игровым текстом о
> том, зачем и как это используется игроком, что код сам по себе не
> объясняет.

**Что это и зачем захватывать.** Захватываемые колонии физически находятся
там же, где обычные — на кольце Мелсион, — но изначально принадлежат
служебному игроку «Destiny Sphere» (не пустуют, как обычные незаселённые
соты кольца колонизации, §1.1). Отличаются жёлтым цветом Центральных Ворот
на виде комплекса. Смысл для игрока — дополнительная сота **без** траты
собственного модуля колонизации и без учёта в обычном лимите
`MAX_COLONIES` (у захватываемых колоний отдельный, обычно гораздо более
узкий лимит — например, «не более 1 на игрока», см. таблицу ниже), но с
риском: её может отбить другой игрок военным путём.

**Как захватить** (`INFO_GAME_MAIN`, 4.4; числа по науке подтверждены
дословно и на `?p=colonies`): нужны научные уровни Кадериум 12,
Нанокристаллы 12, Продиум 12, Статическая энергия 20, Еда 20; нужно
уничтожить защитное поле колонии (снижается на фиксированный процент за
каждую победу, см. таблицу настроек ниже) и одержать после этого ещё одну
победу; нужно также уничтожить весь защищающий гарнизон **и** специального
юнита колонии (по одному на расу: Разрух — Воранеры, Военный Советник —
Лиенсу, Иллюзия — Псолао; тренируются в казармах 1-го уровня, 1 шт./час,
стоят 100 000 продиума + 2 000 000 энергии + 1 000 000 еды + 500 000
кадериума + 300 000 нанокристаллов, нельзя продать или переместить, но
можно спрятать в укрытие — это не мешает захвату при прочих выполненных
условиях). Если хотя бы одно условие не выполнено — сота просто грабится,
как обычная, без смены владельца. В мирах «раса против расы» захватывать
можно только соты противоположных рас.

**Как защитить.** После захвата действует временная защита (по конкретным
мирам из таблицы ниже — 12 или 24 часа). Единственное здание, доступное
только на этом типе колонии — **Генератор Защитного Поля** (строится на
земле в домашней соте колонии, в одном экземпляре, время постройки
1 час); поле стартует со 100% прочности, тает на фиксированный процент за
каждое поражение, восстанавливается мгновенно за ресурсы/серебро. Портал
прямо предупреждает: включённый Силовой щит **не** защищает захватываемую
колонию от нападения (в отличие от обычных сот) — «Силовой щит» и
«Генератор Защитного Поля» это два разных здания с разной функцией, и
активированный щит на такой колонии даже не даёт уведомления о нападении.

**Особенности и ограничения** (§4.5 портала, дополняет код-подтверждённые
`BONUS_COLONY_ATTACK`/`BONUS_COLONY_DAMAGE`/`ALLOW_DEFEND_CAPTURE_COLONIES`
из `mechanics-buildings.md`): бонус атаки/урона при ударе **с** такой
колонии; повышенный бонус производства **на** ней; запрещённые к постройке
здания — Терраформер, оба Храма, Силовой щит, Дом отдыха; нельзя переехать
по кольцу или переименовать колонию; отдельное (не общемировое) время
трансфера; отдельный потолок раундов боя; отдельный лимит артефактов в
военной базе; «Тихий час» — ночное окно (в примере ниже 3:30-6:30), в
которое нельзя начать атаку на такую колонию (уже идущие бои
досчитываются по обычным правилам).

**Что происходит при потере/добровольном отказе** (списки в обоих
источниках совпадают дословно): здания перекрашиваются под расу нового
владельца; все армии прежнего владельца (летящие, в бою, возвращающиеся)
переадресуются на его домашнюю соту и сливаются в одну; лоты и трансфер
переписываются на домашнюю соту; все незавершённые процессы (апгрейд,
активация, постройка юнитов, терраформинг, наука, археологические
экспедиции, полёты шпионских зондов) отменяются; зонды разлагаются,
военный опыт и ресурсы за них возвращаются прежнему владельцу; артефакты
(где бы ни находились) разлагаются в ресурсы; археологи и учёные едут на
домашнюю соту (или гибнут, если там нет места); Генератор Защитного Поля
автоматически сносится; часть ресурсов уходит «администрации» как налог;
новому владельцу включается защита новичка на срок из таблицы ниже. При
добровольном отказе от колонии включается отдельная временная защита
случайной длительности (не более 8 часов, по одному из источников), и
отказаться нельзя, если защитное поле ниже порога (см. таблицу).

**Иллюстративные настройки для двух конкретных живых миров, Волк и
Водолей** (источник: `?p=colonies`, раздел «Настройки колонии» —
конкретные числа этих двух миров, не общий код):

| Параметр | Значение |
|---|---|
| Время трансфера | 5 часов |
| Максимум артефактов в военной базе колонии | 5 |
| Бонус атаки с колонии | 18% |
| Бонус урона с колонии | 18% |
| Снижение защитного поля за поражение | 5% |
| Максимум раундов боя за колонию | 10 |
| Максимум захватываемых колоний на игрока | 1 |
| Мин. уровень науки для захвата | Еда 20, Кадериум 12, Нано 12, Продиум 12, Энергия 20 |
| Временная защита после захвата | 12 ч (Волк) / 24 ч (Водолей) |
| Бонус производства на колонии | 300% (Волк) / 200% (Водолей) |
| Налог администрации при потере/отказе | 5% |
| Мин. защитное поле для добровольного отказа | 90% |
| «Тихий час» | 3:30-6:30 |
| Запрещённые здания | Силовой щит, оба Храма, Терраформер, Дом отдыха |

Эти цифры (как и `MAX_COLONIES` в §5.3 выше) — настройка конкретных миров
в таблице настроек, подобной `ds_gamemodifier`, а не универсальная
константа кода; для других миров из таблицы `mechanics-buildings.md` §17.3
значения могут отличаться.

## 6. Рейтинги

В коде архива нашлись **две независимые системы рейтинга**, легко
перепутать между собой:

1. «Уровень/лига» (`DE_Ranking`/`DS_Ranking`, таблица `ds_ranking`) —
   инкрементальный счётчик очков по 4 категориям, апдейтится **в реальном
   времени** при каждом игровом событии, определяет `id_level` игрока и
   (опционально) его лигу.
2. «Общий рейтинг» / «Детальный рейтинг» (таблицы `ds_finalranking`,
   `ds_detailedranking`, `ds_allianceranking`) — сравнение со **средним по

### 6.1 Система уровня/лиги — `DE_Ranking` / `DS_Ranking`

Хранятся 4 накопительных счётчика на игрока: `science_ranking`,
`artefact_ranking`, `building_ranking`, `battle_ranking`
(`ds/classes/DE/DE_Ranking.class.php:9-22`). Игровые события инкрементируют
их напрямую (пример — `EH_UpgradeBuilding.class.php:253`:
`deltaBuildingRanking(buildinScoreTo - buildinScoreFrom)` при завершении
апгрейда здания, где `buildingScore` берётся из справочника
`DS_Building::GetBuildingScoreNew()`).

При каждом изменении пересчитывается уровень
(`DS_Ranking::GetAccordanceLevel()`, `ds/classes/DS/DS_Ranking.class.php:47-81`):

```
battle_ranking = DE_BattleXP::CreateFromID($uiid)->getXPAbsolute()   -- боевой счётчик берётся не из БД напрямую, а всегда пересчитывается через BattleXP
ranking = science_ranking   * RANKING_SCIENCE_MULTIPLIER
        + artefact_ranking  * RANKING_ARCHEOLOGY_MULTIPLIER
        + building_ranking  * RANKING_BUILDING_MULTIPLIER
        + battle_ranking    * RANKING_BATTLE_MULTIPLIER

id_level = уровень из ds_ranking_level, где score_from < ranking < score_to
```

— крон-джоб, который:
1. Архивирует текущий `ds_finalranking` в `ds_finalrankinghistory` (храня
   `DAYS_TO_STORE_RANKING_HISTORY` дней).
2. Пересобирает `ds_finalranking` из представления БД **`qry_overallranking`**
   (join с юзером/сотой/расой/альянсом/кольцом/комплексом; исключает
   комплексы, не являющиеся `id_complextype = 1`, и служебного игрока
   `Mimicry`).
3. Пересобирает `ds_detailedranking` (`armyranking`, `artefactranking`,
   `buildingranking`, `productionranking`, `scienceranking`) из ещё пяти
   представлений БД: `subqry_armyranking_final`,
   `subqry_artefactranking_final`, `subqry_buildingranking_final`,
   `subqry_productionranking_final`, `subqry_scienceranking_final`.
4. Отдельно пересобирает `ds_allianceranking` — суммарные/средние очки
   альянса (`sum`/`avg` по `ds_finalranking.thefinal` для членов альянса).

**Обновление: точная SQL-формула найдена и подтверждена.** Раньше этот
раздел мог опираться только на пересказ из внутриигрового FAQ, потому что
представления `qry_*`/`subqry_*` — чистый SQL на стороне БД, не
выгруженный в PHP-архив. Теперь есть `schema.sql`
(`pg_dump --schema-only` живой игровой PostgreSQL БД, без данных, только
структура/представления/функции) — в нём все шесть представлений
процитированы дословно (`schema.sql:23089-23388`). FAQ-реконструкция
оказалась верна по сути (базы 100 000/200 000 подтвердились), но точный
SQL раскрывает детали, которых в пересказе FAQ не было:

```sql
-- qry_overallranking — итог, простая сумма пяти под-рейтингов
-- (COALESCE-подобная логика: NULL у отсутствующего параметра → 0)
thefinal = COALESCE(armysum,0) + COALESCE(buildingsum,0)
         + COALESCE(artefactsum,0) + COALESCE(finalranking,0)  -- production
         + COALESCE(sciencesum,0)
```

Каждое `*_final`-представление — это `(значение_игрока / среднее_по_миру) * baseline`,
как и предполагалось, но вот что именно является «значением игрока» в
каждой категории — раскрыто впервые:

- **Армия (`baseline = 200 000`)**: `SUM(ds_unithasattribute.value * ds_resource.exchangerate * количество_юнитов)`
  **только для армий с `ds_unitcontainer.id_unitcontainertype = 1`**
  (`subqry_armyranking`, `schema.sql:23089-23096`) — то есть в рейтинг
  идёт не любая армия игрока, а только определённый тип контейнера,
  а именно **`ARMY`** (расшифровка полного `enum` подтверждена прямым
  запросом к живой БД, `ds_unitorcontainertype`, источник: БД, live-запрос,
  2026-09-02: `1=ARMY, 2=SPY, 3=COLONIZATION, 4=SCIENCE, 5=ARCHEOLOGY,
  6=WORK` — значение `3=COLONIZATION` совпадает с тем, что уже было
  известно по коду в §5.2, `ds_unitorcontainertype.containertypename =
  'COLONIZATION'`).
  То есть в армейский рейтинг действительно идёт только «полноценная армия»
  соты — зонды-шпионы, колонизационный модуль, научный/археологический/
  рабочий контейнер в неё не попадают, даже если формально «весят» что-то
  по `ds_unithasattribute`. Есть
  орфанное, побитово идентичное представление `subqry_armyranking_with_transport`
  (`schema.sql:23395-23402`) — определение совпадает один в один с
  `subqry_armyranking`, но никакая другая вьюха на него не ссылается;
  похоже на неудалённый черновик более раннего варианта формулы.
- **Строительство (`baseline = 100 000`)**: `SUM(ds_comb.combscore)` по
  всем сотам игрока (`schema.sql:23193-23208`) — то есть у каждой соты
  уже есть готовое поле `combscore` (см. также `EH_Colonize` в §5.3 этого
  документа: `combscore = 0` при колонизации), и рейтинг строительства —
  просто сумма этих полей. Как считается сам `combscore` за пределами
  «сбрасывается в 0 при захвате новой соты» — не установлено (нужен
  отдельный поиск по PHP-коду, вне рамок этой задачи).
- **Артефакты/археология (`baseline = 100 000`)**: `SUM(1 / ((rangeto − rangefrom)/5 + 0.01) / baseprobability)`
  по каждому реально прикреплённому к зданию артефакту, отфильтрованному
  флагом `ds_artefact.calc_in_ranking` (`schema.sql:23146-23161`) — то
  есть это не просто счётчик артефактов, а **взвешенная по редкости**
  сумма: чем уже диапазон `rangefrom`-`rangeto` и чем ниже
  `baseprobability` артефакта (то есть чем он реже/ценнее), тем больше
  очков даёт один экземпляр. Флаг `calc_in_ranking` подтверждает
  FAQ-примечание «считаются только реально установленные артефакты» — но
  раскрывает, что это управляется отдельным булевым полем на самом
  артефакте, а не просто фактом «прикреплён/не прикреплён».
- **Производство (`baseline = 100 000`)**: `SUM(ds_combhasresource.value * ds_resource.exchangerate)`
  по атрибутам ресурсов с `id_attribute` от 9 до 13 включительно
  (`schema.sql:23244-23255`) — **это ТЕКУЩИЙ ЗАПАС ресурсов на сотах
  игрока, взвешенный по курсу обмена, а не скорость производства/добычи**,
  несмотря на название «productionranking». Название представления вводит
  в заблуждение — стоит явно решить для ремастера, воспроизводить ли
  именно эту (возможно, исторически случайную) трактовку «производства».
  Есть орфанная пара `subqry_productionranking_raw_old`/`subqry_productionranking_max`
  (`schema.sql:23421-23443`) — `_old` побитово идентична актуальной
  `subqry_productionranking_raw`, а `_max` берёт `MAX()` вместо `AVG()`
  по этой старой версии и никем не используется — похоже на заброшенный
  эксперимент с альтернативной формулой (макс. вместо среднего).
- **Наука (`baseline = 100 000`)**: `SUM(ds_science.researchcosts)` по
  ВСЕМ наукам, когда-либо изученным игроком (`ds_userhasscience`,
  `schema.sql:23287-23297`) — это суммарная «стоимость» всей карьеры
  исследований, а не какой-то отдельный «научный рейтинг» — то есть чем
  дороже была каждая изученная наука (`ds_science.researchcosts`), тем
  больше очков, независимо от того, какая это ветка/уровень.

Отдельно подтверждено: в рейтинг археологии считаются **только реально
установленные (используемые) артефакты**, не то, что просто лежит в
хранилище (`faq.php:1300`) — теперь видно, что это реализовано через
JOIN с `ds_artefactattachedbuilding`/`ds_attachedbuilding` (артефакт
физически должен быть прикреплён к постройке) в сочетании с флагом
`calc_in_ranking`, а не одним из этих двух механизмов по отдельности.

### 6.3 Боевой (военный) рейтинг

Отдельная величина, видимая игроку рядом с общим рейтингом (пример из
самого FAQ, `faq.php:1941,1945`: *«Военный рейтинг: 234.946 + 0.01223»* —
формат «накопленный счёт + дельта за последнее действие»). Формула по FAQ
(`faq.php:1330`):

```
военный_рейтинг += (стоимость_убитых_юнитов_в_продиуме) / 1 000 000
```

*«Убил на 1 000 000 прода — получил 1 рейта. Убил на 2 000 000 — получил
2»*. Если на защите было несколько армий разных владельцев — прирост
рейтинга атакующего делится между обороняющимися **пропорционально весу их
армий** (`faq.php:1330`, дословно: «делится согласно отношению весов их
армий»). В коде это соответствует подсистеме `DE_BattleXP`/`GL_BattleXP*`
(`ds/classes/DE/DE_BattleXP.class.php`, `ds/classes/GL/GL_BattleXP*.class.php`
— не читались построчно в рамках этой задачи, но именно
`DE_BattleXP::getXPAbsolute()` — источник `battle_ranking` в §6.1, так что
эта военная величина и есть `battle_ranking` из системы уровня/лиги, а не
третья отдельная система).

### 6.4 Формула вероятности находки артефакта (археологический рейтинг привязан сюда же)

`GL_ArtefactSearch::isFound()` (`ds/classes/GL/GL_ArtefactSearch.class.php`):

```
endProbability = scopeProbability * (archeologistsCount + archeologistsCount * archBonus) * searchTime * 1000
endProbability *= ARTEFACTS_PROBABILITY_BOOST     -- настройка мира
endProbability = min(endProbability, 900)          -- жёсткий потолок 90%

найдено = (rand(1, 1000) <= endProbability)
```

`archBonus` — как раз тот самый расовый бонус археологии
(`DS_Archeology::getRaceBonus()`, §3.2/§3.4) — то есть числовая механика
«Псолао удачливы в поиске артефактов» (лор из Википедии) подтверждается
буквально: у Псолао `archBonus = 0.10` (по FAQ), у остальных рас —
предположительно 0 или меньше (число для Воранеров/Лиенсу не найдено).

**Player-facing описание категорий/размеров артефактов** (какие бывают, куда
вставляются, как их можно получить), **число археологов на экспедицию и
вместимость Института археологии** — не относится напрямую к формуле
находки выше, разобрано отдельно в
[mechanics-economy-trade.md, §6.2 и §6.9](mechanics-economy-trade.md)
(источники — `ds/help/?name=INFO_GAME_MAIN` и справочные страницы портала
`?p=art_zd`/`?p=art_s`/`?p=art_k`/`?p=art_a`/`?p=artefact_destruction`).
