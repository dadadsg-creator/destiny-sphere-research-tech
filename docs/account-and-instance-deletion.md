# Удаление аккаунта/инстанса — подсистема `DU`

> Источник: `old-sphere` (PHP, read-only). Кодировка файлов — Windows-1251 (читалось через `iconv -f CP1251 -t UTF-8`, там где были русские комментарии — их немного, большинство файлов `DU/` не прокомментированы вовсе).
> Все ссылки вида `file.php:строка` указывают на `old-sphere/<путь>`.
> Раздел про `DU_DeleteAlliance` частично пересекается с уже установленным фактом из
> [`mechanics-alliances-diplomacy.md`, §4.7 и §4.10, находка №10](mechanics-alliances-diplomacy.md) —
> здесь он не пересказывается заново, а расширяется на весь пакет `DU_Delete*` (12 классов, не один).
> `DU_DeleteScience` также мимоходом упомянут в [`mechanics-research.md`, раздел 1](mechanics-research.md) —
> там он описан только как «утилита очистки», без вывода о живом/мёртвом статусе; этот документ такой вывод даёт.

## TL;DR

`DU` (16 файлов, `ds/classes/DU/`) — это подсистема, которая *должна* была реализовывать каскадное
PHP-удаление всех данных игрового аккаунта (инстанса) при закрытии/переносе, но в реальности **почти
целиком мертва**. Из 16 файлов:

- **12 файлов** (`DU_Delete*` — армии, бои, здания, соты, альянс, наука, религия, сообщения, события,
  артефакты, археология, детали инстанса) — мёртвый код. Все они перечислены в массиве `deleteCompanents`
  контроллера, но `foreach`, который бы их вызывал, **целиком закомментирован**
  (`DU_ControllerDeleteUserInstance.class.php:58-67`). Ни один из этих 12 классов не инстанциируется больше
  нигде в кодовой базе (проверено `grep` по `new DU_Delete*(` за пределами `DU/`) — то есть это не только
  отключённый, а полностью недостижимый код.
- **`DU_DeleteBase`** (13-й файл) — абстрактный родитель для этих 12 мёртвых классов; сам по себе не мёртв
  синтаксически, но нужен только им.
- **`DU_ControllerDeleteUserInstance`** — жив и активно используется (5 разных вызывающих найдено), но
  реально в нём исполняется только один SQL-вызов: `SELECT drop_uiid(UIID)` (`:96`). Это тонкая PHP-обёртка
  вокруг хранимой PL/pgSQL-процедуры, которая и делает всё каскадное удаление на стороне БД — независимо
  от (и куда полнее, чем) мёртвый PHP-пайплайн. Подробный построчный разбор самой `drop_uiid()`
  (в части альянсов) — в `mechanics-alliances-diplomacy.md`, §4.10.
- **`DU_ClearWorld`** — жив, реальный оркестратор: применяет `DU_ControllerDeleteUserInstance` ко **всем**
  инстансам одного игрового мира разом (полная очистка мира под повторное использование).
- **`DU_AddDeletionToStatistic`** — жив, но не имеет отношения к самому удалению: это счётчик статистики
  «сколько аккаунтов выбыло из мира сегодня», вызываемый только из одного места.

Таким образом из 16 файлов пакета **фактически работают 3** (`DU_ControllerDeleteUserInstance`,
`DU_ClearWorld`, `DU_AddDeletionToStatistic`), ещё один (`DU_DeleteBase`) — мёртвый по транзитивности, а
**12 — полностью мёртвый, недостижимый код**. Это тот же паттерн, что уже был зафиксирован для
`DU_DeleteAlliance` в отдельности в `mechanics-alliances-diplomacy.md` — здесь подтверждено, что он
касается **всего пакета**, а не одного класса.

## 1. Два уровня: живой контроллер и мёртвый PHP-каскад

### 1.1. `DU_ControllerDeleteUserInstance` (`DU_ControllerDeleteUserInstance.class.php`)

Единственный публичный метод — `drop($UIID)` (`:50-106`). Устроен так:

```php
private $deleteCompanents = array(                    // :23-36
    'DU_DeleteEvents', 'DU_DeleteArchiologyTeams', 'DU_DeleteArmys',
    'DU_DeleteBattles', 'DU_DeleteMessages', 'DU_DeleteArtefacts',
    'DU_DeleteAlliance', 'DU_DeleteScience', 'DU_DeleteReligion',
    'DU_DeleteBuildings', 'DU_DeleteCombs', 'DU_DeleteUserInstanceDetails'
);

function drop($UIID) {
    ...
    /*                                                  // :58-67, ЗАКОММЕНТИРОВАНО
    foreach($this->deleteCompanents as $k=>$companentName) {
        $companent = new $companentName($this->common, $this->UIID);
        $companent->Exec();
    }
    /**/

    /*                                                  // :70-93, ЗАКОММЕНТИРОВАНО
    // перевод остатка премиум-валюты (GC/SC) на сборный аккаунт мира 'UC'
    // перед удалением, через MU_ExecTransferInterworld
    ...
    */

    $sql = "SET STATEMENT_TIMEOUT to 0; SELECT drop_uiid(".$this->UIID.")";  // :96, ЖИВОЕ
    $dres = $this->common->getResultArray("", $sql);
    assert(empty($this->common->errormsg));                                  // :100
    return true;
}
```

Единственное реально исполняемое действие — вызов хранимой процедуры БД `drop_uiid(uiid)`. Весь остальной
метод — два больших закомментированных блока:

1. **`foreach` по `deleteCompanents`** (:58-67) — то, что превратило бы этот класс в настоящий каскадный
   PHP-удалятор. Отключено целиком.
2. **Перевод межмировой премиум-валюты** (:70-93) — до удаления инстанса пытался перевести остаток `GC`/`SC`
   игрока на общий сборный аккаунт мира `'UC'` через `MU_ExecTransferInterworld::Exec()`, используя
   `DE_UserInstance`, `DE_User`, `MU_EntityOperationMember`, `MU_SearchOperations::GetAccountData()`. Это
   тоже отключено.

**Важное наблюдение (не установлено как факт, но совпадение почти дословное):** живая реализация ровно
той же идеи — перевода остатка `SC`/`GC` перед удалением на аккаунт мира `'UC'` — существует и работает в
`UC_ExecDeleteInstance.class.php:152-176` (см. §3, путь F), только полнее: там дополнительно проверяется
`$account['IS_ACTIVE']`, и мир-источник берётся динамически (`DE_World::CreateFromID($worldId)`), а не
захардкожен как `'PLS'`. **Предположение**: закомментированный блок в контроллере — это более ранняя или
экспериментальная версия той же логики, впоследствии доведённая до готовности и перенесённая в
`UC_ExecDeleteInstance` (единственный путь, где перевод валюты игроку действительно нужен — при
самостоятельном удалении аккаунта игроком; в остальных вызывающих контроллер путях, №A/B/C/D/E ниже, это
административные/служебные удаления, где перевод валюты игроку не всегда уместен). Прямого подтверждения
в истории/комментариях кода нет.

### 1.2. `drop_uiid()` — реальный каскад, целиком на стороне БД

Реальное каскадное удаление выполняется хранимой PL/pgSQL-процедурой `drop_uiid(uiid)`
(`schema.sql:878-982` в дампе схемы игровой БД, вне `old-sphere`). Она самостоятельно чистит армии,
события, археологию, бои, артефакты, соты/колонии и — через вложенный вызов `drop_from_aliance(uiid)` —
альянсовую часть. Построчный разбор `drop_from_aliance` (включая её расхождение с мёртвым
`DU_DeleteAlliance` — переназначение лидера вместо простого выхода) уже сделан в
`mechanics-alliances-diplomacy.md`, §4.7 и §4.10 — здесь не повторяется. Остальная, неальянсовая часть
`drop_uiid()` построчно в рамках документирования `DU` не разбиралась (см. §6, открытый вопрос 6) —
но по составу таблиц, которые чистит мёртвый PHP-пайплайн (§2), можно судить о **предполагаемом объёме**
того, что делает и DB-функция, раз она задокументированно полнее PHP-версии.

### 1.3. Порядок в мёртвом массиве как ориентир для ремастера

Хотя `deleteCompanents` никогда не исполняется, порядок в массиве (:23-36) — это единственный оставшийся
в кодовой базе явный документ *замысла* каскада, и в общих чертах он логичен (сначала снять активные
события/действия, потом сущности, зависящие от соты/армии, и только в конце — саму соту и запись
инстанса):

1. `DU_DeleteEvents` — снять все связанные с игроком отложенные события (`ds_eventqueue`) и активные
   действия армий, закрыть открытые сделки на бирже.
2. `DU_DeleteArchiologyTeams` — археологические команды на сотах игрока.
3. `DU_DeleteArmys` — армии/юнит-контейнеры игрока.
4. `DU_DeleteBattles` — бои, в которых участвовал игрок.
5. `DU_DeleteMessages` — личные сообщения (отправленные и полученные).
6. `DU_DeleteArtefacts` — артефакты игрока (на сотах, в комплексах, привязанные к альянсу).
7. `DU_DeleteAlliance` — членство в альянсе (и сам альянс, если игрок был последним участником).
8. `DU_DeleteScience` — исследованные науки.
9. `DU_DeleteReligion` — принадлежность к религии.
10. `DU_DeleteBuildings` — здания на сотах игрока.
11. `DU_DeleteCombs` — сами соты: не удаляются, а **сбрасываются** до начального состояния и отвязываются
    от игрока (см. §2, `DU_DeleteCombs`).
12. `DU_DeleteUserInstanceDetails` — служебные записи (действия, флеш-ключи, способности, очередь логина,
    геймхелпер/геймастер, боевой опыт) и в самом конце — строка `ds_userinstance` самого игрока.

Реальный порядок операций внутри `drop_uiid()` не установлен (SQL-тело функции не разбиралось построчно
целиком, см. §6) — не факт, что DB-версия следует той же последовательности; выше описан именно
**PHP-замысел**, зафиксированный только порядком массива.

## 3. Кто на самом деле запускает удаление — пять путей через контроллер и три в обход него

### 3.1. Через `DU_ControllerDeleteUserInstance` (5 найденных вызывающих)

| # | Откуда | Контекст | Транзакция в PHP |
|---|---|---|---|
| A | `ds/vacationMode.php:313` (метод `deleteUserInstance()`) | Внутренний/административный инструмент миграции аккаунтов между мирами (`storeUser`/`restoreUser`/удалить) — не игровой «отпуск», см. `mechanics-moderation-vacation-messaging.md` §2.1 | Нет явной обёртки вокруг `drop()` |
| B | `ds/classes/SI/SI_ControlMainInterface.class.php:387` (тоже `deleteUserInstance()`) | Второй, почти дословно идентичный инструмент того же назначения (межмировое хранение/восстановление аккаунтов, `SI_ExecStoreUser*`/`SI_ExecRestoreUser*`) | Нет явной обёртки |
| C | `ds/classes/SU/SU_DeleteDeadUsers.class.php:81` (создание), `:568` (вызов `drop()`) | Крон `DeleteDeadUsers.php`, автоматическое удаление неактивных аккаунтов (уже описан в `utils-and-maintenance.md`, раздел про `SU_DeleteDeadUsers`) | **Да** — явный `executeQuery("begin")` / `executeQuery("commit")` вокруг каждого `drop($UIID)` (`SU_DeleteDeadUsers.class.php:565-571`) |

| E | Изнутри `DU_ClearWorld::Clear()` (`DU_ClearWorld.class.php:29,38`) | См. §3.2 | **Да** — `startTrans()`/`closeTrans("COMMIT")` вокруг каждого отдельного инстанса в цикле (`:37-39`) |

**О пути D — единственной веб-кнопке:** на той же странице есть второй сценарий,
`scope=complete` («удалить аккаунт целиком, во всех мирах сразу») — но он гарантированно недостижим:
код начинается с `die("Complete delete users is denied!");` (`DeleteUser/index.php:173`), а вызываемый
дальше класс `DropUserComplete` подключается, но его собственный `$drop->drop($name)` тоже закомментирован
(`:187`). То есть в текущем срезе кода админ может удалить только **один инстанс в одном мире** за раз, не
аккаунт целиком по всем мирам/версиям сайта.

### 3.2. `DU_ClearWorld` — очистка мира целиком

`DU_ClearWorld::Clear($dbId, $worldId)` (`DU_ClearWorld.class.php:15-58`) — не удаление одного аккаунта, а
удаление **всех** инстансов конкретного игрового мира разом:

1. `_getWorldInstances()` (`:65-91`) — собирает все `id_userinstance` из `ds_userinstance` для мира.
2. Цикл по каждому инстансу: `startTrans()` → `DU_ControllerDeleteUserInstance->drop($instanceId)` →
   `closeTrans("COMMIT")` (`:33-42`) — то есть **каждый инстанс удаляется в собственной отдельной
   транзакции**, а не вся пачка сразу одной транзакцией.
3. После цикла — `SU_CollectWorlds::collect()`, ограниченный этой базой (`:46-51`), чтобы пересобрать
   сводный кросс-мировой реестр `ds_userinstancecollection` без удалённых записей.

Внутри класса есть ещё два слоя мёртвого кода: `_deleteUsersAllowed()` (`:100-133`) определён, но вызов
закомментирован (`:25`); `_deleteUsers()` (`:93-98`) вообще не вызывается нигде и даже не выполняет
собственный `$sql` (собирает строку и ничего с ней не делает) — судя по всему, недописанная заготовка.

**Три найденных вызывающих `DU_ClearWorld::Clear()`:**
- `ds/utils/ClearWorld.php:53` — ручной скрипт с захардкоженными параметрами `Clear(1, 3)`, правится
  вручную перед каждым запуском (уже описан в `utils-and-maintenance.md`).
- `TN_ControlInterface.class.php:207` и `Admin/controls/GameWorlds/Turnir/ClearWorld/index.php:118` —
  очистка турнирного мира перед повторным использованием под следующий турнир (уже описано в
  `mechanics-tournaments.md`, разделы 4 и 11).

**Исправление ранее зафиксированного предположения:** и `multi-world-architecture.md` (раздел «Открытые
вопросы», пункт 5), и `mechanics-world-transfer.md` (раздел «Открытые вопросы», пункт 1) отмечали, что
класс `DU_ClearWorld` **не был найден** в явном виде в `ds/classes/DU/` в том срезе кода, который
разбирался для тех документов. В срезе, доступном для этой задачи, файл `DU_ClearWorld.class.php`
присутствует и полностью читается (см. выше) — то есть тот открытый вопрос закрыт, класс существует и
не является динамически подгружаемым откуда-то ещё. Вероятно, при более ранних проходах файл просто не
входил в переданный срез репозитория. Сами эти два документа не редактировались в рамках этой задачи —
исправление стоит перенести туда отдельным шагом.

## 4. Транзакционность и что происходит при сбое посередине

Вопрос имеет два независимых уровня — уровень одной DB-функции и уровень PHP-цикла/пакетной обработки.

### 4.1. Уровень одного инстанса — атомарность обеспечивает Postgres, не PHP

Всё содержательное удаление одного инстанса — это **один вызов** `drop_uiid(uiid)` внутри одной SQL-команды
вида `SET STATEMENT_TIMEOUT to N; SELECT drop_uiid(uiid)`. При отправке такой строки через простой
протокол PostgreSQL (`pg_query`/`$common->executeQuery()`) несколько statement'ов в одной строке
автоматически выполняются в рамках одного неявного transaction block — то есть если что-то внутри
`drop_uiid()` (или в её вложенном вызове `drop_from_aliance()`) вызовет ошибку, Postgres откатывает **всю**
команду целиком, а не оставляет часть таблиц вычищенными, а часть — нет. Для путей D, F, H (без явной
PHP-транзакции) это означает: сам по себе единичный вызов всё равно атомарен на уровне БД, PHP-обёртка
вокруг него не добавляет и не убавляет надёжности для одного инстанса.

Оговорка (не проверено построчно, см. §6): если тело `drop_uiid()` само использует `EXCEPTION`-блоки/
подтранзакции (`SAVEPOINT`) для отдельных шагов — часть эффектов теоретически могла бы быть перехвачена
и не откатиться при частичной ошибке. Разобрана построчно только альянсовая часть (`drop_from_aliance`,
см. `mechanics-alliances-diplomacy.md` §4.10) — там `EXCEPTION`-блоков не встречено, но за пределы этого
фрагмента разбор не выходил.

### 4.2. Уровень пакетной обработки — риск на границах между инстансами, не внутри одного

Три места обрабатывают **несколько** инстансов последовательно, каждый — в собственной отдельной
транзакции:

- `DU_ClearWorld::Clear()` — `startTrans()`/`closeTrans("COMMIT")` вокруг каждого инстанса в цикле по
  всему миру (§3.2).
- `SU_DeleteDeadUsers::_deleteInstance()` — `begin`/`commit` вокруг каждого инстанса (§3.1, путь C).
- `SU_DeleteUserList::_deleteUser()` — `startTrans()`/`closeTrans($mode)` с откатом по умолчанию (§3.3,
  путь G) — единственный путь, где ошибка одного инстанса гарантированно не оставляет очередь в
  неопределённом состоянии (запись помечается обработанной только при успехе).

Поскольку транзакция — per-instance, а не одна на весь пакет, аварийный останов PHP-процесса (таймаут,
падение веб-сервера, фатальная ошибка) между обработкой инстанса N и N+1 **не оставляет ни один отдельный
инстанс в наполовину удалённом состоянии** — гранулярность сбоя «целые инстансы», не «половина инстанса».
Правда в том, что произойдёт с пакетом: инстансы `1..N` уже необратимо удалены и закоммичены, `N+1..конец`
не тронуты вообще — то есть *очистка мира* или *ночной прогон удаления мёртвых аккаунтов* могут оказаться
незавершёнными и потребовать повторного запуска. Явного кода возобновления/отметки прогресса (кроме как
для пути G — через флаг в очереди) не найдено ни в `DU_ClearWorld`, ни в `SU_DeleteDeadUsers` — при
повторном запуске оба просто заново выбирают инстансы по тем же критериям (уже удалённые из выборки не
попадут, так как строк `ds_userinstance` для них больше нет), так что "повторный прогон" сам по себе
безопасен и идемпотентен.

### 4.3. `assert()` как фактический механизм остановки — зависит от точки входа

Все PHP-обёртки после каждого SQL-вызова делают `assert(empty($this->common->errormsg))`. По умолчанию в
PHP (без `ASSERT_BAIL`) проваленный `assert()` — не более чем предупреждение, выполнение скрипта
**продолжается**. Останавливает ли фактически провал `assert()` выполнение — зависит от того, установлен
ли в конкретном входном скрипте `assert_options(ASSERT_CALLBACK, 'DS_AssertHandler')`. Обработчик
`DS_AssertHandler` (`ds/include/ErrorHandlers.inc.php:37-80`) логирует ошибку и **завершает процесс
`die()`** (`:79`) — то есть делает `assert()` фактически фатальным для того запроса. Эта настройка
включена явно (построчно) в части входных скриптов — например, `ds/vacationMode.php:11` (путь A) — но
**не найдена** ни в общем бутстрапе (`ds/config/`, `ds/include/`), ни в `Admin/include/`, ни явно
подключённой для пути D (админ-кнопка удаления) или для крон-обёрток `SU_DeleteDeadUsers`/`DU_ClearWorld`.
Итог: поведение при сбое SQL-запроса (тихое продолжение с предупреждением vs немедленный `die()`) **не
единообразно** и зависит от конкретной точки входа — не установлено, какой вариант действует для каждого
из путей A–H без отдельной проверки полной цепочки `require`/бутстрапа каждого скрипта, что выходит за
рамки этой задачи.

## 5. Это веб-триггер, крон или админ-действие?

Ответ — **и то, и другое, по разным путям**, единого «единственно правильного» способа удаления в
кодовой базе нет:

- **Игрок сам, через веб/Flash-клиент** — путь F (`UC_ExecDeleteInstance`), в обход пакета `DU` целиком.
- **Админ, вручную, через веб-панель** — путь D (`Admin/controls/Players/Delete/DeleteUser`,
  `scope=instance`) — единственная найденная кнопка внутри пакета `DU`; массовое удаление по списку
  (§3.3, путь G, `SU_DeleteUserList`) тоже управляется из админки (не разбиралось в рамках этой задачи —
  см. `mechanics-combat.md`/`mechanics-world-transfer.md`).
- **Крон, автоматически, без участия человека** — путь C (`SU_DeleteDeadUsers`, ночной обход всех миров,
  удаляет неактивных/«мёртвых» игроков по модификаторам мира, предварительно рассылая уведомление и
  сверяясь с биллингом, чтобы не удалить платящего пользователя — `SU_DeleteDeadUsers.class.php:534-537`).
- **Служебный ручной скрипт (не по расписанию)** — `DU_ClearWorld` через `ds/utils/ClearWorld.php` с
  захардкоженными параметрами, правится руками перед запуском (§3.2).
- **Побочный эффект другой операции** — межмировой перенос игрока: старый инстанс удаляется путём H
  (`DS_RecieverWorld::DeleteUser`) уже после того, как новый создан в целевом мире; архивация/восстановление
  аккаунтов между мирами — пути A/B (`vacationMode.php`, `SI_ControlMainInterface`).
- **Побочный эффект турнирного цикла** — очистка турнирного мира целиком между турнирами, через
  `DU_ClearWorld` (§3.2, уже описано в `mechanics-tournaments.md`).

## 6. Открытые вопросы

1. **Полное тело `drop_uiid()` не разобрано построчно.** Разобрана только альянсовая часть
   (`drop_from_aliance`, см. `mechanics-alliances-diplomacy.md` §4.10). Не подтверждено, какие именно
   таблицы реально чистит DB-версия и совпадает ли она по составу с мёртвым PHP-замыслом из §1.3 —
   особенно интересен вопрос про соты: делает ли `drop_uiid()` то же самое «сбросить, не удалять»
   поведение, что и мёртвый `DU_DeleteCombs` (§2, файл 11), или полностью освобождает соту иначе.
2. **`DU_DeleteCombs` раскрывает семантику «сброса» соты, а не удаления** — соты не удаляются, а
   возвращаются в пул с базовым набором зданий по шаблону расы (`resetComb()`/`setBeginningBuildings()`,
   `DU_DeleteCombs.class.php:74-290`). Даже будучи мёртвым кодом, это может быть полезным ориентиром для
   ремастера — не установлено, реализует ли `drop_uiid()` аналогичный «мягкий» сброс сот вместо жёсткого
   удаления строк `ds_comb`.
3. **Почему перевод валюты в контроллере закомментирован, а не удалён** (§1.1) — рабочая гипотеза
   («вытеснен» готовой реализацией в `UC_ExecDeleteInstance`) не подтверждена документально, основана
   только на почти дословном сходстве кода.
4. **Единообразие поведения при сбое (`assert`/`die`, §4.3)** не проверено для каждого из путей A–H
   отдельно — требуется трассировка полной цепочки `require`/бутстрапа каждого входного скрипта, что не
   входило в рамки этой задачи.
5. **`DU_ClearWorld` — исправление предыдущего открытого вопроса.** Класс найден и полностью разобран в
   этом документе (§3.2); ранее `multi-world-architecture.md` и `mechanics-world-transfer.md` отмечали
   его как «не найден в явном виде». Сами эти два документа не редактировались — стоит перенести
   исправление туда отдельно.
6. **`DU_AddDeletionToStatistic`** — подтверждён единственный вызывающий (`SU_DeleteDeadUsers`), но не
   исследовано, где и как читается накопленная им статистика (`ds_inoutworldusers`, `ds_worldsstatisic`) —
   вероятно, где-то в разделе статистики/отчётности админ-панели, не разбиравшемся в рамках этой задачи.
7. **Путь D (`Admin/controls/Players/Delete/DeleteUser`) — единственная ли веб-кнопка полностью в рамках
   этой задачи не подтверждено**: исчерпывающий обход всего `Admin/controls/` на предмет других мест,
   создающих `DU_ControllerDeleteUserInstance` или напрямую вызывающих `drop_uiid`, не проводился за
   пределами `grep` по этим двум именам — маловероятно, что что-то пропущено, но не исключено.
