## 1. Что это такое

`LG` расшифровывается как **Log Gate** — это подтверждается напрямую
структурой репозитория: 11 классов `ds/classes/LG/LG_*.class.php`
реализуют логику, а вызываются они исключительно из каталога
`ds/LogGate/` (12 тонких PHP-скриптов, каждый — HTTP-точка входа,
доступная напрямую по URL вида `https://<хост>/ds/LogGate/<script>.php`).
Docблок почти в каждом файле начинается одинаковой фразой: «*Гейт
анализатора*» (например, `LG_CVSRankingExport.class.php:4`,
`LG_ColoniesListExport.class.php:4`, `LG_XMLSpyLogsExport.class.php:4`).

«Анализатор» (в коде везде так, с опечаткой в производных именах —
`Analizator`) — сторонний инструмент, не входящий в этот репозиторий. Сам
код `ds/classes` не говорит прямо, что это за инструмент; единственная
персистентная связь с игрой — отдельная премиум-подписка
`DS_PremiumAnalizer` (см. §8) и дата её окончания, отдаваемая через
`LG_Authorization`. Чек-лист `docs/README.md` называет в качестве
вероятных потребителей сторонние сайты «DSeye-анализатор» и
«DS.Помощник», со ссылкой на `community-glossary-and-tactics.md` — **эта
ссылка не подтвердилась**: в `docs/community-glossary-and-tactics.md`
(словарь сленга и тактики боя, целиком прочитан для этой задачи) ни
«DSeye», ни «Помощник» не встречаются ни разу. Таким образом, названия
конкретных сторонних инструментов, которые могли использовать этот гейт,
в этом репозитории и в цитируемом источнике не подтверждены — см.
«Открытые вопросы».

По назначению 11 классов делятся на три группы:

1. **Авторизация** (1 класс) — проверка, что вызывающий инструмент
   действует от имени реального залогиненного игрока.
2. **Экспорт данных** (7 классов) — отдают статистику/логи/рейтинги в
   CSV-подобном или XML-формате.
3. **Точечные апдейты/выборки без побочных эффектов** (3 класса) — история
   переименования сот/ников, размер кольца. Несмотря на название
   «апдейты» в изначальном описании задачи, ни один из прочитанных классов
   ничего не **пишет** в БД — все 11 классов только читают и отдают
   данные наружу (мутирующих `INSERT`/`UPDATE`/`DELETE` не найдено ни в
   одном из них).

## 2. Формат протокола: не REST/JSON, а «эхо в stdout»

У гейта нет единого протокола ответа, в отличие от, например, `BG`
(биллинговый гейт, `outputAnswer()`/`incoming_info`/`error_status`, см.
`game-engine.md`) или основного игрового протокола (`SU_OutputHandler`,
см. `protocol-client-server.md`). Каждый `LG_*`-класс сам решает формат и
просто делает `echo` в stdout:

- **Псевдо-CSV** (точка с запятой как разделитель, без заголовка
  колонок, без экранирования значений, содержащих `;`) — большинство
  классов: `LG_Authorization`, `LG_CVSRankingExport`,
  `LG_ColoniesListExport`, `LG_CombCoordsChange`, `LG_CombNameChange`,
  `LG_UserNameChange`, `LG_CVSBattleListExport`.
- **Настоящий XML** через устаревшее PHP-расширение `ext/domxml`
  (`domxml_open_mem()`, DOM API в стиле PHP4/раннего PHP5, отличается от
  современного `DOMDocument`) — `LG_XMLBattleExport`,
  `LG_XMLSpyLogsExport`. Оба вручную заменяют `>` на `>\n` перед выводом
  (`echo str_replace(">", ">\n", $res);`) — чисто косметическое
  форматирование для читаемости, не часть протокола.
- **«Настоящий» CSV с кавычками** — только `ranking_new.php` (см. §7.2):
  экранирует кавычки (`str_replace('"','""', ...)`) и оборачивает
  текстовые поля в `"..."`, в отличие от всех остальных экспортов.
- **Голое число** — `LG_RingSize` (`echo $size;`, без разделителей и
  переводов строк).

`Content-Type` нигде в прочитанном коде явно не выставляется — ответ
уходит с тем HTTP-заголовком, который PHP отдаёт по умолчанию (обычно
`text/html`), независимо от того, что внутри на самом деле XML или CSV.
Не проверено, переопределяет ли что-то `Content-Type` на уровне
веб-сервера (Apache-конфиг вне репозитория).

Ошибок в смысле HTTP-кодов или структурированного тела ответа тоже нет:

- `die("GameDown")` / `die('not_valid')` — обычная текстовая строка,
  HTTP-код всё равно 200.
- Отсутствующий обязательный параметр (`$_REQUEST['idw']` и т.п.) или
  проваленная валидация внутри класса (`assert(...)`) — останавливает
  выполнение через общий сайтовый `assert_options(ASSERT_CALLBACK,
  'DS_AssertHandler')` (`ds/Main.php:54`, обработчик —
  `ds/include/ErrorHandlers.inc.php`), тот же механизм, что и везде в
  `ds/classes` — не специфичен для `LG`, подробно не повторяется здесь.

## 3. Аутентификация

### 3.1. `aut.php` / `LG_Authorization` — единственная проверяющая точка

`ds/LogGate/aut.php` — единственный из 12 entry-скриптов, где вообще
происходит хоть какая-то проверка личности. Запрос:

```
GET /ds/LogGate/aut.php?_sid=<SID>
```

(`aut.php:19-22` — единственный обязательный параметр `_sid`.)

`LG_Authorization::Auth($SID)` (`LG_Authorization.class.php:16-55`) делает
следующее:

1. `_checkSession($SID)` (`:63-97`) вызывает
   `SU_GameSessionWork::SessionContinue($SID)`
   (`ds/classes/SU/SU_GameSessionWork.class.php:49`), который **не
   создаёт новую сессию**, а переиспользует существующую: `session_id
   ($sido)` (`SU_GameSessionWork.class.php:88`) подключается к уже
   существующей на сервере PHP-сессии по её ID. Это **тот же самый**
   session id, что использует обычный игровой Flash-клиент (тот же
   механизм `session_name()`/cookie/`$_REQUEST`, описанный в
   [protocol-client-server.md, §2](protocol-client-server.md)) — то есть
   гейт не выдаёт отдельный API-ключ, а требует **живой session id уже
   залогиненного в браузере игрока**. Практический смысл: чтобы
   «залогиниться» в стороннем инструменте-анализаторе, игрок должен
   скопировать туда свой текущий SID из адресной строки/куки игры — то
   есть это классическая для инструментов такого рода схема «вставь свой
   session id», а не отдельная регистрация стороннего разработчика.
   Формат самого SID нигде в LG не проверяется на «свежесть»/владельца
   IP — только что сессия с таким ID существует
   (`SU_SessionDataBase::sessionExist($sido)` и аналоги, вызывается
   внутри `SessionContinue`).
2. Если `$_SESSION['uid']` пусто или `<= 0` — `die('not_valid')`
   (`LG_Authorization.class.php:20`, `:70-80`).
3. При успехе — временно обнуляет `$_SESSION['dbId']`
   (`:23-24`, чтобы `_getUserWorlds()` шёл по «мастер»-БД, где лежит
   список всех миров игрока, а не по БД конкретного игрового мира),
   читает список миров пользователя из `ds_userinstancecollection` (join
   с `ds_worldcollection`, `:113-123`), берёт дату окончания подписки
   «анализатора» через `DS_PremiumAnalizer::getUserPremiumDates()`
   (`:135-146`) и восстанавливает `$_SESSION['dbId']` обратно (`:51`).

**Ответ** (пример реконструкции по коду, значения условные):

```
Vasya;RU,DE,PL;RU;1725312000;
```

Формат (`LG_Authorization.class.php:30,45,49`): `<ник
пользователя>;<world_identifier1>,<world_identifier2>,...;<текущий
world_identifier>;<unix-timestamp окончания подписки анализатора или
"0">;\n`. «Текущий мир» — это тот, в котором была активна игровая сессия
на момент вызова (`self::$world`/`self::$db`, сверяются с
`$_SESSION['world']`/`$_SESSION['dbId']`, `:37,82-94`); если сессия не
привязана ни к какому миру — берётся первый из списка (`:37`, ветка
`empty($curWorld)`).

### 3.2. Все остальные 10 методов не проверяют вообще ничего

Это ключевая находка (развёрнута в §6.1): ни один из оставшихся 10
entry-скриптов (`battle.php`, `battle_logs.php`, `kolonies.php`,
`logs.php`, `move_sots.php`, `ranking.php`, `ranking_new.php`,
`rnm_nick.php`, `rnm_sots.php`, `size_ring.php`, `spy_logs.php`) не
принимает `_sid`/session и не сверяет вызывающего с каким-либо
пользователем. `LG_Authorization::Auth()` возвращает игроку его **ник**
(`user->getName()`), но никакого токена/подписи, которые нужно было бы
передать дальше в `battle.php?nick=...` или `spy_logs.php?nick=...`, не
существует — эти скрипты принимают `nick` как обычный текстовый параметр
без всякой связи с шагом авторизации. То есть шаг 3.1 полезен только для
того, чтобы **свой** инструмент-анализатор узнал ник и список миров
своего пользователя (аналог «получить профиль по токену»), но не
ограничивает, чьи данные можно запросить через остальные 10 методов.

## 5. Разбор по классам

### 5.1. `LG_Base` — общий паттерн резолва мира (`ds/classes/LG/LG_Base.class.php`)

Единственный метод `_getCommon()` (`:20-65`), вызывается первым делом
почти в каждом `Export()`/`Get()`/`GetChangeLog()`:

1. Проверяет `GameDown(0)` — если весь сайт в режиме обслуживания
   (флаг-файлы в `/etc/cron.ds/`, см. `ds/include/GameDown.inc.php:4-10`)
   — `die("GameDown")` (`:22-25`).
2. Резолвит переданный `world_identifier` (буквенный код мира, например
   `RU`/`DE`/`PL`) в `id_world` и `dbname` через таблицу
   `ds_worldcollection` (`:29-40`) — **это то самое место, где строка
   `$world` подставляется в SQL без экранирования**, см. разбор
   SQL-инъекции в §6.2.
3. Находит числовой `$dbId`, под которым эта БД зарегистрирована в
   `$GLOBALS['dbWorldAccess']` (конфиг соответствия версии сайта →
   список БД миров, см. [multi-world-architecture.md](multi-world-architecture.md))
   и повторно проверяет `GameDown($dbId)` уже для конкретной БД мира
   (`:57-60`).
4. Создаёт `DS_Common` с этим `dbId` и складывает в `self::$common`.

### 5.2. Экспорт боя — `battle.php` / `logs.php` → `LG_XMLBattleExport`

Класс называется с префиксом `LG_`, но лежит в `ds/classes/GL/`
(`ds/classes/GL/LG_XMLBattleExport.class.php`) — см. аномалию автозагрузки
в §7.1. Два входа в один и тот же метод `Export($userName, $battleDate,
$world, $battleID = null, $type = 'xml')`:

- `battle.php` — конкретный бой по `idb` (`$battleID`).
- `logs.php` — все бои игрока после `$battleLastDate=last`, лимит
  `ANALIZATOR_BATTLE_LOGS_LIMIT` (глобальная настройка, дефолт **60**,
  `LG_XMLBattleExport.class.php:131-135`).

XML-дерево (реконструкция по коду, `_exportBattleInfo`/`_exportParticipants`/
`_exportBattleRounds`/`_exportStolenResources`, `:172-355`):

```xml
<?xml version="1.0" encoding="utf-8"?>
<userbattles user="Vasya" world="RU">
  <battle id_battle="123" world="RU" oncomb="1.2.3" fromcomb="1.2.4"
          winner="A" startdate="..." enddate="..." endreason="...">
    <battle_log>текстовый лог боя (см. ниже)</battle_log>
    <participant id_battleparticipant="1" user="Vasya" flag="A" winner="1"
                 combowner="0" exp="123" startround="0">
      <army id="1" unitcontainername="..." startround="0" dieafterround="5"/>
    </participant>
    <battleround ...>
      <result id_army="1" unit="..." amount="10" loses="2"/>
    </battleround>
    <stolen>
      <resource name="PRODIUM" amount="1000"/>
    </stolen>
  </battle>
</userbattles>
```

Особенности:

- При `type=txt` вместо разбора по тегам отдаётся сырой текстовый отчёт
  боя (`_sendBattleReport()`, `:194-197`) — тот же текст, что видит игрок
  в игровом интерфейсе, десериализованный из `ds_battlereport.report`
  (`_getBattleReport()`, `:650-702`) с заменой `$`→`+` и `#`→`%`
  (`_getBattleLogHead`, `:733-744` — назначение подмены символов в коде
  не объяснено, предположительно эскейпинг символов, зарезервированных
  протоколом самого анализатора).
- «Скрытие» части армий: если модификатор мира
  `BATTLE_ONE_ROUND_DEATH_LOG` выключен (`_getFullLogModifier()`, общая
  для `LG_XMLBattleExport` и `LG_CVSBattleListExport`, читает
  `ds_gamemodifier`) и армия атакующего погибла целиком за 1 раунд,
  часть данных о вражеских армиях помечается как `disabledArmies` и
  вырезается из `<result>` (`:269-277`, `:321-324`) — это отражение
  игровой механики «скрытый шпионаж»/неполный лог, а не баг доступа.
- Кодировка текстовых полей конвертируется в UTF-8 из `cp1250`/`cp1251`/
  `cp1257` по языку сессии (`$_SESSION['lang']`, `:104-129`) — то есть
  формат ответа зависит от того, какой язык был выставлен в PHP-сессии
  **сервера**, вызвавшего экспорт (а не какого-то параметра запроса).

### 5.3. Сводка боёв в CSV — `battle_logs.php` → `LG_CVSBattleListExport`

`Export($from, $to, $world, $nick, $exlid = array())`
(`LG_CVSBattleListExport.class.php:68-92`). В отличие от XML-экспорта,
отдаёт компактную построчную сводку, а не полный разбор по раундам:
номер боя реально не выводится (используется только `$battle` как есть —
итоговая строка собирается через `implode(';', $battle)`, `:221`, то есть
включает все колонки исходного SQL: `id_battle`, координаты соты боя,
даты начала/конца, число раундов, ники атакующего/защищавшихся,
победитель, плюс два добавленных вручную поля — `loses_diff` (разница
потерь между сторонами, знак зависит от того, кем из участников был
`$nick`) и `defender_rest`/`stolen` (остаток и разграбленные ресурсы в
формате `кадериум|нанокристаллы|продиум|еда|стата`, `:187-209`).
Параметр `exlid` — список ID боёв, которые нужно **исключить** из ответа
(`$_REQUEST['exlid']` в `battle_logs.php:28`, передаётся без разбора
формата — то есть похоже на CSV-строку, которую `LG_CVSBattleListExport`
использует как есть в `NOT IN (...)`, `:237-246`; не проверено, как
именно клиент должен формировать эту строку — вероятно `id1,id2,id3`).

### 5.4. Логи разведки — `spy_logs.php` → `LG_XMLSpyLogsExport`

`Export($userName, $researchDate, $world, $logID = null, $type = 'xml')`
(`LG_XMLSpyLogsExport.class.php:52`). Структурно почти зеркало
`LG_XMLBattleExport`, но для `ds_spy_log`. XML:

```xml
<?xml version="1.0" encoding="utf-8"?>
<userspylogs user="Vasya" world="RU">
  <spy_log id_log="1" log_owner="A" date="..." accuracy="..."
           comb_from="1.2.3" comb_to="1.2.4" user_from="Vasya"
           user_to="Petya" type="..." weight="1234.5">текст лога</spy_log>
</userspylogs>
```

`log_owner` = `A`, если вызывающий (`$uid`, определён по `nick`) —
инициатор разведки, `D` — если он был целью (`_getLogs`, `CASE WHEN
ui.id_user = sl.id_user_from THEN 'A' ELSE 'D'`, `:178-180`), то есть
через этот эндпоинт видны и логи «меня прошпионили» тоже — не только
собственная активная разведка. `weight` вычисляется не из отдельного
структурированного поля, а **парсингом уже готового человекочитаемого
текста лога** (поиск последнего `:` и числа после него,
`LG_XMLSpyLogsExport.class.php:130-137`) — то же самое уже отмечено как
недостаток в [mechanics-combat.md, §12.9](mechanics-combat.md). Лимит
строк — `ANALIZATOR_SPY_LOGS_LIMIT` (`:86`, без дефолтного значения в
коде, см. §6.4).

### 5.5. Рейтинги — `ranking.php` (`LG_CVSRankingExport`) и `ranking_new.php` (без класса)

`LG_CVSRankingExport::Export($world)` (`:17-34`) отдаёт **весь** рейтинг
мира одним ответом, без пагинации: для каждого игрока — порядковый номер,
ник, тег альянса, `id_race`, итоговый рейтинговый балл (`thefinal`),
боевой опыт, статус ворот комплекса (0 не открывались / 1 открываются
впервые / 2 закрыты / 3 открыты), премиум (0/1), обобщённый статус
(0 защита новичка / 1 щит / 2 бан или заморожен / 3 отпуск / 99 ничего
из перечисленного) и `id_league` (`_printRankingIsCSV`, `:190-258`,
расшифровка кодов — из комментария в самом файле, `:196-204`). Из
рейтинга жёстко исключён только один служебный аккаунт `'Support'`
(`:48`) — закомментированный код чуть выше показывает, что раньше список
исключений был куда длиннее (десятки конкретных ников, `:43-46`) и был
сокращён до одного имени, не установлено когда и почему. SQL-запрос
оборачивается в транзакцию с явным `SET STATEMENT_TIMEOUT` (настройка
`ANALIZATOR_CVS_RANKING_TIMEOUT`, дефолт **120000** мс = 2 минуты,
`:23-27`) — единственное во всём `LG` место, где вообще есть что-то
похожее на защиту от слишком тяжёлого запроса, и то это лимит по времени
выполнения одного запроса, а не rate-limiting вызовов.

`ranking_new.php` — не использует ни один `LG_*`-класс: весь SQL и вывод
написаны прямо в entry-скрипте (`ranking_new.php:16-85`). Отдаёт
похожий, но не идентичный набор колонок (дополнительно — раздельные
`artefactranking`/`buildingranking`/`scienceranking`, полное название
альянса, `id_userinstance`, название лиги как текст, уровень, расу как
текст и `id_race`/`id_alliance`) в честном экранированном CSV (двойные
кавычки удваиваются, `:81-82` — единственный экспорт во всём `LG`,
который это делает). См. §7.2 про то, что этот скрипт также не проверяет
`GameDown()` и содержит SQL-инъекцию без даже слабой `ereg`-проверки.

### 5.6. Список сот мира — `kolonies.php` → `LG_ColoniesListExport`

`Export($world)` (`:18-66`). Несмотря на название класса и файла
(«colonies» = колонии), докблок самого класса прямо оговаривает, что
возвращаются **все** соты мира, включая домашние, не только колонии
(`LG_ColoniesListExport.class.php:6`). Строка ответа: `<порядковый
номер>;<ник владельца>;<кольцо>;<комплекс>;<номер соты>;<имя соты>;\n`
(`:57-62`). Как и `ranking.php` — весь мир одним ответом без пагинации;
для активного мира с тысячами игроков это может быть весьма длинный
ответ (не измерялось, не проверялось вживую).

### 5.7. Истории переименований — `move_sots.php`, `rnm_sots.php`, `rnm_nick.php`

Три похожих класса, каждый просто отдаёт построчно `<старое
значение>;<новое значение>;\n` за период `[from, to]`:

- `LG_CombCoordsChange::GetChangeLog($startDate, $endDate, $world)` —
  из `ds_comb_coords_history`, координаты в формате
  `кольцо_комплекс_номер` (`LG_CombCoordsChange.class.php:48-49`).
- `LG_CombNameChange::GetChangeLog($startDate, $endDate, $world)` — из
  `ds_combname_history`, просто старое/новое имя соты.
- `LG_UserNameChange::GetChangeLog($startDate, $endDate)` — из
  `ds_userdata_change_log`, старый/новый логин пользователя. **Без
  параметра мира** — таблица общая на всю БД конкретной версии сайта
  (Classic/Unlimited/Pulsar), не на игровой мир (см. §7.4 про то, что
  класс вообще устроен иначе остальных).

Ни один из трёх не привязан к конкретному игроку — это полная история
переименований **всех** игроков/сот мира (или БД) за период, что вместе
с отсутствием какой-либо аутентификации (§3.2) означает: кто угодно может
вытянуть полную историю смены ников/имён соты для произвольного диапазона
дат.

### 5.8. Размер кольца — `size_ring.php` → `LG_RingSize`

`Get($world, $ring)` (`:23-37`) — просто `echo` количества занятых
комплексов на кольце `$ring` (1–4) мира `$world`
(`_getRingSize()`, `:44-61`). Единственный метод во всём `LG`, где ответ
кешируется (`GLOBAL_CACHE`, ключ `log_gate_ring_size_world<id>_ring<n>`,
`:57`) — то есть единственный случай, где нагрузка от повторных вызовов
реально ограничена (кешем, а не авторизацией/rate-limit).

## 6. Находки безопасности

### 6.1. Отсутствие авторизации на 10 из 11 методов

Развёрнуто в §3.2. `aut.php` — единственная точка, которая хоть что-то
проверяет (существование игровой сессии), но она не выдаёт токен,
привязывающий последующие вызовы к конкретному пользователю. Все
остальные 10 методов принимают `nick`/`idw` как обычные текстовые
GET/POST-параметры и отдают данные **любого** игрока/мира без всякой
проверки, что вызывающий — тот самый пользователь (или вообще
залогиненный пользователь). В частности:

- Полную боевую историю и разбор боя по раундам (`battle.php`/`logs.php`)
  и **логи разведки** (`spy_logs.php`, включая логи "меня прошпионили") —
  можно вытянуть по одному только известному нику, без пароля/сессии.
- Полный список сот мира с владельцами и координатами
  (`kolonies.php`) и полный рейтинг мира (`ranking.php`/`ranking_new.php`)
  — публичны по конструкции (это агрегированные данные всего мира), но
  тоже без какого-либо контроля объёма запросов.

### 6.2. SQL-инъекция через параметр мира (`idw`)

Подтверждено чтением кода, не проверено вживую на работающем сервере —
формулировка ниже описывает то, что видно в исходниках.

`LG_Base::_getCommon()` подставляет `self::$world` прямо в SQL без
экранирования и без приведения типа:

```php
// LG_Base.class.php:29-37
$sql = "
    SELECT dbname, id_world
    FROM ds_worldcollection
    WHERE world_identifier = '".self::$world."'
    ";
```

`DS_Common::getResultArray()` → `getQuery()` не параметризует и не
экранирует запрос — это обычный `pg_query($this->conn, $sql)`
(`ds/classes/DS/DS_Common.class.php:581`), то есть вся защита зависит
исключительно от того, что попадёт в `self::$world` до этой точки.
Единственная проверка перед присвоением — не заякоренный `assert(ereg
("[A-Z]{1,3}", $world))`, повторённый почти дословно в каждом из 9
классов, наследующих `LG_Base` (например `LG_RingSize.class.php:26`,
`LG_CVSRankingExport.class.php:19`, `LG_ColoniesListExport.class.php:47`,
`LG_XMLBattleExport.class.php:100`). Функция `ereg()` без `^...$`
проверяет **не то, что вся строка состоит из 1–3 заглавных латинских
букв**, а лишь то, что где-то внутри строки есть подстрока из 1–3
заглавных букв подряд — этому условию удовлетворяет практически любая
строка, содержащая хотя бы одну заглавную латинскую букву в любом месте
(в том числе строка с кавычками, точкой с запятой, SQL-ключевыми
словами). Таким образом, если это предположение (что `assert()`
действительно останавливает выполнение при провале — см. `ds/Main.php:8-11`,
`ASSERT_BAIL=1`) верно и никакой дополнительной фильтрации `idw` нет
выше по стеку (не проверено — например, на уровне веб-сервера/WAF, вне
репозитория), то параметр `idw` во всех девяти entry-скриптах, которые
его принимают (`battle.php`, `battle_logs.php`, `kolonies.php`,
`logs.php`, `move_sots.php`, `ranking.php`, `rnm_sots.php`, `size_ring.php`,
плюс `spy_logs.php`), выглядит как классическая SQL-инъекция в запрос,
резолвящий мир в `LG_Base::_getCommon()`.

`ranking_new.php` (§7.2) — тот же паттерн, но даже без слабой
`ereg`-проверки: `$world = $_REQUEST['idw']` подставляется в SQL напрямую
(`ranking_new.php:14,16-20`).

Для сравнения: параметр `nick`, где он есть, **проверяется анкорированным
регэкспом** (`VD_UserName::Validate`, `^[a-zA-Z0-9_]+$`,
`ds/classes/VD/VD_UserName.class.php:9-13`) перед использованием в SQL
(`LG_CVSBattleListExport.class.php:103`, `LG_XMLBattleExport.class.php:143`,
`LG_XMLSpyLogsExport.class.php:94`) — то есть автор кода в принципе умеет
писать нормальную валидацию, просто не применил её к параметру мира.

### 6.3. Доступ на уровне веб-сервера — есть, но выглядит нефункциональным

В корне `old-sphere/` есть `.htaccess` (9 строк, не относится специально
к `ds/LogGate/` — отдельного `.htaccess` внутри `ds/LogGate/` не найдено):

```
allow from 212.32.62.216
allow from 104.28.166.181
#deny from all
#deny from 188.162.144.0/20
#deny from 188.134.42
#deny from 88.215.168.2 
#deny from 178.252.101.12
#deny from 195.5.41.202
#deny from 176.8.75.5
```

Все строки `deny from ...` закомментированы, а директивы `Order` нет
вообще. В классическом `mod_access` Apache 2.2 (для `mod_authz_host`
Apache 2.4 поведение отличается, версия веб-сервера не установлена) при
отсутствии `Order` действует поведение по умолчанию, эквивалентное
`Order deny,allow` — то есть базовое состояние «доступ разрешён», `deny`
обрабатывается первым (здесь их нет — ничего не блокируется), `allow`
вторым (здесь это два конкретных IP, но они и так уже разрешены базовым
состоянием). **Похоже, что этот файл в текущем виде не ограничивает
доступ практически ни для кого** — вероятно, реликт какой-то прошлой
блокировки (возможно, той самой активности вокруг найденного фишинг-кита,
см. `docs/README.md`/`portal-cms.md`, §3.4 — не подтверждено, просто по
времени и характеру совпадает с «список подозрительных IP»). В любом
случае это общесайтовый файл, не специфичный для `LG`/`LogGate`.

### 6.4. Отсутствие rate-limiting

Ни в одном из 11 классов и 12 entry-скриптов нет счётчиков запросов,
throttling или IP-based ограничений в PHP-коде. Единственные механизмы,
хоть как-то ограничивающие нагрузку:

- `SET STATEMENT_TIMEOUT` в `LG_CVSRankingExport` (настройка
  `ANALIZATOR_CVS_RANKING_TIMEOUT`, дефолт 120000 мс, §5.5) — обрывает
  один конкретный тяжёлый запрос, не ограничивает частоту вызовов.
- `LIMIT` на число возвращаемых боёв/логов разведки
  (`ANALIZATOR_BATTLE_LOGS_LIMIT`, дефолт **60**,
  `LG_XMLBattleExport.class.php:131-135`; `ANALIZATOR_SPY_LOGS_LIMIT`,
  **без дефолта в коде** — `LG_XMLSpyLogsExport.class.php:86`:
  `self::$logLimit = (int)DE_GlobalSettings::Get('ANALIZATOR_SPY_LOGS_LIMIT', true);`
  без `if(!self::$logLimit) {...}`, в отличие от battle-лимита. Если
  строки `ANALIZATOR_SPY_LOGS_LIMIT` нет в таблице `ds_globalsettings`
  конкретной инсталляции, `DE_GlobalSettings::Get(..., true)` возвращает
  `false` (`ds/classes/DE/DE_GlobalSettings.class.php:45-48`), `(int)false
  = 0`, и итоговый SQL получает `LIMIT 0` (`LG_XMLSpyLogsExport.class.php:207`)
  — экспорт логов разведки в этом случае всегда возвращал бы пустой XML.
  Не проверено по живой БД (дамп `ds_globalsettings` не в репозитории),
  указано как открытый вопрос/потенциальный дефект, а не факт.
- Кеш на 1 метод (`LG_RingSize`, §5.8).

`ranking.php`/`ranking_new.php`/`kolonies.php` отдают весь мир целиком без
`LIMIT`/пагинации вообще.

### 6.5. Секреты

Хардкоженных паролей БД, API-ключей или подобного в 11 файлах
`ds/classes/LG/` и 12 файлах `ds/LogGate/` **не найдено** — весь доступ к
БД идёт через общий `DS_Common`/`settings.php` (см.
[multi-world-architecture.md](multi-world-architecture.md)), собственных
креденшлов для «анализатора» гейт не хранит. Ничего добавлять в
`REDACTED_CREDENTIALS.txt` по итогам этой подсистемы не потребовалось.

## 7. Несостыковки и странности кода

### 7.1. `LG_XMLBattleExport` физически лежит в `GL/`, а не в `LG/`

Уже отмечено в [game-engine.md](game-engine.md) при разборе `GL`.
Автозагрузчик `import()` (`ds/include/Import.inc.php`) резолвит
`PREFIX_ClassName` в `ds/classes/PREFIX/PREFIX_ClassName.class.php` — для
`LG_XMLBattleExport` это означало бы `ds/classes/LG/LG_XMLBattleExport.class.php`,
но реальный файл лежит в `ds/classes/GL/LG_XMLBattleExport.class.php`. Ни
`battle.php`, ни `logs.php` не делают явный `require`/`include` этого
файла — оба полагаются на автозагрузку (никаких `require_once` класса в
`battle.php`/`logs.php`, только `require_once '../Main.php'`, который
подключает `Import.inc.php`, но не сам класс). Если это единственный
механизм подгрузки классов на проде — `battle.php` и `logs.php`
сломаны (класс не будет найден). Не проверено, есть ли где-то ещё в
конфигурации PHP (`auto_prepend_file` или подобное) альтернативный путь
подгрузки, который мог бы это компенсировать.

### 7.2. `ranking_new.php` выпадает из общего паттерна

Единственный entry-скрипт, который: (а) не вызывает никакой `LG_*`-класс,
весь код — прямо в файле; (б) не проверяет `GameDown()` — блока
`require_once(...'/GameDown.inc.php'); if(GameDown()){die(...);}`,
присутствующего во всех остальных 11 скриптах, здесь нет
(`ranking_new.php:1-12`, сравнить с любым другим entry-скриптом в
таблице §4); (в) не использует слабую `ereg`-проверку `$world` вообще
(§6.2) — даже видимость валидации отсутствует; (г) единственный, кто
корректно экранирует CSV-поля (`str_replace('"','""', ...)`,
`:81-82`). Судя по всему (по названию и более широкому набору колонок,
включая `id_alliance`/`id_race`/полное имя расы) — более новая
альтернатива `ranking.php`, добавленная позже и не приведённая к общему
паттерну `LG_Base`/entry-скриптов. Не установлено, использует ли
«анализатор» сейчас `ranking.php`, `ranking_new.php` или оба.

### 7.3. `LG_UserNameChange` не наследует `LG_Base`

Единственный из 11 классов, у которого нет `extends LG_Base`
(`LG_UserNameChange.class.php:8`) — вместо `self::_getCommon()` создаёт
`DS_Common` инлайн (`$common = DS_Common::CreateForCurentDB(0);`, `:58`) —
через метод с именем `CreateForCur**ent**DB` (без второго `r`), а не
`CreateForCur**rent**DB`, которым пользуется `LG_Base::_getCommon()`
(`LG_Base.class.php:27`) и `LG_Authorization::_getUserWorlds()`
(`LG_Authorization.class.php:111`, тоже «укороченный» вариант). Это не
опечатка, ломающая код — `DS_Common` реально объявляет оба метода как
отдельные (`DS_Common.class.php:98` и `:133`), похоже, исторический
дубль, закрепившийся как отдельный метод вместо того, чтобы быть
исправленным, а не единственно верное имя. Сам факт, что
`LG_UserNameChange` идёт в обход общего `LG_Base`-паттерна, делает его
единственным классом без параметра `$world`/`idw` вообще (см. §5.7).

### 7.4. `assert(ereg(...))` — вызов удалённой в PHP 7 функции

`ereg()` объявлена устаревшей в PHP 5.3 и **полностью удалена** в PHP 7.0.
Она используется в проверках `$world` в 9 из 11 классов (везде, где есть
наследование от `LG_Base` через параметр мира). Если эти скрипты
запускались (или запускаются сейчас) под PHP 7+, каждый такой `assert()`
должен был бы завершаться фатальной ошибкой `Call to undefined function
ereg()` ещё до какой-либо валидации — то есть либо весь этот срез `LG` на
самом деле работал только под PHP 5.x (что согласуется с явными
`version_compare(PHP_VERSION,'5','>=')`-проверками в некоторых
entry-скриптах для `domXML`, см. `battle.php:19-22`), либо эти эндпоинты
сейчас на проде уже нерабочие. Версия PHP, под которой реально
эксплуатировался/эксплуатируется этот гейт, в репозитории не установлена.

## 8. Связь с премиум-подпиской «анализатора»

Отдельная подписка `DS_PremiumAnalizer` (таблица
`ds_analizer_premium_change`, покупается вместе с обычным премиумом или
отдельно на фиксированные 30 дней) подробно разобрана в
[mechanics-premium-gameplay-effects.md, §4](mechanics-premium-gameplay-effects.md).
В игровом коде (`ds/classes`) не найдено ни одной проверки «включён ли
анализатор» — `DS_PremiumAnalizer::checkIfUserProfi()` нигде не
вызывается. **Единственное найденное реальное использование** этих
данных — как раз здесь: `LG_Authorization::_getPremEndDate()`
(`LG_Authorization.class.php:135-146`) включает дату окончания подписки в
ответ `aut.php`. То есть сервер только сообщает вызывающему инструменту
дату окончания — решение, что делать с этой информацией (например,
включать ли платные функции самого стороннего инструмента), полностью на
стороне внешнего клиента, вне этого репозитория.

## Открытые вопросы

1. **Кто конкретно использует этот гейт.** `docs/README.md` называет
   «DSeye-анализатор» и «DS.Помощник» со ссылкой на
   `community-glossary-and-tactics.md` — при прямой проверке этого файла
   в рамках данной задачи ни одно из двух названий там не встречается ни
   разу. Настоящее имя/имена стороннего инструмента (или нескольких),
   реально дёргавших `ds/LogGate/`, в этом репозитории не подтверждены.
2. **Используется ли гейт сейчас.** Живые ли сейчас
   `destinysphere.ru`/`ds-game.ru` отвечают на `ds/LogGate/*.php` — не
   проверялось (см. `docs/external-sites.md` про состояние живых сайтов
   в целом, но не про этот конкретный путь).
3. **Работоспособность под текущей версией PHP.** См. §7.4 — если сайт
   давно перешёл на PHP 7+, весь `LG` (кроме, возможно,
   `ranking_new.php`, который не использует `ereg`) может быть мёртвым
   кодом уже сейчас.
4. **`LG_XMLBattleExport` и автозагрузка** (§7.1) — не проверено, ловится
   ли класс из `GL/` каким-то альтернативным механизмом подключения,
   или `battle.php`/`logs.php` фактически неработоспособны.
5. **`ANALIZATOR_SPY_LOGS_LIMIT` без дефолта** (§6.4) — не проверено по
   дампу `ds_globalsettings`, задано ли это значение в реальной БД; если
   нет, `spy_logs.php` всегда возвращал бы пустой ответ.
6. **Официальная документация для сторонних разработчиков.** В
   `Admin/` не найдено ни переключателя вкл/выкл `LogGate`, ни страницы
   с документацией по API для внешних инструментов — вероятно, доступ
   и правила использования согласовывались с конкретными авторами
   инструментов вне какой-либо системы, отражённой в этом репозитории.
7. **Реальная строгость ограничения доступа на уровне сети.** Корневой
   `.htaccess` (§6.3) выглядит нефункциональным в текущем виде — не
   исключено, что на живом хостинге доступ к `ds/LogGate/` в
   действительности ограничивался на уровне, не отражённом в этом
   репозитории (firewall, конфигурация vhost вне `old-sphere/`).
