# Игровые эффекты премиум-статуса

Этот документ — обратная сторона [`billing-and-monetization.md`](billing-and-monetization.md).
Тот документ разбирает премиум со стороны **платежей** (как купить, биллинг,
SMS, `billing.destinysphere.ru`). Здесь разбирается только то, что премиум-статус
**меняет в геймплее** конкретного игрока: бонусы, лимиты, доступ к функциям,
защита — без повторения платёжной механики.

Все пути ниже — относительно `D:\Projects\Destiny Sphere\old-sphere`, если не
указано иное.

## 0. Термины

В коде премиум-статус называется по-разному в разных слоях:

- **`profi`** — колонка в таблице `ds_userprofidata` и общее название статуса
  в БД/логах (`changeUserStatusToProfi`, `checkIfUserProfi`).
- **`isProfy()`** — метод `DE_User`, единая точка входа для игровой логики
  (см. §1).
- **`$_SESSION['profi_game']`** — кэш этого же флага в сессии, выставляется
  один раз при логине (`GE_Login.class.php`) и используется в большинстве
  игровых проверок вместо повторных запросов к БД.
- **«Непрофи»** — разговорный термин из кода/документации для аккаунта без
  премиума (используется, например, в `game-engine.md` при описании защиты
  от подмены премиум-статуса, см. §4.3).
- **«Премиум-бан»** — не наказание, а отдельная **платная** услуга
  (self-service защита/неучастие в PvP), в комментариях кода прямо названная
  «ВИП-сауна» (`DS_User.class.php:355`: `Информация о премиум-бане (ВИП сауне)`).
  Рассмотрена отдельно в §5, т.к. это не тот же «премиум», что в остальном
  документе.
- **«Анализатор» / `PremiumAnalizer`** — вторая, полностью независимая
  премиум-подписка (своя таблица, свои даты, отдельно покупается или
  докупается к основному премиуму). Рассмотрена в §6.

## 1. Как технически определяется премиум-статус

### 1.1. Хранение

Таблица `ds_userprofidata` (одна строка на игрока):

| Колонка | Смысл |
|---|---|
| `id_user` | игрок |
| `profi` (bool) | «премиум включён» (администативно/по истории — не единственный критерий, см. ниже) |
| `trial` (bool) | это временный/пробный премиум, а не купленный |
| `active` (bool) | запись активна |
| `creationdate`, `startdate`, `enddate` | даты создания записи, начала и окончания текущего периода премиума |

Источник: `ds/classes/DS/DS_Premium.class.php`.

### 1.2. Проверка статуса

`DS_User::IsPremium($userID)` (`ds/classes/DS/DS_User.class.php:59-83`) — TRUE, если
`active=true AND enddate > now() AND trial=false`.

`DS_User::IsTrialPremium($userID)` (там же, `:86-110`) — то же самое, но `trial=true`.

`DE_User::isProfy()` (`ds/classes/DE/DE_User.class.php:438-444`) — **главная
точка входа для игровой логики**:

```php
$this->isProfy = (DS_User::IsPremium($this->getID()) || DS_User::IsTrialPremium($this->getID()));
```

То есть **и купленный, и «пробный» премиум дают игроку абсолютно одинаковые
игровые бонусы** — разница между ними видна только в одном месте (лимит
обращений в саппорт, см. §4.2).

`$_SESSION['profi_game']` выставляется один раз при логине
(`ds/classes/GE/GE_Login.class.php:268-277`):

```php
if(DS_User::IsPremium($user->getID())) {
    $_SESSION['profi_game'] = 1;
} else {
    if(GL_HaveTrialPremium::GetMode($user)) {
        $_SESSION['profi_game'] = 1;
        $_SESSION['after_reg_trial'] = 1;
    }
}
```

Большинство игровых проверок (лимит колоний, здания, действия армии, вкладки
интерфейса) читают именно `$_SESSION['profi_game']`, а не вызывают `isProfy()`
заново — то есть статус кэшируется на сессию логина, не проверяется on-the-fly
на каждое действие.

### 1.3. Что происходит при истечении

`PU_ExecChangePremiumDays::Exec()` (`ds/classes/PU/PU_ExecChangePremiumDays.class.php`)
— единая точка изменения количества премиум-дней (вызывается из биллинга, SMS,
админки, кабинета игрока и подарков). При каждом вызове:

1. `checkIfPremiumAccountEnded()` (там же, `:110-124`) — если `enddate` уже в
   прошлом (или записи ещё нет), считает, что премиум **закончился**;
2. если закончился — `DS_Premium::setStartEndDateToNow()` сбрасывает
   `startdate`/`enddate` на «сейчас» (результат операции — `ACCOUNT_ENDED`),
   и только после этого прибавляет новые `$daysDelta` дней;
3. если не заканчивался — новые дни просто прибавляются к текущему `enddate`
   (`ACCOUNT_PROLONGED`), т.е. **покупки премиума складываются**, а не
   перезаписываются.

Специальной «деградации» аккаунта при истечении премиума в этом коде нет —
разница в поведении полностью сводится к тому, что `isProfy()`/`profi_game`
становятся `false`, и все проверки в §3-4 идут по non-premium ветке. Никакого
удаления построек/юнитов при истечении премиума не найдено.

### 1.4. Несколько параллельных источников «бесплатного» премиума для новых игроков

В коде найдено **несколько независимых** механизмов, дающих новому игроку
премиум без оплаты. Они пересекаются и, по всей видимости, слоями наросли
друг на друга за историю проекта (см. «Открытые вопросы», п.1):

|---|---|---|---|

### Живой пример: конкретные проценты бонуса производства (данные сайта, не кода)

### 2.1. Ограничения/эффекты для «непрофи»

Строго говоря, все пункты таблицы выше одновременно являются и «бонусами
премиума», и «ограничениями непрофи» (два описания одного и того же условия).
Отдельно стоит выделить два места, где логика асимметрична сама по себе, а не
просто «получает бонус / не получает бонус»:

1. **Полная блокировка действия** (не просто урезание) — переброска армии
   между своими сотами (`UA_MoveArmyToComb`, см. таблицу) недоступна непрофи
   вообще, а не медленнее/дороже.
2. **Защита от «фейкового премиума»** (упомянута в `game-engine.md` как
   «подозрительно для непрофи-аккаунтов») — блок в
   `ds/classes/UserAction.class.php:180-215` (`/**** BEGIN ЗАЩИТА ОТ
   ФЕЙКОВОГО ПРЕМИУМА ****/`). Логика: для непрофи-сессий
   (`!$_SESSION['profi_game']`) отслеживается флаг
   `$_SESSION['PEREMIUM_CHEATER_ALLERT']` по списку «чувствительных» тегов
   действий (`archeologyteam`, `attachartefact`, `detachartefact`, `sell`,
   `buy`, `transferresource`, `defend`, `canceldefend`, `cancelattack`,
   `createarmy`). Если такой тег приходит **два раза подряд без
   промежуточного** `getbuildmenu` — раньше это логировалось и должно было
   давать ошибку `FAKE_PREMIUM` (комментарий `ds_error(...)`), но **сейчас
   строки логирования и выдачи ошибки закомментированы** — функция вызывает
   `return true` и ничего не делает, то есть **проверка фактически отключена
   / не имеет видимого эффекта** в этом срезе кода. Смысл изначальной задумки:
   ловить клиентов/ботов, которые эмулируют быстрые действия премиум-клиента,
   пропуская обычную навигацию по меню, которую делает настоящий
   Flash-клиент.

## 3. «Премиум-бан» — платная услуга неучастия в PvP (не путать с основным премиумом)

Это **отдельная платная услуга** в личном кабинете (`UC_ExecByPremiumBan`,
`ds/classes/UC/UC_ExecByPremiumBan.class.php`), не связанная с флагом
`profi`/`isProfy()`. В коде она называется «премиум-бан», а в комментарии к
`DS_User::GetPremiumBan()` — «ВИП-сауна». По сути это самостоятельно покупаемая
неприкосновенность/тайм-аут, действующая в обе стороны:

- Хранится в отдельной таблице `ds_user_premium_ban` (`start_date`,
  `end_date`, `comments`, `allow_trade`) — не путать с `ds_userprofidata`.
- Два тарифа: `PS_BY_PREMIUM_BAN` (**1–14 дней**, `min=1/max=14` —
  значения по умолчанию в классе) и `PS_BY_PREMIUM_BAN_30` (**15–30 дней**,
  `UC_ExecByPremiumBan.class.php:21-24`). Игрок сам указывает число дней в
  пределах диапазона.
- Начинается через **12 часов** после покупки, длится `count_of_days + 12
  часов` (`_AddPremiumBan()`, `:141-142`, `strtotime("+12 hours")` /
  `strtotime("+N days 12 hours")`).
- Пока активен:
  - владелец **не может атаковать** (`ARMY_ACTION_BAN`,
    `GL_CanAttackComb.class.php:527-534`, `GL_CanAttackComb2.class.php:436-443`);
  - на владельца **нельзя напасть** (`DENIED_ATTACK_BANNED_USER_MESS`,
    те же файлы, `:550-555` / `:459-464`);
  - владелец **не может защищаться и не может быть атакован при защите**
    (`ARMY_ACTION_PREMIUM_BAN` / `DENIED_DEFEND_BANNED_USER`,
    `ds/classes/GL/GL_CanDefendComb.class.php:144-154`);
  - **торговля на бирже заблокирована** (покупка/продажа), если явно не
    выставлен `allow_trade='t'` (по умолчанию `'f'` при самостоятельной
    покупке) — `CANT_SELL_WITH_TRADE_BAN` /
    `CANT_BUY_WITH_TRADE_BAN`
    (`GL_TradeCanSellByThisPriceAndScope.class.php:328-334`,
    `GL_TradeCanByThisLotByThisPrice.class.php:271-277`).
- Повторная покупка ограничена по времени после окончания предыдущего бана,
  но в коде это сделано **противоречиво**: комментарий говорит про «3 месяца»
  (`_ShowIndex()`, `:79`: «смотрим, прошло ли 3 месяца»), однако фактическая
  проверка блокировки — `$userBan->getStartDate()->value > strtotime("-45
  day")` (**45 дней**, не 3 месяца), при этом отображаемый игроку
  «остаток до следующего заказа» считается от `strtotime("-3 month")`.
  Несовпадение комментария/показываемого текста и реальной проверки — см.
  «Открытые вопросы».
- Интерфейс отображает предстоящий/идущий премиум-бан в списке сот
  (`combData['cban']`, `combData['godpro']` — время до активации, в мс),
  `ds/classes/UA/UA_ComplexView.class.php:391-399`.

## 4. «Анализатор» (`PU_ExecChangeAnalizerPremium` / `DS_PremiumAnalizer`)

Отдельная от основного премиума подписка, задание явно просило её разобрать.

- Собственная таблица `ds_analizer_premium` (`id_user`, `active`,
  `creation_date`, `start_date`, `end_date`) и лог
  `ds_analizer_premium_change` — структурно калька с `DS_Premium`, но **без
  колонки `trial`**: у «анализатора» нет пробного режима, только
  включён/выключен + дата окончания.
- `PU_ExecChangeAnalizerPremium::Exec()`
  (`ds/classes/PU/PU_ExecChangeAnalizerPremium.class.php`) — точный аналог
  `PU_ExecChangePremiumDays::Exec()` (тот же алгоритм: регистрация → продление
  → лог), но пишет в `DS_PremiumAnalizer`, а не в `DS_Premium`.
- Покупается двумя способами:
  - **вместе** с основным премиумом, как опция «плюс анализатор»
    (`DE_MoneyActionType::CreateFromName('PS_BUY_PREMIUM_PLUS_ANALIZATOR_'.$countOfDay)`,
    `ds/classes/UC/UC_ExecByPremium.class.php:76-97, 188-193`);
  - **отдельно**, фиксированно на **30 дней**
    (`PU_ExecChangeAnalizerPremium::Exec(self::$user, 30, 'CABINET', ...)`,
    `ds/classes/UC/UC_ExecByAnalizator.class.php:56`).
  - Также есть биллинговый шлюз `BG_PremiumAnalizer` /
    `BG_PremiumAndAnaliz` (`ds/classes/BG/*.class.php`) — начисление и
    основного премиума, и анализатора одним вызовом от
    `billing.destinysphere.ru`.
- **Что конкретно даёт «анализатор» в геймплее — в коде `ds/classes` не
  найдено.** Метод `DS_PremiumAnalizer::checkIfUserProfi()` (эквивалент
  `DS_Premium::checkIfUserProfi()`) нигде не вызывается — то есть в этом
  срезе кода нет ни одной игровой проверки «включён ли анализатор». Единственное
  реальное использование данных анализатора — `LG_Authorization.class.php`
  (`:44-49, 132-143`, метод `_getPremEndDate()`, с докблоком «Получение даты
  окончания премиума в анализаторе»): дата окончания анализатора включается в
  ответ отдельного протокола авторизации (`$str .= ";".$premEndDate.";\n"`).
  Это похоже на логин внешнего клиента/инструмента («анализатора»), не
  входящего в этот репозиторий — сервер только сообщает дату окончания
  подписки, а решение «пускать или нет» принимает внешний клиент. **Это
  предположение**, реальная функциональность «анализатора» не может быть
  восстановлена только из `old-sphere` без внешнего инструмента/клиента.

## 5. Открытые вопросы

1. **Пересечение механизмов «бесплатного премиума для новичка»** (§1.4):
   180-дневный сессионный триал (`GL_HaveTrialPremium`) и 365-дневная прямая
   запись в `ds_userprofidata` при создании инстанса
   (`GE_ExecStartCreateInstance`) выглядят как два независимых слоя одной и
   той же идеи, наросшие в разное время. Поскольку `GE_ExecStartCreateInstance`
   пишет `profi=true` напрямую в БД (не через `PU_ExecChangePremiumDays`) и не
   указывает колонку `trial` явно, не установлено:
   - действует ли эта запись как «настоящий» (`trial=false`) премиум или как
     «пробный» — зависит от DB-дефолта колонки `trial`, DDL которой нет в
     этом репозитории;
   - если это настоящий премиум — получается, что **почти каждый новый
     игрок автоматически получает 365 дней полного премиума** при первом/
     втором входе в мир, что стоит явно перепроверить перед переносом баланса
     в ремастер (это принципиально влияет на всю экономику).
2. **Знак `TRADE_PREMIUM_TAX_DELTA`** не виден в коде (это runtime-настройка
   мира в БД, а не константа) — предположение (см. `mechanics-economy-trade.md`
   и таблицу в §2), что дельта отрицательная (премиум платит **меньше**
   налога), сделано только по косвенному признаку (обрезание налога снизу
   нулём). Нужна выгрузка реальных значений `ds_worldsettings`, чтобы
   подтвердить.
3. **Конкретные проценты бонуса производства** (`BONUS_PREMIUM_*`/
   `BONUS_NON_PREMIUM_*`) и дельта лимита колоний
   (`MAX_COLONIES_PREMIUM_DELTA`) — это world-settings в БД
   (`ds_worldsettings`), не константы в PHP. Ни SQL-дампов, ни конфигов с
   актуальными числами в `old-sphere` не найдено. Без доступа к живой БД
   конкретные числа для баланса ремастера взять неоткуда — это либо
   принимается заново с нуля, либо нужно запросить выгрузку `ds_worldsettings`
   отдельно. **Частично закрыто** для `BONUS_PREMIUM_*`: живые значения по
   всем текущим мирам найдены на официальных справочных страницах сайта (не
   в коде — см. новый раздел «Живой пример» в §2 выше, диапазон 5–20%).
   `BONUS_NON_PREMIUM_*` сайт не публикует — по нему открытый вопрос остаётся
   в полном объёме.

   > ⚠️ **`MAX_COLONIES_PREMIUM_DELTA` — новая находка, требует внимания
   > владельца проекта (источник: БД, live-запрос, 2026-09-02).** Прямой
   > запрос к каталогу всех модификаторов игры (`ds_gamemodifiertemplate`)
   > показывает, что для ключа `MAX_COLONIES_PREMIUM_DELTA` оба текстовых
   > поля `description`/`descforuser` буквально равны `Not used`, значение
   > по умолчанию — `0`. Это не просто «данные недоступны» (как
   > формулировалось раньше в этом пункте) — это прямой сигнал от самой БД,
   > что поле не задействовано на практике, при этом PHP-код его всё же
   > читает (`UA_Colonize.class.php:212-219`, см. `mechanics-races-world-ranking.md`
   > §2.1/§5.3, где эта же находка задокументирована подробнее). То есть
   > премиум-бонус к лимиту колоний, вероятно, никогда не был включён ни на
   > одном мире (либо везде стоит `0`, что эквивалентно отсутствию бонуса) —
   > стоит уточнить у владельца проекта, а не молча закладывать этот бонус в
   > баланс ремастера как рабочую механику.
4. **Что именно разблокирует «Анализатор»** (§4) — не установлено; вероятно,
   это внешний клиент/инструмент вне этого репозитория. Стоит уточнить у
   тех, кто застал живую игру, что это был за функционал (по имени похоже на
   анализ боя/торговли/статистики).
5. **Несостыковка «3 месяца» / 45 дней** в кулдауне повторной покупки
   премиум-бана (§3) — комментарий в коде и реально исполняемая проверка не
   совпадают (`strtotime("-45 day")` в условии блокировки vs `strtotime("-3
   month")` в отображаемом отсчёте). Похоже на баг/недоделанный рефакторинг в
   оригинале; при переносе в ремастер нужно явно решить, какое поведение
   было «настоящим» на проде (без доступа к БД/логам не проверить, какая
   ветка реально отрабатывала).
6. **Действие 180-дневного `GL_HaveTrialPremium`** относительно
   `WORLDS_WITH_PREMIUM` — единственный настроенный интервал промо-премиума
   на мир (`settings_secondary.php:117-121`) относится к 2008 году и давно
   истёк; сам механизм (глобальный промо-период «премиум для всех на этом
   мире») мог использоваться и позже с другими датами, но актуальной
   конфигурации в этом срезе кода нет.
7. **Клиентский эффект флага `mode`** в `UA_Refresh`/`Refresh2`/`Refresh3`
   (§2, предпоследняя строка таблицы) не может быть подтверждён без
   Flash-клиента — в PHP виден только факт передачи 0/1, но не то, что клиент
   с этим значением делает (реклама, интервал опроса, что-то ещё).
