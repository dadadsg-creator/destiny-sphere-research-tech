# Часть 1. NPC (боты)

## TL;DR

NPC в «Сфере Судьбы» — это не отдельная лёгкая сущность-«монстр», а **полноценный игровой аккаунт** (`ds_user.npc = true`), с обычным `ds_userinstance`, обычной сотой (`ds_comb`), обычной домашней армией и обычным участием в бою — движок боя не различает NPC и живого игрока на уровне `DE_Battle`/`EH_BattleRound`. NPC-аккаунты создаются заранее пачкой служебным классом `SU_PopulateNPC` (шаблонная сота одной из 3 «сложностей» на расу) и рассаживаются по кольцу равномерно алгоритмом `GL_GetCombForNPC`. Дальше их «оживляет» периодический скрипт `utils/NPC_Update.php → SU_NPC`, который, судя по всему, запускается по расписанию (крон, конфигурация которого не входит в репозиторий): доращивает армию NPC до случайного значения в диапазоне `[min_army, max_army]` для его «лиги+типа» (`ds_npc_army_settings`), инициирует атаки на живых игроков по одному из 4 алгоритмов выбора цели, и после каждого боя с участием NPC (`ME_LogNPCBattle`) с некоторой вероятностью планирует ответную атаку/повторный визит. Игрок, победивший NPC, получает обычный грабёж ресурсов (как в PvP) **плюс** специальную «награду новичка» (`ME_EndBattle::_RewardNewb`) по ставке из отдельной группы настроек мира `REWARD_NEWB_FOR_NPC_<разница_лиг>`, если победитель — не NPC. Соту NPC нельзя взять под защиту другим игроком (`GL_CanDefendComb`, код ошибки `DEFEND_NPC_COMB`). Никакой связи между NPC и археологическими экспедициями (`DS_Archeology`/`EH_ArcheologyTeam`) в коде не найдено — это полностью независимые подсистемы (см. §1.9).

## 1.3 Заселение: создание и расстановка NPC-аккаунтов

### 1.3.1 `SU_PopulateNPC::CreateUsers($level, $count, $raceID)` (`SU_PopulateNPC.class.php:59-82`)

Массово создаёт `$count` «болванок» NPC-аккаунтов заданного уровня сложности (`1..3`) и расы (`1..4`, где, по аналогии с остальным кодом, `4`, вероятно, означает «межрасовый»/квестовый — не подтверждено прямым использованием здесь). Для каждого:
1. Генерирует уникальный логин через `GL_GenerateNPCCombName::generate($raceID)` (до 20 попыток на уникальность, `:69-75`).
2. `_createNPCUser` (`:201-235`) в одной транзакции: вставляет строку `ds_user` (пароль — фиксированная строка `'(PgS_nPc_#1)'`, одна на всех NPC, e-mail `<login>@npc.com`, `accountactive=true`) и строку `ds_npc_user (id_user, npc_level, id_race)`.

**Замечание (см. открытый вопрос §1.10.1):** INSERT в `ds_user` (`:214-219`) не указывает столбец `npc` явно — то есть в БД он либо имеет `DEFAULT true` (не проверено — дампа схемы нет), либо этот метод оставляет `npc=false/NULL`, и реальным маркером «это бот» на данном этапе служит только наличие строки в `ds_npc_user`. Флаг `ds_user.npc`, судя по всем остальным SELECT’ам в коде (`u.npc`), обязателен для остальной NPC-логики (`SU_NPC`, `GL_CanDefendComb`, ranking-фильтры) — значит либо БД доопределяет его сама, либо где-то есть недостающий шаг, не найденный в этом файле.

### 1.3.2 `SU_PopulateNPC::Populate($dbId, $worldID, $targetRace, $tplRace, $tplLevel, $count)` (`:84-155`)

Расселяет `$count` уже готовых (из `ds_npc_user`) NPC-аккаунтов заданного `$tplLevel`/`$targetRace` на соты кольца:

1. **Подбор `$count` сот** — `GL_GetCombForNPC::Get(worldID, targetRace, count)` (аргумент называется `$targetRace`, но фактически передан как номер **кольца**, судя по сигнатуре `GL_GetCombForNPC::Get($worldID, $ringnumber, $count, ...)` — несовпадение имени параметра, см. открытый вопрос §1.10.2). Если свободных сот меньше, чем `$count` — расселяется меньше, с предупреждением в stdout.
2. **Подбор `$count` свободных NPC-аккаунтов** нужного `$tplLevel`+`$targetRace`, которых **ещё нет** в этом мире — `_getNPCUIDs` (`:157-199`), прямой SQL по `ds_npc_user` с `NOT EXISTS (... ds_userinstancecollection ...)`.
3. Для каждой пары (сота, аккаунт): бан на бирже (`_addTradeBan`), применение шаблона персонажа (`_applyTemplate`) и регистрация инстанса в общей коллекции миров (`_addToCollection`, тот же `SU_CollectWorlds`, что используется при обычной регистрации игрока).

### 1.3.3 Шаблоны сот NPC (`$templates`, `:14-31` + `$combNames`, `:39-43`)

```
раса 1 (Воранер): уровень 1 → '1lvlvoraner_race1', 2 → '2lvlvoraner_race1', 3 → '3lvlvoraner_race1'
раса 2 (Лиенсу):  уровень 1 → 'LiensuMan1_race2',  2 → 'LiensuMan2_race2',  3 → 'LiensuMan3_race2'
раса 3 (Псолао):  уровень 1 → 'psolao1lvl_race3',  2 → 'psolao2lvl_race3',  3 → 'psolao3lvl_race3'
```
Применение шаблона выполняется тем же служебным механизмом переноса персонажа между мирами — `SI_ControlApplyTemplate::Apply(...)` (`:262`), то есть NPC технически «телепортируется» на новую соту точно так же, как переносится реальный игрок при межмировом переезде (полный набор стартовых зданий/юнитов шаблона проставляется этим общим кодом, не специфичным для NPC).

Название соты: для уровня 1 — жёстко `'Sleeping_threat'` («Спящая угроза»), для уровня 2 — `'Sleeping_death'` («Спящая смерть»), для уровня 3 — имя **не задано** (`$combNames[3] = ''`), поэтому используется случайно сгенерированный логин `GL_GenerateNPCCombName::generate($raceID)` как имя соты. Вывод (не проверено дизайн-документами): уровни 1-2 — узнаваемые «именные» опасные точки на карте, уровень 3 — маскируется под обычного игрока с расовым именем.

### 1.3.4 Кто и когда это запускает

**В репозитории не найдено ни одного вызова `SU_PopulateNPC::CreateUsers`/`Populate`** ни из `Admin/`, ни из `ds/utils/`, ни из какого-либо крон-скрипта — класс определён, но нигде не инстанцируется/не вызывается статически в остальном коде. Вероятнее всего это разовая GM-операция, запускаемая вручную через интерактивный PHP (`php -r "SU_PopulateNPC::Populate(...);"`) при развёртывании/донаселении конкретного мира — но прямого подтверждения (например, `.sh`-обёртки) в репозитории нет. Отмечено как открытый вопрос (§1.10.3).

### 1.3.5 Алгоритм подбора сот — `GL_GetCombForNPC::Get` (`GL_GetCombForNPC.class.php:11-76`)

Цель — равномерно расставить `$count` NPC по кольцу, ориентируясь на **число живых игроков**, а не на число сот:

```
countOnRing    = DS_Ring::GetCountUsersOnRing(worldID, ringnumber)   // живые игроки на кольце, NPC исключены (LEFT JOIN ds_npc_user ... nu.id_user IS NULL)
countPerSector = floor(countOnRing / count)
```
Далее кольцо последовательно режется на `count` секторов по числу комплексов (`DS_Ring::GetComplexCountWithUsers`, ищет минимальный номер комплекса, накопивший `countPerSector` заселённых игроками сот от предыдущей границы). Если сектор упирается в «конец жилой зоны» (`offset==0`), последний(е) сектор(а) достраиваются равным делением оставшихся комплексов. Внутри каждого сектора `_getCombInRange` (`:78-119`) ищет свободную соту, постепенно увеличивая допустимое число NPC в одном комплексе (`limitNPCInComplex`, старт с 1, до 5 — в комплексе всего 6 мест), и использует `DS_Comb::GetFreeCombInComplex`/`HasNPCInSameComplex` (`DS_Comb.class.php:783,812`), чтобы не сажать больше одного NPC в один сотовый комплекс без необходимости.

### 1.3.6 Генерация имён — `GL_GenerateNPCCombName` (весь файл)

Три расовых генератора, каждый со своим списком «слогов»/основ и добавок, собираемых через `_` (например Воранер: `Имя_Добавка`, напр. `Styheim_Q01`; Лиенсу: `Имя_Слог_Слог`; Псолао: `Имя_Слог`), с проверкой уникальности через `VD_CombName::Validate` (до 100 попыток). Раса `4`/по умолчанию → `_generateQuest()` возвращает пустую строку (не реализовано/зарезервировано).

## 1.4 Периодическая AI-логика NPC — `SU_NPC` (весь класс)

Точка входа — конструктор `SU_NPC::__construct($dbId)` (`:8-36`), запускаемый CLI-скриптом `ds/utils/NPC_Update.php` (`new SU_NPC((int)$argv[1])`, весь файл 11 строк) — предположительно по крону, конфигурация которого не входит в репозиторий.

При каждом запуске:
1. Чистит окно `ds_npc_spawn_army` старше 3 дней (`:12-13`).
2. Выбирает **все** соты, принадлежащие NPC-аккаунтам (`u.npc = true`) во **всех** мирах разом, группируя по `(id_comb, id_league, id_race, type, id_world)` и считая число незавершённых боёв на соте (`:15-22`).
3. Для каждой строки — если в этом мире включена настройка `ACTIVE_NPC` (`DE_WorldSettings`) — выполняет по порядку: `deleteIdleArmies` → `restoreHomeArmy` (или, если не подошла — `makeArmyLayer`) → (если включён шпионаж в мире, `SPY_ENABLED`) `addSpyBots` → `makeInitiatedAttacks` → `restoreProtectiveField`.

Настройки поведения кэшируются один раз на вызов (`getNPCSettings`, `:38-58`) — читает всю таблицу `ds_npc_army_settings` и раскладывает по ключам `[лига][тип]`, разбивая CSV-поля `strike_units_<раса>`/`transport_units_<раса>` в массивы ID юнитов.

### 1.4.1 Удаление «простаивающих» армий — `deleteIdleArmies` (`:67-82`)

Если на соте NPC **нет** активных боёв, удаляются все её не-домашние армии (`!isDefault`), которые либо не в действии, либо имеют нулевую силу — предварительно логируя это как **отрицательный** вклад в `ds_npc_spawn_army` (`weight = -армия.getArmyPower()`), то есть компенсируя ранее «влитую» силу в лимите расхода.

### 1.4.2 Восстановление домашней армии — `restoreHomeArmy` (`:123-158`)

```
p_check = battles>0 ? fight_army_prob : army_prob      // вероятность из ds_npc_army_settings[лига][тип]
если random() > p_check → выход (в этот тик не рероллим армию)

power      = текущая сила домашней армии NPC
min_army,max_army = ds_npc_army_settings.min_army/max_army
если у соты НЕТ владельца (getUserInstanceID()==0):
    mult = getDSArmyMultiplier(getComplexNumber())      // §1.4.6, «прогрессивная сила»
    min_army *= mult ; max_army *= mult
если power >= min_army → выход (армия уже достаточно сильна)

addedPower = random(0, max_army-min_army) + min_army - power
если Σ(домашний spawn-лимит за 3 дня) + addedPower > defense_spawn_limit → выход (упёрлись в лимит)
→ пишем строку в ds_npc_spawn_army (home=true, weight=addedPower)
→ makeArmyUnits(row, addedPower) → добавляем юниты сразу в домашнюю армию (ME_AddUnitsToHomeArmy::AddUnit)
```
**Замечание (см. §1.10.4):** условие `if (!$comb->getUserInstanceID())` теоретически противоречит тому, что исходная выборка (§1.4) требует `c.id_userinstance=ui.id_userinstance` (сота гарантированно принадлежит NPC-аккаунту) — то есть эта ветка «прогрессивной силы для ничейных сот» в наблюдаемом потоке выполнения не должна срабатывать. Либо `getUserInstanceID()` имеет неочевидную семантику (возвращает 0 именно для NPC-владельцев), либо это защитный/мёртвый код, оставшийся от более старой версии, где NPC-«монстры» могли не иметь `id_userinstance`. Без дампа БД/`DE_Comb`-семантики однозначно не разрешено — зафиксировано как факт кода, не как проверенный вывод.

Формула армии по частям (`makeArmyUnits`, `:353-414`) — армия строится из 3 групп в пропорции `strike_part : transport_part : layer_part` (сумма — `totalParts`):
- **Ударные** (`strike`) — 1 случайный юнит-ID из списка `strike_units_<раса>`, количество = `ceil(мощность_доли / getUnitPower(юнит))`.
- **Транспортные** (`transport`) — все юниты из списка `transport_units_<раса>`, мощность делится поровну между ними, `round(...)`.
- **«Прослой»** (`layer`) — все юниты класса `<= max_layer_class`, доступные расе (или всем расам < 4 в мире `FREE_FOR_ALL`), кроме уже использованных ID и служебных ID `93,98,99` (вероятно колонисты/рабочие/учёные — не юниты боя), мощность делится поровну, `round(...)`.

Для армии типа `'Pillager'` (см. §1.4.4) пропорции переопределяются жёстко: 2% на ударный юнит + 98% на транспорт, `max_layer_class` ограничен `1`.

### 1.4.3 Доращивание «прослоя» без переролла всей армии — `makeArmyLayer` (`:84-113`)

Альтернатива `restoreHomeArmy`, вызывается только если та вернула `false` (армия уже сильна). С вероятностью `layer_prob` добавляет **по 1 юниту каждого доступного вида** класса `<= max_layer_class` (расы или всех рас в `FREE_FOR_ALL`), которых у NPC ещё нет в домашней армии — то есть медленно «дополняет» линейку юнитов, а не наращивает силу существующих.

### 1.4.4 Инициативные атаки — `makeInitiatedAttacks` + `chooseTarget` (`:191-320`)

С вероятностью `init_attack_prob` NPC выбирает цель (`chooseTarget`) одним из 4 взаимоисключающих способов, вероятность каждого задаётся отдельным полем `attack_by_<тип>` (нормируются в кумулятивные интервалы и рулетка):

| Тип выбора | Логика |
|---|---|
| `top_rating` | Топ `NPC_TOP_RATING_PERCENT_FOR_ATTACK`% игроков мира по убыванию `science_ranking+artefact_ranking+building_ranking + battlexp.absolute_value*100` |
| `rating_change` | Топ тот же % игроков по наибольшему **приросту** суммарного рейтинга за последние сутки (`ds_ranking_archive`, вчера/сегодня) |
| `attackers` | Игроки, которые **сами атаковали** этого NPC (были `defender` в `ds_npc_battle_log`) за последние 2 дня |
| `neighbours` | Игроки с номером комплекса в диапазоне `±50` от комплекса NPC |

Общий фильтр цели (все 4 варианта): активен аккаунт, не забанен (обычный/премиум-бан), не под силовым щитом, не сам NPC (`not u.npc`), сота имеет активные Центральные Ворота (`id_building=6`), уровень игрока — в диапазоне `[min_level_for_init_attack, max_level_for_init_attack]`; для `RACE_VS_RACE`-миров исключается своё кольцо; если в мире запрещены атаки внутри своего комплекса (`ALLOW_COMBCOMPLEX_ATTACK=false`) — исключается свой комплекс.

Тип армии: если цель выбрана способом `attackers` → NPC шлёт `'Raider'` (полноценный отряд, 2 волны: 5% силы + 95% силы, см. `:206-215`); во всех остальных случаях → `'Pillager'` («грабля», сила из `[min_pillage_army, max_pillage_army]`, состав почти целиком транспорт). Для NPC без владельца сила армии дополнительно множится на `(1 + getComplexNumber()/100)` (плавный рост с удалением от центра, отдельный от «прогрессивной силы» §1.4.6 — та же оговорка §1.10.4 применима). Полёт создаётся как обычное событие `MOVE_TO_ATTACK` (`ME_CreateArmyAction`) с временем перелёта по стандартной формуле `GL_TravelTime::Count`.

### 1.4.5 Защитные зонды — `addSpyBots` (`:161-188`, только если `SPY_ENABLED`)

Если сумма `CURRENT_AMOUNT+AWAY_AMOUNT` зондов-разведчиков (`SPY_ZOND_SCOUT`) меньше `min_zonds`, докупает случайное число до `[min_zonds, max_zonds]` и сразу ставит их всех в режим `DEFEND` (юнит `id_unit=83`) на время `SPY_MAX_DEFENCE_TIME * TURN_TIME * 60` секунд.

### 1.4.6 «Прогрессивная сила» — `getDSArmyMultiplier` (`:116-121`)

```
mult(complex) = HYPER^(complex-1) * HVP + (PARA+complex)² / (PARA+1)² * (1-HVP)
```
где `HYPER = PROGRESSIVE_STRENGTH_HYPER_MOD`, `PARA = PROGRESSIVE_STRENGTH_PARA_MOD`, `HVP = PROGRESSIVE_STRENGTH_HYPER_VS_PARA` — настройки мира (0..1 для `HVP`, судя по названию — доля «гиперболической» составляющей формулы против «параболической»). Композиция экспоненциального и квадратичного роста, смешанная линейно по `HVP`. Используется для масштабирования силы NPC-армии на **ничейных** сотах в зависимости от номера комплекса (расстояния от центра кольца) — семантика владения обсуждена в открытом вопросе §1.10.4.

### 1.4.7 Восстановление защитного поля — `restoreProtectiveField` (`:417-424`)

Если у соты нет активных боёв и она является «захваченной колонией» (`getIsCapture()`), защитное поле (`DE_CombProtectiveField`) поднимается до 100%, если оно ниже.

## 1.5 Ответная реакция NPC после боя

### 1.5.1 `ME_LogNPCBattle::Log($battle, $isDefender)` (весь файл)

Вызывается из `CR_Battle.class.php:309-313` для **любого** законченного боя, где хотя бы одна из сторон — NPC (`ACTIVE_NPC` должен быть включён в мире). Всегда пишет строку в `ds_npc_battle_log`. Если NPC был **защитником** (`$isDefender`):

1. Считает `lossPart` — долю потерянной силы защитника за весь бой (`потери/(остаток+потери)`), и `foundRes` — грабили ли у него что-то из 5 базовых ресурсов.
2. Ищет `(league, type)` NPC (если не задан хотя бы один — выход без реакции).
3. Складывает **4 независимые вероятности** атаки из `ds_npc_attack_chance` (значения **суммируются**, не перемножаются и не выбираются по одной):
   - `condType=1` — по проценту потерь (`condValue` — верхняя граница диапазона, наименьший подходящий `condValue > lossPart*100`);
   - `condType=2` — по числу боёв NPC против именно этого атакующего за 2 дня (как защитник);
   - `condType=3` — по числу **ответов** NPC этому же атакующему за 2 дня (как атакующий);
   - `condType=4` — по факту, был ли грабёж (`condValue=1/0`).
4. `random() < Σвероятностей` → создаётся ответная атака: с вероятностью 60% — на ту же соту, что атаковала; иначе — на случайную соту из всех сот атакующего инстанса.
5. Сила ответной армии: базовая сила атакующего в этом бою (`$weight`, вес юнитов-атакующих в 0-м раунде) умножается на случайный коэффициент из диапазона `[min,max]`, взятого из `condType=6/7` (`ds_npc_attack_chance`) в зависимости от того, кто выиграл бой (`getWinnerCode()=='D'` — оборона выстояла — берётся один диапазон, иначе другой), затем **ограничивается сверху** `max_attack_army` (с той же поправкой `getDSArmyMultiplier`, если у NPC нет владельца), и итог проверяется против скользящего 3-дневного лимита `attack_spawn_limit` (`ds_npc_spawn_army`, `home=false`).
6. Событие `NPC_ATTACK` создаётся с **случайной задержкой вылета 0..3600 сек** (`DE_EventQueue::CreateInDB`, не немедленно) — фактическая генерация армии и расчёт перелёта откладываются до обработки события (`EH_NPCAttack`, §1.5.3).
7. С вероятностью `condType=5` может быть запланирована **вторая** такая же атака (либо на ту же соту, либо — с вероятностью 60% на случайную, иначе на **ближайшую по времени перелёта** соту атакующего), с тем же лимитом.

### 1.5.2 Восстановление «прослоя» и повторные вылеты внутри самого боя — `EH_BattleRound` (`:285-430`)

Между раундами одного и того же боя (не после его завершения!), если бой идёт против NPC-защитника, с вероятностью `fight_layer_prob` NPC добавляет по 1 юниту каждого доступного вида `<= max_layer_class` прямо в свою домашнюю армию (аналог `makeArmyLayer`, но во время боя). Если атакующая сторона — NPC (не `Collector`-армии, которые используются механикой археологии/уборки урожая — здесь не разбирается), после раунда, где решилась победа, с вероятностью из `ds_npc_repeat_attack` (индекс — комбинация булевых условий: первый ли бой против этого игрока за 2 дня, была ли это грабля, победил ли NPC, были ли потери, был ли грабёж) планируется **немедленный повторный вылет** — тип армии выбирается рулеткой среди 5 вариантов (`pillager`/`big_pillager`/`raider`/`big_raider`/`spam`), размер — соответствующий диапазон `[min,max]_pillage_army`/`[min,max]_init_army`, при `big_*` дополнительно умноженный на `big_army_multiplier`.

### 1.5.3 `EH_NPCAttack` (весь файл)

Обработчик отложенного события `NPC_ATTACK` (созданного `ME_LogNPCBattle`): по параметрам события (`ID_CombFrom`, `ID_CombTo`, `ArmyWeight`) заново собирает армию через собственный `GenerateArmy()` (структурно идентичен `SU_NPC::makeArmyUnits`, но как самостоятельная копия — юниты собираются из тех же долей `strike/transport/layer_part`, определяемых по `(league, type)` цели-NPC на момент обработки события), после чего создаёт стандартный полёт `MOVE_TO_ATTACK`.

## 1.6 Последствия для игрока: победа/поражение против NPC

- **Обычный грабёж** ресурсов при победе атакующего работает как в PvP — тот же `ME_ResourceStealing::LoadResource` (не специфичен для NPC, здесь не переразбирается).
- **Награда новичку за бой с NPC** — `ME_EndBattle::_RewardNewb` (`:59-224`), включается настройкой мира `REWARD_NEWB_ENABLED`. Для боёв **игрок против игрока** ставка вычисляется по формуле от разницы уровней (парабола `0.5*(A*(diff-Xa)²+Ya)`, здесь не переразбирается подробно — общий, не NPC-специфичный механизм). Но если одна из сторон — NPC, ветка иная:
  ```
  attIsNPC ? recipient='ATTACKER', rewardClass=Reward(defender), leagueDiff = max(0, defenderLeague - attackerLeague)
  defIsNPC ? recipient='DEFENDER', rewardClass=Reward(attacker), leagueDiff = max(0, attackerLeague - defenderLeague)
  rewardTax = REWARD_NEWB_FOR_NPC_<leagueDiff>          // отдельная группа настроек мира, по разнице ЛИГ (не уровней!)
  ```
  Награда по каждому ресурсу = `rewardTax% × Σ(число убитых юнитов победившей от NPC стороны × PRODUCTION_COSTS(ресурс) этого юнита)`. Начисляется через `DE_Reward::deltaReward`, а также кладётся в атрибуты самого боя (`STEALING_REWARD_<ресурс>`) для отображения в боевом отчёте.
- **Отдельный «NPC-опыт»** — `DE_BattleXP::getNpcXP()/deltaNpcXP()` — накапливается отдельно от обычного боевого опыта именно за бои с NPC (`ME_FormBattleLog.class.php:170-173,248-251`); используется, видимо, для отдельной статистики/ачивок (само место начисления `deltaNpcXP` за пределами прочитанных файлов не поймано — не расшифровано подробно).
- **Текст в боевом отчёте** переключается на специальную локализацию `STEALING_REWARD_NPC`/`STEALING_REWARD_DEFENDER` в зависимости от того, кто из сторон был NPC (`ME_FormBattleLog.class.php:467-509`).
- **Рейтинг**: любое изменение рейтинга (`DE_Ranking::delta{Science,Atefact,Battle,Building}Ranking`) — **no-op**, если целевой аккаунт NPC (`DE_Ranking.class.php:66-124`). То есть NPC не поднимаются в общем рейтинге игроков ни от боя, ни от чего-либо ещё.
- **Соту NPC нельзя взять под защиту** другим игроком — `GL_CanDefendComb.class.php:224-227`, отдельная явная проверка с кодом ошибки `DEFEND_NPC_COMB` (используется в `UA_Defend.class.php:183-184`).
- **NPC не получает «защиту новичка»** от чужих атак наравне с обычными игроками не проверялось отдельно, но `UA_Attack.class.php:465`/`UA_Defend.class.php:229` содержат условие `$this->combTo->getUser()->getIsUserNpc() == 'f'` при проверке новичкового щита цели — то есть NPC как **цель** не подпадает под чужую newb-защиту (её физически нет на NPC-аккаунтах либо проверка её игнорирует).

## 1.7 Административная сторона (`Admin/controls/GameWorlds/NPC/`)

Панель (`index.php`+`save.php`) позволяет **без деплоя кода** править вживую все ~30 полей `ds_npc_army_settings`, всю таблицу вероятностей `ds_npc_attack_chance` (общий список условий `1|1, 1|3, 1|12, 1|25, 1|50, 1|100, 2|1, 2|2, 2|4, 2|8, 2|12, 2|18, 3|0, 3|1, 3|2, 3|4, 3|10, 3|30, 4|1, 4|0, 5|0, 6|1, 7|1, 6|0, 7|0` — жёстко зашит в `save.php:10`, задаёт ровно те пороги, что видны в шапках таблицы UI, см. §1.5.1) и `ds_npc_repeat_attack`, добавлять новые пары `(лига, тип)`, а также — для каждого уже расселённого NPC-аккаунта в выбранном мире — вручную менять его лигу/тип/уровень рейтинга и смотреть его координаты и статистику атак/защит за день/неделю. Создания/расселения новых NPC (эквивалента `SU_PopulateNPC`) в этой панели нет.

## 1.8 Соответствие терминов «лига»/«тип»/«уровень»

В коде фактически три независимых числовых параметра NPC, которые легко перепутать:
- `ds_npc_user.npc_level` (1..3) — «уровень сложности» **шаблона**, задаваемый один раз при расселении (`SU_PopulateNPC`), определяет только стартовый шаблон сотового комплекса и имя;
- `ds_userinstance.id_league` — лига, обычный игровой атрибут инстанса (используется как есть и для реальных игроков);
- `ds_npchastype.type` — целое число, отдельный «поведенческий тип» NPC внутри лиги, ключ (вместе с лигой) в `ds_npc_army_settings`/`ds_npc_attack_chance`; заводится/меняется только через админку.

Прямой связи «`npc_level` → `type`» в коде не найдено — они независимы, `type` управляется полностью вручную через `Admin/controls/GameWorlds/NPC`.

## 1.9 Связь с археологическими экспедициями — не обнаружена

По заданию проверена гипотеза, что NPC — это то, на что игрок натыкается при археологии (`DS_Archeology`/`EH_ArcheologyTeam`, упомянутые в [mechanics-economy-trade.md](mechanics-economy-trade.md) и [mechanics-research.md](mechanics-research.md)). Проверка (полный список файлов с упоминанием `archeol*`, перекрёстный `grep -i npc` по каждому) **не выявила ни одного пересечения** — ни `EH_ArcheologyTeam`, ни `DS_Archeology`, ни любой из связанных `PN_Archeology*`/`MC_CompilerArcheologyTeam`/`SMS_ArhiologyController` не ссылаются на `ds_npc_*`-таблицы или NPC-классы, и наоборот — ни один NPC-класс не ссылается на археологию. Единственное совпадение — техническое: `DS_Comb.class.php` содержит и метод `HasNPCInSameComplex` (NPC), и упоминания слова «archeol» в других несвязанных методах того же файла (комментарии/имена методов про совсем другие сущности) — это совпадение внутри одного файла с разнородными статическими методами, не архитектурная связь. **Вывод: в прочитанном коде это две полностью независимые подсистемы.**

# Часть 2. Терраформинг

## TL;DR

Терраформинг — компактная, полностью независимая от NPC подсистема на 5 классов (без вариаций/подтипов, в отличие от NPC). Механика привязана к **конкретной ячейке** (`ds_cell`, не ко всей соте): чтобы сменить тип грунта (`id_groundtype`) одной ячейки, на ней должно стоять специальное здание **«Терраформер»** (`id_building = 64`, имя восстановлено косвенно — см. §2.3). Игрок выбирает целевой тип грунта из тех, для которых в справочнике `ds_terraforming` есть запись `(id_groundtypefrom = текущий тип, id_groundtypeto = целевой)` и все требуемые науки (`ds_terraformingneedscience`) изучены. Стоимость и время — фиксированные данные-атрибуты этой конкретной пары «откуда-куда» (`ds_terraforminghasattribute`, тип `PRODUCTION_COSTS`), без формулы роста. Ключевая особенность: **тип грунта ячейки меняется мгновенно** в момент запуска команды (не по завершении!), а по завершении отрабатывающего события удаляется само здание-терраформер на этой ячейке (освобождая её под постройку здания нового типа, которому подходит новый грунт). Терраформинг можно отменить в процессе — грунт откатывается назад, здание-терраформер остаётся (не удаляется), часть ресурсов возвращается по той же формуле, что и при отмене апгрейда здания (см. ниже — возможная неточность/наследованный баг, §2.9.1). Явного числового лимита «сколько раз можно терраформировать одну ячейку» в коде не найдено — ограничение фактически только в том, что здание-терраформер каждый раз нужно строить заново.

## 2.1 Карта классов

## 2.3 Требуемое здание — «Терраформер» (`id_building = 64`)

`UA_Terraforming::checkAction()` (`UA_Terraforming.class.php:46-47`) первым делом вызывает `DS_Terraforming::ValidateCellIDInAction($cellID, $combID)` (`DS_Terraforming.class.php:127-159`), которая **жёстко проверяет наличие активного (`active`) здания с `id_building = 64` именно на этой ячейке этой соты** — иначе возвращает `0`, и `assert` в `checkAction` завалит команду. Русскоязычное имя здания в коде напрямую не встречается (нет `PN_BuildingInfo`-текста с явным ID=64 в прочитанных файлах), но косвенно подтверждается системным сообщением `$lang['ACTIVE_TERRAFORMER']` («Вы не можете удалить терраформер во время его работы», `language/R/user_shop.lang:132`) и логикой блокировки/разблокировки атрибута `DESTROYABLE` именно на этом здании во время процесса (см. §2.5). Здание-терраформер, судя по всему, строится обычным путём — через стандартную постройку зданий (`UA_ConstructBuilding`, не переразбирается здесь), требования по научным уровням/предзданиям для самого здания №64 в рамках этой задачи не проверялись отдельно.

Отдельно, тип грунта, на котором можно **строить** конкретное здание, задаётся таблицей `ds_buildingcanbebuildon (id_building, id_celltype, id_groundtype)` — используется в `PN_AllowBuildings.class.php:83,227` для фильтрации списка доступных к постройке зданий. Отсюда **практический смысл терраформинга**: сменить тип грунта ячейки, чтобы на ней стало можно строить здания, недоступные на исходном грунте (терраформинг сам по себе не даёт прямого производственного бонуса — влияние на производство соты в прочитанном коде терраформинга не найдено).

## 2.4 Флоу команды `UA_Terraforming` (`весь файл`)

**`checkLocalParams()`** (`:22-40`): разбирает номер ячейки (`c`) из XML, резолвит `id_cell`/`id_attachedbuilding` через `ME_CombViewGetCellIDAndBuildigIDByCell::Exec`, читает желаемый **тип грунта по имени** (`type` — атрибут XML, строка вида `groundname`, не числовой ID).

**`checkAction()`** (`:43-55`):
```
groundTypeIDFrom = DS_Terraforming::ValidateCellIDInAction(cellID, combID)     // здание-терраформер должно стоять именно тут
assert(groundTypeIDFrom > 0)

terraformingID = DS_Terraforming::ValidateTerraformingType(groundTypeIDFrom, groundTypeToName, uiid)
assert(terraformingID > 0)
```
`ValidateTerraformingType` (`DS_Terraforming.class.php:161-225`) ищет **единственную** запись `ds_terraforming`, у которой `id_groundtypefrom = groundTypeIDFrom` и `id_groundtypeto = (SELECT id_groundtype FROM ds_groundtype WHERE groundname = ...)`, **И** у которой число требуемых наук (`ds_terraformingneedscience`) равно числу тех же наук, уже изученных этим игроком (`ds_userhasscience.inresearch=false`) — если наука не подходит или перехода вообще не существует, вернётся `0`, и вся команда завалится на `assert`.

**`performAction()`** (`:58-131`):
1. Проверка отпускного режима (`GL_IsUserInVocationMode`) и активного силового щита (`DE_PowerShild`) — команда молча завершается с алертом, ничего не расходуя.
2. **Списание ресурсов сразу и полностью** (без учёта прогресса, без деления на какой-либо «дивизор»): для каждого атрибута `PRODUCTION_COSTS.<ресурс>` записи терраформинга — если у соты есть такой ресурс, вычитается **вся** нужная сумма; если ресурса не хватает — вызывается `ds_error(...)` (сообщение об ошибке, ресурсы всё равно теоретически уже могли начать списываться по предыдущим ресурсам цикла — порядок неатомарный по ресурсам внутри одного `foreach`, отмечено как факт кода).
3. **`DS_Terraforming::SetNewGroundTypeOnCellByTerraformingID`** — тип грунта ячейки меняется **немедленно**, в момент запуска команды, а не по завершении процесса. Кэш вида соты сбрасывается (`CR_CombView::resetCells`).
4. **Время работы**: `workTime = CONSTRUCTION_TIME(ходы) × TURN_TIME(мин/ход) × 60` секунд — простое произведение, **без** какого-либо дополнительного делителя (в отличие от, например, времени активации здания, которое делится на `REACTIVATION_DIVISOR` — см. [mechanics-buildings.md](mechanics-buildings.md)).
5. Создаётся событие `TERRAFORMING` (`createEvent`, параметры `ID_Cell`, `ID_Comb`, `ID_Terraforming` — `createEventParams`, `:133-143`), биндится к ячейке (`DS_Terraforming::BindEventQueue`).
6. Игроку — системное сообщение `TERRAFORMING_START`.
7. **Зданию-терраформеру снимается флаг `DESTROYABLE`** (`DS_Building::DeleteAttachedBuildingAttribute(...,'DESTROYABLE')`) — его нельзя снести, пока идёт процесс (отсюда и текст `ACTIVE_TERRAFORMER`, §2.3).

## 2.5 Обработка события — `EH_Terraforming` (весь файл)

Стандартный паттерн `EH_*`: если время ещё не наступило (`_isTimeToHandle()==false`) — `_preHandle()` просто шлёт участникам события необязательное для хранения (`'NOTFORSTORE'`) сообщение `TERRAFORMING_PROCESS` с оставшимся временем, ничего не меняя. По наступлении времени — `_handle()`:
1. Отвязывает событие от ячейки (`UnBindEventQueue`).
2. **Удаляет само здание-терраформер** на этой ячейке (`DS_Terraforming::DeleteTerraformer` → `DELETE FROM ds_attachedbuilding WHERE id_cell = ...`) — ячейка становится свободной (грунт уже сменился в момент запуска, см. §2.4.3), готовой под новую постройку.
3. Сбрасывает кэш вида соты (`resetBuildings`), шлёт сообщение `TERRAFORMING_END`, помечает событие как отработанное (`setTrash`).

## 2.6 Отмена — `UA_CancelTerraform` + `ME_CancelTerraform`

`UA_CancelTerraform` (`extends UA_Terraforming`, но фактически не использует унаследованную логику начала процесса, только `UA_Action`): проверяет, что на данной ячейке действительно есть привязанное событие (`DS_Terraforming::HaveTerraformingOnCell`), и — при отсутствии вакационного режима/щита — делегирует всё в `ME_CancelTerraform::Cancel($cellID)`:

```
res            = DS_Building::GetAttachedBuildingByCellID(cellID)     // здание-терраформер на этой ячейке
combID, attachedBuildingID = res[...]
bindeqid       = DS_Terraforming::HaveTerraformingOnCell(cellID)
terraformingID = EventQueueAttributes(bindeqid).ID_Terraforming

DS_Terraforming::SetOldGroundTypeOnCellByTerraformingID(terraformingID, cellID)   // откат грунта на ИСХОДНЫЙ тип

prog    = getProgress(bindeqid)                                  // % готовности, 0..100 (SQL-функция БД)
minlost = MIN_RES_LOST_ON_CANCEL_BUILDING * 100                  // мировая настройка, доля→проценты
prog    = max(prog, minlost)                                     // штраф не может быть меньше минимального
divisor = UPGRADE_COSTS_DIVISOR                                  // мировая настройка

для каждого ресурса PRODUCTION_COSTS терраформинга (кроме WORKER):
    delta = round((value - value*prog/100) / divisor)            // возврат (100-prog)% стоимости, делённой на divisor
для WORKER:
    delta = round(value / divisor)                                // рабочие возвращаются полностью (без учёта прогресса)

combAttributes.CURRENT_AMOUNT[ресурс] += delta

event.setIsTrash(true)
DS_Terraforming::UnBindEventQueue(cellID)
DS_Building::InsertAttachedBuildingAttribute(attachedBuildingID, 'CURRENT_FLAG', 'DESTROYABLE')   // здание снова можно снести
```

Формула возврата **дословно повторяет** формулу отмены апгрейда здания (`ME_CancelUpgradeBuilding`, см. [mechanics-buildings.md §5.4](mechanics-buildings.md)), включая переиспользование мировой константы `UPGRADE_COSTS_DIVISOR`. Ключевое отличие: терраформинг при **старте** списывает ресурсы **без** деления на `UPGRADE_COSTS_DIVISOR` (см. §2.4.2, шаг 2 — там нет никакого `/divisor`), тогда как здание при апгрейде списывает стоимость именно **с** этим делителем. Значит формула отмены здесь, по-видимому, скопирована из кода отмены апгрейда без адаптации под то, что терраформинг сам делитель при списании не использовал — при `UPGRADE_COSTS_DIVISOR != 1` это давало бы игроку заниженный (или завышенный, если делитель <1) возврат по сравнению с реально списанной суммой. Отмечено как вероятная унаследованная неточность оригинала, не как продуманный дизайн — см. открытый вопрос §2.9.1.

Здание-терраформер при отмене **не удаляется** (в отличие от успешного завершения, §2.5, шаг 2) — оно остаётся на ячейке, снова доступное для сноса (`DESTROYABLE` восстановлен), либо для повторного запуска другого терраформинга.

## 2.7 UI-панель — `PN_Terraforming` (весь файл)

Открывается на конкретной ячейке (`extends UA_GetBuildMenu`, `id_cell` контекста уже разрешён родителем). Если на ячейке **нет** активного терраформинга (`HaveTerraformingOnCell == 0`) — `_formXMLForFirstMenu`: список **всех** допустимых переходов из текущего грунта, доступных этому игроку по науке (`GetAllowFormingsByCellIDAndUIID`), для каждого — целевой тип грунта, время (`CONSTRUCTION_TIME × TURN_TIME × 60`, в форматированном виде `GB_TimePeriod::getDSFormat()`), список нужных ресурсов в компактном виде `<первая_буква_ресурса><число>` через `:`, и флаг `s` (`"1"` — можно начать, `"0"` — не хватает текущих ресурсов на соте, `PRODUCTION_COSTS > CURRENT_AMOUNT` хотя бы по одному ресурсу). Если терраформинг **уже идёт** — `_formXMLForSecondMenu`: та же информация по единственной активной записи плюс `action` — оставшееся время до конца, и `s="2"` (жёстко — «разрешена отмена», без дополнительных условий).

## 2.8 Ограничения — сводка

1. **Наука** — `ds_terraformingneedscience`, схема «число нужных = число изученных», аналогично зданиям/юнитам (см. §2.2, §2.4). Проверяется дважды: в `GetAllowFormingsByCellIDAndUIID` (для списка в UI) и в `ValidateTerraformingType` (в самой команде) — обе идентичны, дублирования расхождений (как было с расой у науки, см. mechanics-research.md §4.9) здесь не найдено.
2. **Здание** — активный «Терраформер» (`id_building=64`) должен стоять именно на целевой ячейке (§2.3). Здание одноразовое в смысле процесса — уничтожается автоматически по завершении (§2.5), то есть **на следующий терраформинг той же ячейки здание нужно строить заново**.
3. **Один активный процесс на ячейку** — `ds_terraformingbindeventqueue` уникален по `id_cell` (assert в `HaveTerraformingOnCell`). Разные ячейки одной и той же соты **можно** терраформировать параллельно (лимита на число одновременных терраформингов на соту/аккаунт в прочитанном коде не найдено — в отличие от науки, где ограничение жёсткое «1 на аккаунт»).
4. **Ресурсы соты** — обычная проверка достаточности `CURRENT_AMOUNT >= PRODUCTION_COSTS` по каждому используемому ресурсу; листинг допустимых переходов в UI дополнительно помечает недоступные по ресурсам варианты (`s="0"`), но не скрывает их из списка.
5. **Отпускной режим / силовой щит** — команда старта и команда отмены обе проверяют `GL_IsUserInVocationMode`/`DE_PowerShild` и молча блокируются алертом, если активно хотя бы одно.
6. **Явного лимита числа терраформирований одной и той же ячейки за игру** нет — только организационное ограничение «нужно каждый раз заново строить здание».

## 2.9 Итоговая схема потока

```
Игрок строит здание "Терраформер" (id_building=64) на конкретной ячейке X своей соты
        │
        ▼
UA_Terraforming.checkAction():
  ├─ на ячейке X стоит активный Терраформер?           (DS_Terraforming::ValidateCellIDInAction)
  └─ существует переход groundFrom→groundTo с именем type
     И все требуемые науки изучены?                     (DS_Terraforming::ValidateTerraformingType)
        │ (ок)
        ▼
UA_Terraforming.performAction():
  не в отпуске / нет активного щита?
  списать PRODUCTION_COSTS(ресурсы) со соты ПОЛНОСТЬЮ (без деления)
  id_groundtype ячейки X → НЕМЕДЛЕННО меняется на целевой
  создать событие TERRAFORMING на workTime = CONSTRUCTION_TIME*TURN_TIME*60 сек
  забиндить событие к ячейке X (ds_terraformingbindeventqueue)
  снять DESTROYABLE со здания-Терраформера
        │
        ▼  (каждый тик, пока не наступит endtime)
EH_Terraforming.handleEvent():
  ещё не время → сообщение о прогрессе, ничего не меняется
  наступило время → отвязать событие, УДАЛИТЬ здание-Терраформер на ячейке X,
                    сообщение TERRAFORMING_END, событие в trash
        │
        │  (в любой момент до завершения — альтернативная ветка)
        ▼
UA_CancelTerraform → ME_CancelTerraform.Cancel():
  id_groundtype ячейки X → откат на ИСХОДНЫЙ тип
  частичный возврат ресурсов по формуле (100-prog)%/UPGRADE_COSTS_DIVISOR (WORKER — 100% всегда)
  событие в trash, ячейка отвязана
  здание-Терраформер ОСТАЁТСЯ на ячейке, снова разрешено к сносу (DESTROYABLE восстановлен)
```

Относится к §2.2/§2.4 (`ds_terraformingneedscience`). В статье числа
сведены в одну таблицу «наука × целевой тип грунта», без разбивки по
исходному типу — то есть, судя по всему (**предположительно**, вики не
уточняет), требование зависит только от того, **во что** превращают
ячейку, а не от того, из чего:

| Наука | → вода | → пустыня | → трава | → земля |
|---|---|---|---|---|
| Кадериум | 10 | 12 | 12 | 12 |
| Нано-кристаллы | 10 | 13 | 13 | 13 |
| Продиум | 0 | 14 | 18 | 20 |
| Статическая энергия | 12 | 13 | 20 | 25 |
| Еда | 12 | 18 | 25 | 25 |

«0» у Продиума для перехода в воду, судя по всему, означает «эта наука не
входит в требования для этого перехода» (в схеме
`ds_terraformingneedscience` попросту нет строки), а не «требуется 0-й
уровень» — по аналогии с тем, как устроены научные требования
зданий/юнитов в остальном движке (см. §2.8, п.1).

### Время перестройки одной ячейки (в турнах)

Раскладывает `workTime`/`CONSTRUCTION_TIME` из §2.4 шаг 4 на конкретные
числа для этого мира:

- Постройка терраформера — **4 турна** (обычная постройка здания №64,
  отдельно от самого события `TERRAFORMING`).
- Собственно перестройка грунта (событие `TERRAFORMING`, §2.5) — **20
  турнов**.
- Итого полный цикл смены типа грунта одной ячейки «с нуля» (здания на
  ячейке ещё нет) — **24 турна**.

### Допустимые переходы между типами грунта (граф `ds_terraforming`, §2.2)

Вики явно перечисляет только следующие переходы (граф несимметричный):

- **вода ↔ пустыня** — единственная пара, где переход работает в обе
  стороны напрямую.
- **трава → вода, пустыня, земля** — из травы можно уйти в любой из трёх
  остальных типов.
- **земля → вода, пустыня, трава** — симметрично траве.

Обратных переходов **вода → трава/земля** и **пустыня → трава/земля** в
статье не перечислено — то есть, если ячейка уже стала водой или пустыней,
вернуть её напрямую в траву/землю (по данным этого мира) нельзя. Граф не
полный: из 12 возможных упорядоченных пар «откуда-куда» между 4 типами
допустимо, по вики, всего 8: вода→пустыня, пустыня→вода, трава→вода,
трава→пустыня, трава→земля, земля→вода, земля→пустыня, земля→трава.

## Открытые вопросы

### По части 1 (NPC)

1. **§1.3.1** — `SU_PopulateNPC::_createNPCUser` вставляет строку `ds_user` без явного столбца `npc` в списке INSERT (`:214-219`), хотя вся остальная NPC-логика жёстко полагается на `ds_user.npc = true`. Либо в схеме БД есть `DEFAULT true`/триггер (не проверено — дампа схемы нет в репозитории), либо это неполный код и где-то ещё (не найдено) флаг проставляется отдельно.
2. **§1.3.2** — в `SU_PopulateNPC::Populate` четвёртый параметр вызова `GL_GetCombForNPC::Get(self::$worldID, $targetRace, $count)` фактически передаётся туда, где сигнатура метода ожидает **номер кольца** (`$ringnumber`), а не расу — несовпадение имени переменной со смыслом использования. Не установлено, баг ли это (могло исторически работать, если для конкретного мира номер кольца численно совпадал с ID расы) или неверно подобранное автором имя параметра без функциональной ошибки.
3. **§1.3.4** — в репозитории не найдено ни одного вызова `SU_PopulateNPC::CreateUsers`/`Populate` (ни из `Admin/`, ни из `ds/utils/`, ни из конфигурации крона). Механизм и периодичность первичного создания/расселения новых NPC в проде не установлены — вероятно, ручная разовая операция вне репозитория.
4. **§1.4.2, §1.4.4** — условие `if (!$comb->getUserInstanceID())` («прогрессивная сила» для «ничейных» сот) в наблюдаемом потоке выполнения `SU_NPC` формально противоречит тому, что исходная выборка требует владения сотой NPC-аккаунтом. Осталось не выясненным: имеет ли `DE_Comb::getUserInstanceID()` особую семантику для NPC-владельцев (например, различает «настоящего» NPC-игрока и разряд «диких»/нейтральных сот) — определение самого метода не читалось в рамках этой задачи. Требует либо чтения `DE_Comb.class.php` целиком, либо трактовки как защитного/мёртвого кода.
5. **§1.5.1** — точное значение `condType` в `ds_npc_attack_chance` для «побеждён/не побеждён» (`getWinnerCode()=='D'`) сопоставлено с полями `condType=6/7` по данным из кода (`ME_LogNPCBattle.class.php:112-119`) и заголовков колонок в админке («Бой выигран, мин/макс армия» / «Бой проигран, мин/макс армия») — само сопоставление 6↔выигран/7↔проигран (или наоборот) не подтверждено на 100% (могло быть в обратном порядке).
6. **Численные значения всех настроек мира**, используемых в NPC-логике (`ACTIVE_NPC`, `SPY_ENABLED`, `NPC_TOP_RATING_PERCENT_FOR_ATTACK`, `PROGRESSIVE_STRENGTH_*`, `REWARD_NEWB_FOR_NPC_<N>` и т.д.) и всё содержимое таблиц `ds_npc_army_settings`/`ds_npc_attack_chance`/`ds_npc_repeat_attack` по конкретным лигам/типам — не найдены в PHP-репозитории (это данные БД, не логика); реконструирован только список названий столбцов (через админ-панель) и алгоритм их использования.

### По части 2 (терраформинг)

1. **§2.6** — формула возврата ресурсов при отмене терраформинга дословно копирует формулу отмены апгрейда здания и использует мировую константу `UPGRADE_COSTS_DIVISOR`, хотя при **старте** терраформинга (§2.4, шаг 2) эта константа не применяется вовсе (списывается полная сумма `PRODUCTION_COSTS`). Похоже на копипасту без адаптации — при значении `UPGRADE_COSTS_DIVISOR ≠ 1` возврат игроку не будет соответствовать реально списанной сумме. Требует решения при ремастере: воспроизводить как есть или считать багом оригинала и не переносить в новую реализацию.
2. **Наполнение справочника `ds_terraforming`** — какие именно типы грунта существуют (`ds_groundtype`), какой граф переходов между ними задан (не «любой в любой», а конкретный список пар «откуда-куда»), какие конкретно науки/уровни требуются для каждого перехода и какова конкретная стоимость/время — все это данные БД, не найденные в PHP-репозитории. В коде подтверждён только сам механизм (граф пар + атрибуты + требования науки), не его конкретное наполнение. **Теперь есть иллюстративный пример** — §2.10, конкретные числа (граф переходов, уровни науки, стоимости, время) из архивной вики игроков для одного мира на 2014 год. Вопрос остаётся открытым **в общем случае**, поскольку это per-world настройка (§2.2) — вики не гарантирует, что те же числа/граф действуют во всех мирах и версиях (Classic/Unlimited/Pulsar) архива.
3. **Название и требования здания «Терраформер» (`id_building=64`)** — сам факт ID и связь с локализационной строкой `ACTIVE_TERRAFORMER` установлены косвенно; полная карточка здания (стоимость постройки, требуемые науки/предздания, допустимые типы грунта для его собственной постройки) не разбиралась в рамках этой задачи — это относится к обычной механике зданий, не к терраформингу как таковому. **Частично закрыто §2.10**: уровни требуемой науки и стоимость постройки самого терраформера теперь известны из вики одного мира — но требуемые предздания и допустимые типы грунта для постройки терраформера (`ds_buildingcanbebuildon`, §2.3) по-прежнему не установлены.
4. **Атомарность списания ресурсов при старте** (§2.4, шаг 2) — цикл по ресурсам не оборачивает списание в транзакцию/предварительную проверку "хватает ли всех сразу"; при нехватке одного из нескольких требуемых ресурсов вызывается `ds_error(...)`, но не проверено, откатываются ли уже списанные до этого момента ресурсы того же вызова (в других частях движка это обычно решается проверкой "хватает по всем" до начала списания — здесь такой предварительной проверки в самом `performAction` не видно, в отличие от UI-панели, которая заранее помечает `s="0"`, если ресурсов не хватает, но это не серверная гарантия).
