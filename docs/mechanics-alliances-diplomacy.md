# Механика альянсов и дипломатии

Технический разбор подсистемы альянсов «Сферы Судьбы» на основе PHP-кода
`old-sphere`. Документ нужен как основа для ремастера (реализация с нуля, без
чтения оригинального PHP) — поэтому упор на точные правила, формулы,
состояния БД и найденные дефекты оригинала, а не на пересказ архитектуры.

Все ссылки вида `file.php:строка` — на файлы внутри
`D:\Projects\Destiny Sphere\old-sphere`. Кодировка исходников — Windows-1251.

**Границы документа.** Здесь описано устройство самого альянса (данные,
роли, жизненный цикл), правила «мира» между альянсами/игроками и устройство
глобального (межмирового) альянса. Детали боевой механики (расчёт боя,
защита, армии) сознательно не дублируются — см. `docs/mechanics-combat.md`;
здесь взаимодействие с боем описано только там, где оно завязано именно на
статус мира (проверка перед атакой, автоматический разрыв мира атакой).

Дополняет обзорный раздел 3.3 в `docs/game-engine.md`.

## 1. Термины

| Термин в коде | Значение |
|---|---|
| «Альянс» / `DE_Alliance` / `ds_alliance` | **Локальный** альянс — существует в рамках одного игрового мира (одной БД). Единица дипломатии внутри мира: у него есть пароль вступления, лидер, список участников. |
| «Глобальный альянс» / `DE_GlobalAlliance` / `ds_global_alliance` | Надмировая сущность в центральной БД (`dbId = 0`), объединяющая **по одному локальному альянсу в каждом существующем мире**. Управляется через отдельный веб-кабинет (`UC_*`), а не через Flash-клиент мира. |
| «Посольство» / `ALLIANCE_CONNECTOR` | Здание в игре. Наличие постройки в конкретном мире — необходимое условие, чтобы: (а) открылись вкладки альянса (`PN_AllianceManagement` и др.) вообще, и (б) чтобы игрока автоматически подключило к локальному альянсу его глобального альянса в этом мире. |
| «Мир» (`ds_peace_alliance`) | Соглашение о ненападении **между двумя локальными альянсами** одного мира, с обменным «залогом» в ресурсах/серебре. |
| «Приватный мир» (`ds_peace_user`) | Соглашение о ненападении **между двумя конкретными игроками**, без залога. Действует сильнее (приоритетнее), чем мир альянсов. |

## 2. Локальный альянс: модель данных

Таблица `ds_alliance` (через `DS_Alliance::GetByID`,
`DS/DS_Alliance.class.php:180-203`, и конструктор `DE_Alliance`,
`DE/DE_Alliance.class.php:50-81`):

| Поле | Тип/источник | Смысл |
|---|---|---|
| `id_alliance` | PK | Идентификатор в рамках БД мира |
| `alliancename` | string, 3–50 симв. | Полное название. Уникально в пределах мира (или глобально при создании глобального альянса, см. §7) |
| `alliancetag` | string | Короткий тег, **хранится в БД в квадратных скобках**: `[GODS]` (`UA_CreateAlliance.class.php:131`, `DS_Alliance.class.php:291`) |
| `joinpassword` | string, 3–30 симв. | Пароль вступления. Хранится в открытом виде (сравнение `==`, `UA_JoinAlliance.class.php:63`) |
| `members_amount` | int, денормализовано | Счётчик участников; используется для проверки лимита. Целостность проверяется/чинится джобом `MP_DBAllianceMembers` (см. §9) |
| `id_world` | FK | Мир, к которому привязан альянс |
| `id_global_alliance` | FK, nullable | Если > 0 — альянс является локальным «филиалом» глобального альянса (`DE_Alliance::isGlobal()`, `DE_Alliance.class.php:154-162`) |
| `id_religion` | FK, nullable | Религия альянса (используется в панелях, отдельная подсистема) |
| `creationdate` | timestamp | — |
| `image_url` | через `ds_alliance_has_image` (LEFT JOIN) | Аватар/картинка альянса |

Валидация полей при создании/смене (`VD/VD_AllianceName.class.php`,
`VD/VD_AllianceTag.class.php`, `VD/VD_AlliancePassword.class.php`):

| Поле | Запрещённые символы | Длина | Уникальность |
|---|---|---|---|
| Название | `' " `` < >` | 3–50 | Да, в пределах мира (`ALLIANCE_NAME_NOT_UNIQUE`) |
| Тег | разрешено только `[a-zA-Z0-9_#$*+!@]` (regex `^[...]+$`) | ≤ 8 | Да, в пределах мира (`ALLIANCE_TAG_NOT_UNIQUE`) |
| Пароль вступления | `` ' " ` ! @ # $ % ^ * ( ) ; : { } [ ] < > ? `` | 3–30 | нет |

Примечание: `UA_JoinAlliance::checkLocalParams` (`UA_JoinAlliance.class.php:41`)
и `UA_ChangeAllianceJoinpassword::checkLocalParams` (`:64`) продублировали
собственные regex для пароля, слегка отличающиеся от канонического

**Ролей/рангов в таблице участников нет отдельного enum'а с несколькими
уровнями** — см. §3.

## 3. Роли и права участников

В коде для локального альянса используется только одна выделенная роль —
**LEADER**, хранится как запись в `ds_userhasalliancestatus`
(`id_alliance`, `id_userinstance`, `id_status`), где `id_status`
ссылается на `ds_useralliancestatus.statusname = 'LEADER'`
(`DS_Alliance::IsUserLeader`, `DS_Alliance.class.php:430-451`;
назначение — `DS_Alliance::SetNewAllianceLeader`, `:145-173`).

По всей кодовой базе (проверено `grep -rn "statusname"`) **не встречается
никакого второго статуса** (офицер/заместитель/дипломат и т.п.) — таблица
`ds_useralliancestatus`, судя по всему, задумывалась расширяемой
(`localizedstatus`/`ds_localizedtextlanguage` для локализованного названия
статуса в `PN_AllianceManagement.class.php:29-41`), но фактически
использован только один статус. Все, кто не лидер, — обычные участники без
особых прав.

| Роль | Как определяется | Права |
|---|---|---|
| **LEADER** (лидер) | Запись в `ds_userhasalliancestatus` со статусом `LEADER`. Один на альянс (создаётся при `UA_CreateAlliance`, передаётся при `UA_ChangeAllianceLeader`, автоматически переходит следующему по дате вступления при выходе лидера — см. §4.3) | Исключение участников (`UA_ExpelAlliance`), смена пароля вступления (`UA_ChangeAllianceJoinpassword`), передача лидерства (`UA_ChangeAllianceLeader`), заключение/расторжение мира с другими альянсами (`UA_AlliancePeace`) |
| **MEMBER** (рядовой участник) | Запись в `ds_userhasalliance` без записи в `ds_userhasalliancestatus` | Выход из альянса, участие во внутриальянсовой переписке (`INTERNAL_ALLIANCE`/`EXTERNAL_ALLIANCE` message scopes, `UA_CreateAlliance.class.php:184-197`), торговля по alliance-scope (`ALLIANCE_TRADING`), защита сокомплексников (если разрешено настройкой мира) |

Проверка «лидер ли игрок» встроена прямо в SQL везде, где нужна авторизация
действия (`UA_ChangeAllianceLeader.class.php:86-98`,
`UA_ChangeAllianceJoinpassword.class.php:116-128`,
`UA_ExpelAlliance.class.php:44-50`) — отдельного механизма ACL/permissions
нет, каждая команда явно перепроверяет лидерство запросом к БД.

## 4. Жизненный цикл локального альянса

### 4.1. Создание — `UA_CreateAlliance`

Файл: `UA/UA_CreateAlliance.class.php`.

Предусловия (`checkAction`, `:77-117`):
- игрок не в вокейшн-моде и не под «энергощитом» новичка (иначе действие
  просто блокируется алертом);
- игрок **ещё не состоит ни в каком альянсе** (`ds_userhasalliance` пуст для
  него);
- имя/тег/пароль проходят `VD_Alliance::Validate` (см. §2).

Никакого минимального уровня игрока, очков рейтинга или иной «стоимости»
создания локального альянса в коде не найдено (в отличие от глобального —
см. §7, где создание формально платное, но реально не списывается).

`performAction` (`:120-283`) выполняет одной последовательностью:
1. `INSERT INTO ds_alliance (...) VALUES (..., members_amount = 1)`;
2. добавление создателя в `ds_userhasalliance`;
3. выдача ему статуса `LEADER` в `ds_userhasalliancestatus`;
4. открытие ему message-scope'ов `INTERNAL_ALLIANCE`/`EXTERNAL_ALLIANCE`;
5. простановка alliance-scope на торговлю (`ds_comballowedtradescope`) для
   всех его сот;
6. привязка к альянсу артефактов уровня `ALLIANCE` (артефактных бонусов),
   уже установленных на его зданиях;
7. снятие «щита новичка» (`clearNewbDefend`), если был.

### 4.2. Вступление — `UA_JoinAlliance`

Файл: `UA/UA_JoinAlliance.class.php`.

Модель — **по паролю**, без заявки/одобрения (в отличие от глобального
альянса, где подтверждение — явная опция). Проверки в `checkAction`
(`:50-81`):
- пароль совпадает с `alliance.joinpassword` (`INCORRECT_JOINPASSWORD`);
- `members_amount + 1 <= MAX_ALLIANCE_MEMBERS` (настройка мира,
  `ALLIANCE_HAS_MAX_MEMBERS`);
- закомментированная (не реализованная) проверка наличия посольства у
  вступающего (`:74-78` — мёртвый код, ничего не проверяет).

Дополнительная проверка в `performAction` (`:101-124`) — если игрок состоит
в **глобальном** альянсе, ему разрешено вступать только в локальный альянс,
привязанный к тому же `id_global_alliance` (иначе сообщение
`ALLIANCE_CAN_JOIN_ONLY_GLOBAL`); и наоборот — прямое вступление в чужой
глобальный альянс через игровой (не веб-) интерфейс запрещено
(`ALLIANCE_TRY_JOIN_GLOBAL`).

**Важно (баг оригинала):** сама проверка «состоит ли игрок в глобальном
альянсе» идёт через `DS_Alliance::IsUserInGlobslAlliance()`
(`UA_JoinAlliance.class.php:104`), а эта функция
(`DS_Alliance.class.php:86-89`) **начинается с `return false;` раньше
`assert`**, то есть весь код проверки — мёртвый, функция всегда возвращает
`false`. На практике это значит, что в исходной игре указанное выше
ограничение (можно вступать только в локальный альянс своего глобального)
**фактически не работает** ни в одну из сторон. См. §9.

При успешном вступлении: вызывается `ME_AddUserToAlliance::Add()` →
хранимая процедура `add_user_to_alliance(uiid, id_alliance)`; рассылается
письмо всем членам альянса; снимается «щит новичка».

### 4.3. Выход — `UA_LeaveAlliance`

Файл: `UA/UA_LeaveAlliance.class.php`.

- Заблокировано целиком настройкой мира `DISABLE_LEAVE_ALLIANCE`
  (`:65-70`).
- Выход из **локального филиала глобального альянса** через игровой
  интерфейс запрещён (`ALLIANCE_TRY_EXPELL_GLOBAL`, `:56-62`) — выйти из
  глобального альянса можно только через веб-кабинет (§7).
- `performAction` вызывает `ME_ExpelAlliance::Exec()` (см. ниже), затем:
  - **если уходит не лидер** — просто уменьшается состав;
  - **если уходит лидер и в альянсе остались другие участники** — новым
    лидером автоматически назначается участник **с самой ранней датой
    вступления** (`DS_Alliance::GetMemberExceptThis`, сортировка по
    `joindate`, `DS_Alliance.class.php:51-84` + `SetNewAllianceLeader`);
  - **если уходит лидер и он был последним** — альянс **распускается**
    (`DS_Alliance::DeleteAlliance`).

### 4.4. Исключение — `UA_ExpelAlliance`

Файл: `UA/UA_ExpelAlliance.class.php`. Доступно только лидеру
(`checkAction`, `:39-67`); нельзя исключить самого себя
(`Can't expel yourself`, `:60-64`); нельзя исключать из глобального
филиала через игровой интерфейс (`:90-96`, аналогично §4.3).

`ME_ExpelAlliance::Exec()` (`ME/ME_ExpelAlliance.class.php`) перед
собственно исключением:
1. отзывает армии исключаемого, стоящие в защите у сокомплексников по
   альянсу (`GetUserArmyOnDefend`);
2. отзывает армии сокомплексников, стоящие в защите у исключаемого
   (`GetArmyOnUserCombDefend`);
3. если армия в этот момент участвует в бою — не отзывает сразу, а ставит
   отложенное действие `END_BATTLE → RETURN_ARMY_FROM_DEFEND`
   (`ME_ArmyOccurrence`);
4. вызывает хранимую процедуру `expel_alliance(uiid, id_alliance)`.

То же самое (`ME_ExpelAlliance::Exec`) отрабатывает при добровольном
выходе и при выходе из глобального альянса — то есть **любое прекращение
членства рвёт активные ордера взаимной защиты внутри альянса**, это
общий побочный эффект, не специфичный только для исключения.

### 4.5. Смена лидера — `UA_ChangeAllianceLeader`

Только текущий лидер может назначить преемника; преемник обязан уже
состоять в этом альянсе (`UA_ChangeAllianceLeader.class.php:70-172`). Смена
реализована как `UPDATE ds_userhasalliancestatus SET id_userinstance = ...`
— то есть **старый лидер полностью теряет статус** (запись переходит, а не
добавляется новая), запасного/дополнительного лидера быть не может.

### 4.6. Смена пароля вступления — `UA_ChangeAllianceJoinpassword`

Только лидер; новый пароль проходит те же ограничения длины/символов, что и
при создании (§2). Никакого лимита частоты смены (кулдауна) в коде нет.

### 4.7. Роспуск/удаление

Два пути:
- **Естественный** — уход последнего/единственного лидера без преемника
  (§4.3), через `DS_Alliance::DeleteAlliance` (простой `DELETE FROM
  ds_alliance`, без каскадных проверок на стороне PHP — рассчитано на
  внешние FK/триггеры БД).
- **При полном удалении аккаунта игрока** (служебная операция, не игровая
  команда) — **не** `DU_DeleteAlliance`, вопреки тому, что подсказывает имя
  класса. `DU_DeleteAlliance` (`DU/DU_DeleteAlliance.class.php`)
  действительно существует и реализует на чистом PHP/SQL то же самое (удаляет
  `ds_userhasalliancestatus`/`ds_userhasalliance`, и если участников не
  осталось — сам альянс), но подключён только как элемент массива
  `deleteCompanents` в `DU_ControllerDeleteUserInstance::drop()`
  (`DU/DU_ControllerDeleteUserInstance.class.php:23-36`) — а `foreach`,
  который проходил бы по этому массиву и вызывал `Exec()` каждого компонента
  (`DU_DeleteAlliance` и ещё десяток похожих `DU_Delete*`), **целиком
  закомментирован** (`:59-68`). То есть класс объявлен и зарегистрирован в
  списке, но **никогда не выполняется**. Реальная логика полного удаления
  инстанса — единственный вызов хранимой процедуры БД `drop_uiid(uiid)`
  (`schema.sql:878-982` в дампе схемы игровой БД, см. §4.10), вызываемой как
  `SELECT drop_uiid(...)` из `DU_ControllerDeleteUserInstance.class.php:96`,
  `UC/UC_ExecDeleteInstance.class.php:182`, `DS/DS_RecieverWorld.class.php:336`
  (перенос аккаунта в другой мир) и `SU/SU_DeleteUserList.class.php:250`
  (массовое админ-удаление списком). `drop_uiid` сама реализует на PL/pgSQL
  куда более полную очистку (армии, события, археология, бои, артефакты,
  соты, колонии), и в частности вызывает `drop_from_aliance(uiid_v)` для
  альянсовой части — её поведение **не совпадает** с описанием выше:
  лидерство **переназначается** (см. §4.10). Это самостоятельная находка о
  дублирующейся архитектуре: PHP-реализация той же операции существует, но
  мертва; реально работающий путь — независимая DB-реализация, к которой
  PHP-слой обращается только как к чёрному ящику.

### 4.8. Диаграмма состояний членства игрока в локальном альянсе

```
[нет альянса] --CreateAlliance--> [участник, LEADER]
[нет альянса] --JoinAlliance(пароль верный, есть места)--> [участник, MEMBER]

[участник, MEMBER] --LeaveAlliance / ExpelAlliance--> [нет альянса]
[участник, LEADER] --LeaveAlliance, есть другие участники--> [нет альянса]
                                                (LEADER переходит старейшему по joindate)
[участник, LEADER] --LeaveAlliance, единственный участник--> [нет альянса]
                                                (альянс удаляется)
[участник, MEMBER] --ChangeAllianceLeader (текущим лидером)--> [участник, LEADER]
[участник, LEADER] --ChangeAllianceLeader--> [участник, MEMBER]
```

### 4.9. Целостность БД — `MP_DBAllianceMembers`

Периодический патч-джоб (`MP/MP_DBAllianceMembers.class.php`), три
независимые проверки/починки:

| Проверка | Чинит |
|---|---|
| `members_amount` не совпадает с реальным `count(*)` из `ds_userhasalliance` | `UPDATE ds_alliance SET members_amount = ...` |
| Альянс без единого участника («пустой альянс») | `DELETE FROM ds_alliance` |
| Альянс **без лидера**, но только если `id_global_alliance != NULL`* | Назначает лидером участника с минимальным `joindate` |

\* Условие в коде — `AND al.id_global_alliance != NULL` (`:77`, `:126`).
Это сравнение с `NULL` через `!=` в SQL **всегда ложно** (по стандарту
NULL-семантики), то есть на практике условие никогда не выполняется, и
починка «альянс без лидера» **не применяется ни к одному альянсу** —
похоже на баг (должно было быть `IS NOT NULL`). См. §9.

Это единственное место, подтверждающее, что после автопривязки к
глобальному альянсу локальный альянс **не обязан иметь лидера сразу** — см.
§7.3, где `ME_AddUserToAlliance::Add` не назначает статус при массовом
создании локальных филиалов.

### 4.10. Хранимые процедуры уровня БД за операциями §4.1–4.7

Ранее (см. старую редакцию §10 «Открытые вопросы») тела `add_user_to_alliance`
и `expel_alliance` не были доступны — сами процедуры находятся не в
`old-sphere`, а в дампе схемы игровой БД (`pg_dump --schema-only`,
`schema.sql`, лежит вне репозитория `old-sphere` и использован здесь только
для сверки, в сам код не входит). Ниже — что процедуры реально делают и как
это соотносится с PHP-слоем, описанным выше.

**`add_user_to_alliance(uiid_v, alliance_v)`** (`schema.sql:142-215`).
Единственная точка вызова — `DS_Alliance::AddUserToAlliance()`
(`DS_Alliance.class.php:306-318`, `SELECT add_user_to_alliance(...)`),
которую, в свою очередь, вызывает только `ME_AddUserToAlliance::Add()`
(`ME/ME_AddUserToAlliance.class.php:7`). Проверено `grep` по всей
`old-sphere` — других вызовов процедуры нет. `ME_AddUserToAlliance::Add()` —
общий примитив «добавить участника», используемый **во всех** путях
вступления в локальный альянс, упомянутых в этом документе: `UA_JoinAlliance`
(§4.2), автовступление через `EH_ConstructBuilding` (§7.3), создание и
обычное вступление в глобальный альянс через
`UC_ControlGlobalAllianceRegistration` (§7.3–7.4, два независимых места) и
принятие заявки лидером в `UC_ControlGlobalAllianceControlPanel` (§7.4).
Дублирования или альтернативного пути нет — это подтверждённый общий код, а
не параллельная реализация.

Тело процедуры одним SQL-вызовом, без промежуточных проверок, выполняет:

1. `UPDATE ds_alliance SET members_amount = members_amount + 1`;
2. `INSERT INTO ds_userhasalliance (id_alliance, id_userinstance, joindate) VALUES (..., now())`;
3. выдачу скоупа `INTERNAL_ALLIANCE` через `INSERT INTO ds_userallowedmessagescope`;
4. простановку `ALLIANCE_TRADING` в `ds_comballowedtradescope` для всех сот
   вступающего (с проверкой `NOT EXISTS`, чтобы не задублировать);
5. привязку уже установленных на его зданиях артефактов уровня `ALLIANCE` к
   альянсу (`ds_artefactattachedalliance`).

**Находка, ранее не задокументированная:** в отличие от `UA_CreateAlliance`
(§4.1, п. 4), которая выдаёт создателю **оба** скоупа —
`INTERNAL_ALLIANCE` и `EXTERNAL_ALLIANCE`, — эта процедура выдаёт
вступающему **только** `INTERNAL_ALLIANCE`. Рядовой участник, вступивший по
паролю (а не основавший альянс), никогда не получает право на
`EXTERNAL_ALLIANCE` — асимметрия между «основать» и «вступить». Проверки
лимита участников (`MAX_ALLIANCE_MEMBERS`, §8) на уровне самой процедуры
**нет** — это подтверждает предположение из старой версии §10: лимит
проверяется только на PHP-уровне, в `UA_JoinAlliance::checkAction` (§4.2),
**до** вызова процедуры; сама процедура не защищена от гонки — теоретически
два одновременных вступления, оба прошедших PHP-проверку лимита до того, как
первое успело увеличить `members_amount`, могли превысить
`MAX_ALLIANCE_MEMBERS`. Не проверено, случалось ли это на практике.

**`expel_alliance(uiid_v, alliance_v)`** (`schema.sql:1478-1533`). Единственная
точка вызова — `DS_Alliance::ExpelAlliance()` (`DS_Alliance.class.php:420-428`)
→ `ME_ExpelAlliance::Exec()` (`ME/ME_ExpelAlliance.class.php:47`) —
используется симметрично при выходе (§4.3), исключении (§4.4) и исключении
лидером глобального альянса (§7.4), как и было описано выше. Полностью
зеркальна `add_user_to_alliance` плюс явная очистка: `members_amount - 1`;
`DELETE FROM ds_userhasalliancestatus` (снимает `LEADER`, если был);
`DELETE FROM ds_userhasalliance`; `DELETE FROM ds_userallowedmessagescope` для
**обоих** скоупов сразу — `INTERNAL_ALLIANCE` и `EXTERNAL_ALLIANCE`
(несимметрично п. 3 у `add_user_to_alliance`, которая выдаёт только первый —
но безвредно, `DELETE` по не существующей записи — no-op); отвязка
артефактов со всех зданий игрока (`ds_artefactattachedalliance`); снятие
`ALLIANCE_TRADING` со всех его сот. Подтверждает вторую часть предположения
из старой версии §10 — никакой скрытой бизнес-логики сверх видимого на
PHP-уровне нет.

**`drop_from_aliance(uiid_v)`** (`schema.sql:790-851`; опечатка в имени —
оригинальная, из исходной схемы). **Не вызывается напрямую ни из одного
PHP-класса** (проверено `grep -rn` по всей `old-sphere` — ни одного
совпадения). Единственный вызов — `PERFORM drop_from_aliance(uiid_v);`
изнутри другой хранимой процедуры, `drop_uiid(uiid_v)` (`schema.sql:954`,
сама `drop_uiid` — `schema.sql:878-982`), которая на уровне БД реализует
полное удаление игрового инстанса (армии, события, археология, бои,
артефакты, соты, колонии, и в конце — `DELETE FROM ds_userinstance`). Пути
вызова `drop_uiid` из PHP — см. §4.7.

Логика `drop_from_aliance` **не эквивалентна** `expel_alliance` — это третий,
отдельный вариант ухода из альянса, специфичный именно для полного удаления
аккаунта:

- если удаляемый — единственный участник альянса → `DELETE FROM ds_alliance`
  (каскад по FK `ds_userhasalliance.id_alliance → ds_alliance.id_alliance ON
  DELETE CASCADE`, `schema.sql:35927-35928`, сам подчищает членство);
- если участников больше и удаляемый — **лидер** → лидерство переходит
  самому раннему по `joindate` из оставшихся (`ORDER BY joindate LIMIT 1`)
  через `UPDATE ds_userhasalliancestatus SET id_userinstance = <новый лидер>
  WHERE id_userinstance = uiid_v` — то есть **лидерство переназначается**, по
  тому же правилу, что и в `UA_LeaveAlliance` (§4.3, «самая ранняя дата
  вступления»);
- если участников больше и удаляемый — рядовой участник → **процедура не
  делает вообще ничего** для строки `ds_userhasalliance` удаляемого и не
  уменьшает `members_amount`.

Последний пункт — не самостоятельный баг, а зависимость от вызывающей
стороны: `drop_uiid`, вызвав `drop_from_aliance` в середине своего
выполнения, **в конце** делает `DELETE FROM ds_userinstance WHERE
id_userinstance = uiid_v` (`schema.sql:978`); у
`ds_userhasalliance.id_userinstance` есть FK `ON DELETE CASCADE` на
`ds_userinstance.id_userinstance` (`schema.sql:35895-35896`) — строка
членства всё равно исчезнет каскадом чуть позже в той же транзакции. **Но
`members_amount` этот каскад не трогает** — счётчик в `ds_alliance` остаётся
завышенным на единицу после каждого удаления через `drop_uiid` рядового
(не единственного и не лидера) участника — то есть после переноса аккаунта
в другой мир (`DS_RecieverWorld`) или массового админ-удаления
(`SU_DeleteUserList`). Похоже, что именно для починки такого дрейфа и
существует первая проверка в `MP_DBAllianceMembers` (§4.9) — раньше в
документе не было прослежено, откуда конкретно берётся рассинхронизация
`members_amount`; теперь источник найден.

**`insert_alliance_leader()`** — триггер `BEFORE INSERT ON
ds_userhasalliancestatus` (тело — `schema.sql:1586-1613`, привязка —
`CREATE TRIGGER ds_userhasalliancestatus_tr ... EXECUTE PROCEDURE
insert_alliance_leader()`, `schema.sql:31854`). Не вызывается явно ни из
PHP, ни из другой процедуры — Postgres исполняет его сам при `INSERT` в
`ds_userhasalliancestatus`. Логика: если для `NEW.id_alliance` уже есть
строка (то есть у альянса уже есть лидер), триггер **превращает `INSERT` в
`UPDATE`** (`UPDATE ... SET id_userinstance = NEW.id_userinstance WHERE
id_alliance = NEW.id_alliance`) и возвращает `NULL`, что в `BEFORE`-триггере
отменяет исходную вставку; если строки ещё нет — возвращает `NEW`, вставка
проходит как обычно.

Это DB-уровневый инвариант «не больше одного `LEADER` на альянс»,
независимый от PHP-слоя. Он объясняет, *почему* безопасно устроена смена
лидера в §4.5 («старый лидер полностью теряет статус, запись переходит, а не
добавляется новая») — даже если бы какой-то код (текущий или будущий)
попытался **вставить** вторую строку `LEADER` для уже существующего лидера
вместо `UPDATE`, триггер на уровне БД всё равно свёл бы это к тому же
результату. Единственная точка, где это действительно имеет значение —
изначальная выдача статуса при `UA_CreateAlliance` (§4.1, п. 3): в этот
момент строки для альянса ещё нет, `uiid_v` внутри триггера — `NULL`,
поэтому вставка проходит без вмешательства триггера.

## 5. Мир между альянсами (Alliance Peace)

Таблица `ds_peace_alliance` (доступ через `DS/DS_PeaceAlliance.class.php`),
действие — `UA/UA_AlliancePeace.class.php`, UI — `PN/PN_PeaceAlliance.class.php`,
фоновая уборка истёкших — `MP/MP_AlliancePeace.class.php`.

### 5.1. Модель данных

Пара альянсов кодируется как «слот 1»/«слот 2»: у альянса с **меньшим**
`id_alliance` всегда слот `1`, у альянса с большим — слот `2`
(`UA_AlliancePeace.class.php:53-60`, `DS_PeaceAlliance::getAlliancePeace`,
`:89-102`). Отсюда пары полей `*_1`/`*_2`:

| Поле | Смысл |
|---|---|
| `id_alliance_1`, `id_alliance_2` | стороны соглашения (1 = меньший id) |
| `status` | см. таблицу состояний ниже |
| `who_offer` | `id_alliance`, предложивший мир изначально |
| `peace_date` | дата предложения |
| `peace_duration` | срок мира в днях — **берётся из XML-запроса клиента без серверной валидации** против `ALLIANCE_PEACE_DURATION_MAX` (см. §9) |
| `peace_end_date` | дата истечения — проставляется **только в момент подтверждения** (`confirmPeace`), как `NOW() + peace_duration days` |
| `id_comb_1`, `id_comb_2` | сота, с которой был внесён залог каждой стороны (нужна, чтобы вернуть ресурсы туда же) |
| `price_prodium_{1,2}`, `price_kad_{1,2}`, `price_nano_{1,2}`, `price_food_{1,2}`, `price_energy_{1,2}`, `price_silver_{1,2}` | залог каждой стороны — 5 видов ресурсов сот + серебро (реальная валюта, через `UC_PaymentServiceMoneyOperation`, отдельно от ресурсов сот) |

### 5.2. Состояния и переходы

`status` в `ds_peace_alliance` (интерпретация по `UA_AlliancePeace.class.php`
и `PN_PeaceAlliance::checkAlliance`, `:175-219`):

| `status` | Значение | Кто мог инициировать переход |
|---|---|---|
| `0` | Предложен, ожидает подтверждения другой стороной | `who_offer` — сторона, приславшая оффер |
| `1` | Мир действует (`peace_end_date` = `peace_date` + `peace_duration` дней) | Другая сторона (`confirmPeace`) |
| `4` | Одна из сторон запросила **досрочное** расторжение — конкретно та, чей `id_alliance == who_offer` исходного мира | любая сторона (`terminatePeace`) |
| `5` | То же, но инициатор — сторона, которая **не** была `who_offer` | любая сторона (`terminatePeace`) |
| — (запись удаляется) | Мир расторгнут/отклонён/истёк | см. переходы ниже |

Переходы (`status`-параметр UA-команды → действие в БД,
`UA_AlliancePeace.class.php:62-274`):

| Действие клиента (`status` в запросе) | Условие | Эффект |
|---|---|---|
| `setPeace` | оффера ещё нет | `INSERT` со `status=0`; **списывается залог только у предлагающей стороны** (её `price_*_my_n`, `sign=-1`, без налога) |
| `confirmPeace` | запись существует, `status=0` | `status → 1`, `peace_end_date = NOW()+duration`; списывается залог **второй** стороны; отзываются все армии, находящиеся во «полёте»/атаке между членами обоих альянсов (`DS_Peace::StopArmy` для каждой пары участников, `:157-177`) |
| `declinePeace` | запись существует, `status=0`, отклоняет **получатель** оффера | запись удаляется; залог оффёрера **возвращается полностью, без налога** (`changeRes(..., +1, 0)`) |
| `cancelPeace` | запись существует, `status=0`, отменяет **сам оффёрер** | то же: удаление + полный возврат без налога |
| `terminatePeace` | запись существует, `status=1` | `status → 4` или `5` (см. выше) — это только заявка, мир пока действует |
| `declineTerminatePeace` | `status ∈ {4,5}` | `status → 1` (запрос на расторжение отклонён, мир продолжается) |
| `cancelTerminate` | `status ∈ {4,5}` | то же: `status → 1` (инициатор сам отозвал заявку на расторжение) |
| `confirmTerminatePeace` | `status ∈ {4,5}`, подтверждает **другая** сторона | запись удаляется; **обеим сторонам возвращается их собственный залог, с налогом** (`changeRes(..., +1)`, `getTax` по умолчанию `1`) |

Естественное истечение (не UA-команда, а ленивая проверка при каждом
открытии панели `PN_PeaceAlliance::checkAlliance`, `:184-198`, и в фоновом
патче `MP_AlliancePeace::patch`, `MP_AlliancePeace.class.php:10-32`): если
`status > 0` и текущее время `>` `peace_end_date`, мир удаляется, **обеим
сторонам возвращается их собственный (не чужой) залог, с налогом**.

### 5.3. Формула налога и денег

`ALLIANCE_PEACE_TAX` — процент (0–100), настройка мира. Официальная
справочная страница сайта (`https://destinysphere.ru/ds/help/?name=INFO_GAME_MAIN`,
раздел 6.2 «Перемирия», проверено 2026) называет конкретное значение —
**«Налог на заключение во всех мирах составляет 11%»** — то есть, судя по
формулировке источника, `ALLIANCE_PEACE_TAX` в реальности не варьируется
между мирами, а имеет одно и то же значение 11% везде. Там же указан
**максимальный срок перемирия — 365 дней**, что, вероятно, соответствует
атрибуту `maxdays` корневого узла `<alliancepeace>` в клиентском протоколе
(см. `docs/client-economy-social-ui.md`, парсер `alliancepeace_menu_parser`).

> ⚠️ **Расхождение с прямым запросом к живой БД (источник: БД,
> live-запрос, 2026-09-02) — портальное «11% во всех мирах» не
> подтверждается.** Точные значения `ALLIANCE_PEACE_TAX` на 4 живых мирах:
>
> | Мир | `ALLIANCE_PEACE_TAX` |
> |---|---:|
> | Чёрная дыра | 0% |
> | Сфера Парусов | 1% |
> | Сфера Змееносца | 10% |
> | Сфера Гончих Псов (турнирный) | 10% |
>
> Ни одно из 4 значений не равно заявленным порталом 11% — притом что
> разброс (0-10%) явно показывает, что налог **variable по мирам**, вопреки
> буквальной формулировке справки «во всех мирах составляет 11%». Ближе
> всего к «универсальному» — глобальное значение по умолчанию в каталоге
> модификаторов (`ds_gamemodifiertemplate.value = 10` для
> `ALLIANCE_PEACE_TAX`) — то есть похоже, что справка портала либо устарела
> (когда-то дефолт/типичное значение действительно было 11%, затем
> изменилось на 10% или было явно переопределено по мирам), либо просто
> неточна как обобщение. Не установлено, какая из этих версий верна — но
> сам факт расхождения (0/1/10/10% в реальных БД против заявленных
> портал-справкой 11%) задокументирован явно, а не молча проигнорирован.

```
tax_multiplier = 1 - 0.01 * ALLIANCE_PEACE_TAX
```

- Списание залога при оффере/подтверждении: **без налога** (полная сумма).
- Возврат при отказе/отмене **до** подтверждения (declinePeace/cancelPeace):
  **без налога**, `getTax=0` явно передан (`UA_AlliancePeace.class.php:187`,
  `:203`).
- Возврат при истечении срока, при `confirmTerminatePeace`, и «своя» доля
  при разрыве атакой — **с налогом** (`tax_multiplier` применяется к каждому
  из 5 ресурсов сот; к серебру — тоже, через
  `UC_PaymentServiceMoneyOperation::EnterMoney`).

Формула по каждому ресурсу при возврате (`UA_AlliancePeace::changeRes`,
`:285-314`):

```
Δresource = sign * floor(price_resource_slotN * tax_multiplier)
```
где `sign = -1` при списании (оффер/подтверждение), `sign = +1` при
возврате.

### 5.4. Разрыв мира атакой (связь с боевой механикой)

Реализовано в `UA/UA_Attack.class.php:335-425` (не дублирую детали расчёта
самого боя — см. `docs/mechanics-combat.md`), но именно правило разрыва
мира — часть этой подсистемы:

1. Личный мир проверяется **раньше** и **имеет приоритет** над мирами
   альянсов (`:293` — комментарий в коде: «личный мир сильнее»). Если
   между атакующим и защищающимся есть активный приватный мир — атака
   блокируется целиком, без возможности «подтвердить» (см. §6).
2. Если приватного мира нет, но атакующий и защищающийся состоят в
   альянсах, между которыми есть **активный** мир альянсов
   (`status > 0` и `peace_end_date` в будущем):
   - **первый клик по атаке без `confirm=1`** — сервер не выполняет атаку,
     а возвращает клиенту XML-подтверждение с предупреждением
     (`ATTACK_ON_PEACE_USER_CONFIRM`) и готовой командой повтора с
     `confirm="1"` (`:349-366`);
   - **повторный запрос с `confirm=1`** — атака выполняется, и **мир
     разрывается немедленно и односторонне**, без согласия второй стороны:
     - обоим лидерам и всем участникам обоих альянсов рассылаются
       уведомления (`ATTACK_ON_PEACE_USER_SUBJECT`/`_MSG1`/`_MSG2`,
       `ATTACK_ON_PEACE_USER_BREAK_GLOBAL_*`);
     - запись мира удаляется (`DS_PeaceAlliance::deletePeace`);
     - **весь залог — и свой, и атакующей стороны — целиком уходит
       атакованной (пострадавшей) стороне**, с налогом
       `ALLIANCE_PEACE_TAX` (`UA_Attack.class.php:410-420`): доли обеих
       сторон складываются (`price_X_he += price_X_my`) и зачисляются на
       комб лидера атакованного альянса. То есть нападающий **теряет свой
       залог полностью** — это штраф за разрыв мира атакой, отличный от
       обычного «мирного» расторжения (§5.2), где каждая сторона получает
       обратно только своё.
   - Условие для блокировки атаки — `status > 0` (то есть блокирует **и**
     активный мир `status=1`, **и** мир в состоянии «ожидает расторжения»
     `status ∈ {4,5}`) — иными словами, пока вторая сторона не подтвердила
     мирное расторжение (`confirmTerminatePeace`) или мир не истёк
     естественно, атаковать без штрафного «разрыва боем» нельзя.

## 6. Приватный мир (Private Peace) между игроками

Таблица `ds_peace_user` (`DS/DS_Peace.class.php`), действие —
`UA/UA_PrivatePeace.class.php`, UI — `PN/PN_PeacePrivate.class.php`.

### 6.1. Отличия от мира альянсов

| | Мир альянсов | Приватный мир |
|---|---|---|
| Стороны | два альянса целиком (действует на всех участников обоих) | два конкретных игрока |
| Залог/цена | да, 5 ресурсов + серебро, с обеих сторон | **нет** — просто флаг |
| Кто инициирует | лидер альянса (`UA_AlliancePeace` вызывается из панели, доступной по проверке лидерства на уровне UI, но серверной проверки роли в `checkAction` метода нет — `checkAction()` в `UA_AlliancePeace.class.php:35-38` **всегда возвращает `true`**, реальная защита только в том, что панель показывает кнопки лидеру — см. §9) | любой игрок лично, за себя |
| Приоритет при атаке | проверяется вторым | проверяется **первым**, сильнее |
| Разрыв атакой с подтверждением | да, немедленно, штрафной | **нет** — атака при активном приватном мире **блокируется безусловно**, обхода через «confirm» не предусмотрено |
| Способ прекратить | `terminatePeace`→`confirmTerminatePeace` (требует согласия второй стороны) либо истечение срока | `LIST_REQUEST_REJECT_PEACE` — расторжение с отложенным вступлением в силу (см. ниже), согласие второй стороны **не требуется** |
| Симметрия сторон в БД | слот 1/2 по меньшему `id_alliance` | слот 1/2 по меньшему `id_userinstance` (`DS_Peace::addPeace`, `:66-88`) |

### 6.2. Состояния и переходы (`ds_peace_user.status`)

| `status` | Значение |
|---|---|
| `0` | Предложен, ждёт подтверждения |
| `1` | Мир действует |
| запись с `peace_end_date` (`psec`) заполненным, `status=0` | Мир **расторгнут**, но ещё действует отложенная задержка перед тем, как разрешить атаку заново |

Действия (`UA_PrivatePeace::performAction`, `:126-201`,
`DS_Peace::SetPeace`, `DS_Peace.class.php:104-179`):

| Действие (`reason`) | Условие | Эффект |
|---|---|---|
| `PRIVATEPEACE_REQUEST` | нет существующей записи между игроками | `INSERT` со `status=0` |
| `PEACE_CONFIRMATION` | запись есть, `status=0` | `status → 1`; **отзываются все армии в полёте в обе стороны** между этими двумя игроками (`DS_Peace::StopArmy` дважды) |
| `PEACE_REJECTING` | запись есть, `status=0` | запись удаляется (получатель отклонил оффер) |
| `LIST_REQUEST_CANCEL_REQUEST` | запись есть, `status=0` | запись удаляется (сам оффёрер отозвал предложение) |
| `LIST_REQUEST_REJECT_PEACE` | запись есть, `status=1`, `peace_end_date` ещё не проставлен | **не удаляет** запись сразу: `status → 0`, `peace_end_date = NOW() + BATTLE_PEACE_DELAY * TURN_TIME минут` — отложенное расторжение (см. ниже) |

**Задержка перед новой атакой.** При расторжении действующего мира
(`LIST_REQUEST_REJECT_PEACE`) стороны не могут атаковать друг друга ещё
`BATTLE_PEACE_DELAY` ходов (`TURN_TIME` минут за ход, настройки мира,
`DS_Peace.class.php:141-153`). До истечения этого времени `UA_Attack`
показывает алерт `PRIVATE_PEACE_CANNOT_ATTACK2` с датой, когда можно будет
атаковать (`UA_Attack.class.php:318-327`); после истечения — атака проходит
как обычно, специального «штрафа» (в отличие от мира альянсов) нет, потому
что залога изначально не было.

Фоновая уборка полностью истёкших приватных миров (когда
`peace_end_date < NOW()`) — `MP_CheckPeace::patch`
(`MP/MP_CheckPeace.class.php:10-16`), простой `DELETE`.

## 7. Глобальный (межмировой) альянс

Отдельная сущность в центральной БД (`dbId=0`), объединяющая **до одного
локального альянса в каждом существующем мире** под общим руководством.
Управляется не из Flash-клиента конкретного мира, а из отдельного
веб-кабинета (`UC_ControlGlobalAlliance*`).

### 7.1. Модель данных (`ds_global_alliance`, `DE_GlobalAlliance`,
`DE/DE_GlobalAlliance.class.php:1-204`)

| Поле | Смысл |
|---|---|
| `id_global_alliance` | PK |
| `alliance_name` | полное название, уникально **среди всех глобальных альянсов и среди названий локальных альянсов во всех мирах** (`VD_Alliance::_validGlobal`, см. §9 про баг) |
| `short_name` | тег |
| `id_leader` | `id_user` лидера (единственный, не список) |
| `join_password` | пароль вступления — используется двояко: и для вступления рядовых игроков (если включено), и **как пароль подтверждения личности лидера** при чувствительных операциях (смена лидера, роспуск, смена названия, смена аватара — везде требуется повторный ввод текущего `join_password`) |
| `join_payment` | сумма (в игровой валюте), которую годится взимать при вступлении, 0 ≤ x < `GLOBAL_ALLIANCE_MAX_JOIN_PAYMENT` |
| `join_confirmation` | boolean — требуется ли подтверждение лидера при вступлении (иначе вступление свободное по паролю/без пароля) |
| `creation_date` | — |

Вспомогательные таблицы (по обращениям в `DS_GlobalAlliance`):

| Таблица | Назначение |
|---|---|
| `ds_global_alliance_users` | членство: `(id_global_alliance, id_user)` — по **пользователю** (аккаунту), а не по `userinstance` конкретного мира |
| `ds_global_alliance_user_black_list` | чёрный список: `(id_global_alliance, id_user, comments)` — заблокированным нельзя (по логике) вступить повторно после исключения-с-ЧС |
| `ds_alliance_new_members` | очередь заявок на вступление (ожидание подтверждения лидера): `(id_global_alliance, id_user, comments)` |
| `ds_alliance` (per-world) | `id_global_alliance` FK связывает локальный альянс мира с глобальным (по одному на мир) |
| `ds_alliance_has_image` | аватар — хранится **отдельно в каждой БД мира** на локальном `id_alliance`, при обновлении рассылается циклом по всем мирам (`DS_GlobalAlliance::AddAvatar`/`UpdateAvatar`, `:1415-1485`) |

### 7.2. Роли

Определяются на лету функцией `UC_LogicGetPageControllerForUser::Get()`
(`UC/UC_LogicGetPageControllerForUser.class.php`), без отдельного
enum-поля:

| Роль | Условие | Панель |
|---|---|---|
| **LEADER** | `user.id_user == ds_global_alliance.id_leader` | `UC_ControlGlobalAllianceControlPanel` |
| **MEMBER** | есть запись в `ds_global_alliance_users`, но не лидер | `UC_ControlGlobalAllianceMemberPanel` |
| (никто) | нет ни записи членства, ни лидерства | `UC_ControlGlobalAllianceRegistration` (создание/вступление) |

В диспетчере (`UC_ControlGlobalAlliance.class.php:32-34`) заготовлена ветка
`ASSISTANT_CONTROL_PANEL` (третья, промежуточная роль — «заместитель»), но
она **пустая** (`break;` без реализации) — то есть в коде запланирована, но
не реализована. Полезно как ориентир при проектировании ремастера, но не
как рабочая механика оригинала.

### 7.3. Здание `ALLIANCE_CONNECTOR` как мост локальный ↔ глобальный

`EH/EH_ConstructBuilding.class.php:281-323` — при **завершении постройки**
этого здания в конкретном мире:

1. Проверяется, состоит ли строящий игрок в каком-то глобальном альянсе
   (`DS_GlobalAlliance::GetUserGlobalAlliance`).
2. Если да — по `(id_global_alliance, id_world)` находится локальный
   альянс-филиал в этом мире (`ds_alliance.id_global_alliance`).
3. Игрок автоматически добавляется в этот локальный альянс
   (`ME_AddUserToAlliance::Add`) — **без проверки пароля, без выбора, без
   возможности отказаться**.
4. Если игрок не состоит в глобальном альянсе — здание просто
   существует и открывает доступ к обычным вкладкам альянса
   (`PN_AllianceManagement`, `PN_AllianceOverview`, `PN_AllianceSettings`,
   `PN_PeaceAlliance`, `PN_PeacePrivate` — у всех в шапке файла комментарий
   «закладка здания ALLIANCE_CONNECTOR»), никакого автовступления не
   происходит.

Также используется `DS_GlobalAlliance::HaseUserEmbassy()`
(`DS_GlobalAlliance.class.php:377-405`) — проверка «есть ли у игрока в этом
мире здание ALLIANCE_CONNECTOR» — **перед** добавлением игрока в локальный
филиал при обычном вступлении в глобальный альянс через веб-кабинет
(`UC_ControlGlobalAllianceRegistration::_joinUserToAlliance`, `:636-667`):
если посольства нет — игрок остаётся членом глобального альянса
(`ds_global_alliance_users`), но **не** попадает в локальный альянс этого
конкретного мира, пока не построит посольство (тогда сработает пункт выше).

**Несимметрично:** при **создании** глобального альянса
(`_addLocalAlliances`, `UC_ControlGlobalAllianceRegistration.class.php:533-552`)
создатель добавляется во **все** только что созданные локальные филиалы
без проверки посольства — проверка `HaseUserEmbassy` есть только в ветке
обычного вступления, не в ветке создания. Похоже на несогласованность
оригинала, см. §9.

### 7.4. Жизненный цикл

**Создание** (`UC_ControlGlobalAllianceRegistration::_createAlliance`,
`:437-495`):
- предусловие — у игрока есть хотя бы один `userinstance` в каком-либо
  мире (`HasUserInstance`) и он ещё не в другом альянсе;
- имя/тег/пароль — та же валидация `VD_Alliance`, но с `worldId=0` (значит,
  проверяется уникальность **по всем мирам сразу**, см. §2 и §9);
- по факту создания **автоматически создаётся локальный альянс-филиал в
  каждом существующем мире** (`InsertLocalAlliance`, цикл по
  `GetWordList()`), даже там, где у создателя нет персонажа;
- стоимость создания — настройки `GLOBAL_ALLIANCE_CREATION_COST` /
  `_COST_CREDITS` показываются в UI, но **фактическое списание денег
  закомментировано** (`UC_GlobalAllianceMoneyOperations::GetMoneyForOperation`,
  `:446`) — см. §9;
- есть необязательная загрузка аватара (ровно 60×60 px).

**Вступление** (`_joinAlliance`, `:554-634`):
- нельзя вступить, если уже есть активная заявка в очереди
  (`ds_alliance_new_members`);
- если задан пароль в запросе — сверяется с `join_password`;
- если `join_confirmation = true` — заявка уходит в очередь
  (`ds_alliance_new_members`), ждёт решения лидера;
- если `join_confirmation = false` — игрок вступает немедленно:
  добавляется в `ds_global_alliance_users`, и в локальные альянсы всех
  миров, где у него есть персонаж **и** посольство (см. §7.3); всем
  участникам альянса во всех мирах рассылается уведомление.
- список ожидающих подтверждения (заявок) и решение по ним — на панели
  лидера, `_joinControl` (`UC_ControlGlobalAllianceControlPanel.class.php:438-537`):
  кнопка **«принять»** — заявка удаляется из очереди, игрок вступает
  (как в ветке без подтверждения выше); кнопка **«отклонить»** — заявка
  удаляется, опционально (`decline_to_black_list`) игрок сразу заносится в
  чёрный список.

**Исключение лидером** (`_expelMembers` → `_expelUser`,
`:307-437`): для каждого выбранного игрока — по каждому миру находится его
`userinstance` и локальный альянс, вызывается `ME_ExpelAlliance::Exec`
(те же побочные эффекты с отзывом армий, что и при обычном исключении,
§4.4), затем убирается запись из `ds_global_alliance_users`. Опционально
(`expelWithBL`) — сразу заносится в чёрный список с комментарием (лимит
600 символов на комментарий).

**Выход по собственной инициативе** (`UC_ControlGlobalAllianceMemberPanel::_leaveGlobalAlliance`,
`:267-306`) — то же самое, но инициатор — сам игрок; лидер выйти таким
способом не может (для лидера нет этой команды в его панели — у него
только «распустить альянс» или «передать лидерство»).

**Смена лидера** (`_changeSettings`, `case 'change_leader'`,
`ControlPanel.class.php:749-800`) — только текущим лидером, требует
повторного ввода `join_password`; новый лидер должен существовать и уже
быть участником этого глобального альянса. После смены — уведомление всем
участникам, и вызывающий переключается на `MemberPanel`.

**Роспуск** (`case 'delete_alliance'`, `:849-895`) — только лидером, тоже
требует `join_password`; уведомляет всех участников; исключает всех
участников из всех локальных альянсов во всех мирах
(`_expelUser` по каждому); удаляет все локальные альянсы-филиалы
(`DeleteLocalAlliance`, по каждому миру); удаляет запись из
`ds_global_alliance`, а также связанные `ds_alliance_new_members` и
`ds_global_alliance_user_black_list`.

**Переименование** (`case 'change_alliance_name'`, `:922-1005`) — только
лидером, пароль обязателен; новое имя/тег проверяются на уникальность
среди **всех** глобальных альянсов и среди локальных альянсов всех миров
(`CheckUniqAllianceName`/`CheckUniqAllianceTag`); стоимость
(`GLOBAL_ALLIANCE_RENAME_COST`) показывается, но списание **закомментировано**.

**Смена аватара** (`case 'change_avatar'`) — макс. 100×100 px, пароль
обязателен, стоимость (`GLOBAL_ALLIANCE_CHANGE_AVATAR_COST`) показывается,
но списание тоже закомментировано (`:1057`).

### 7.5. Прочие возможности панели лидера/участника

Помимо вступления/исключения, `UC_ControlGlobalAllianceControlPanel`
(лидер) и `UC_ControlGlobalAllianceMemberPanel` (участник) дают:
рассылку сообщений всем участникам или выбранным игрокам
(`sent_message`/`send_message_to_users`), просмотр статистики по мирам
(`world_stat`, суммирует очки/бонусы от артефактов, привязанных к
альянсу — `GetWordStat`/`GetBonusByWorlds`), просмотр списка чёрного
списка и снятие из него (`black_list`/`del_user_from_bl`, только у лидера).

## 8. Лимиты и настройки мира, влияющие на альянсы/мир

## 9. Известные несоответствия и дефекты оригинального кода

Важно для ремастера — эти пункты либо стоит **не** повторять как баг, либо
явно решить, как их «исправленная» версия должна себя вести:

1. **`DS_Alliance::IsUserInGlobslAlliance()` — мёртвый код**
   (`DS_Alliance.class.php:86-89`, `return false;` до `assert`). Из-за
   этого проверка «глобальный альянс-участник может вступать только в
   локальный альянс своего же глобального объединения»
   (`UA_JoinAlliance.class.php:104-124`) **не работает** — участник
   глобального альянса в реальности мог свободно вступать в произвольный
   локальный альянс через игровой клиент, если знал пароль.
2. **`VD_Alliance::_validGlobal()` вызывает несуществующий метод**
   (`DS_GlobalAlliance::GetByTag()`, закомментирован,
   `DS_GlobalAlliance.class.php:182-205`, вызов —
   `VD_Alliance.class.php:36`). При создании глобального альянса (`worldId
   == 0`) валидация тега неизбежно упадёт с PHP fatal error «call to
   undefined method». В сочетании с рубильником `GLOBAL_ALLIANCE_ACTIVE`
   (§8) это сильный сигнал, что **функциональность создания глобальных
   альянсов не была доведена до рабочего состояния** в этом снэпшоте кода.
3. **Монетизация глобальных альянсов — везде закомментирована.**
   Создание, вступление, переименование, смена аватара показывают
   стоимость в UI, но фактическое списание денег
   (`UC_GlobalAllianceMoneyOperations::GetMoneyForOperation`/`CheckMoney*`)
   закомментировано во всех перечисленных местах (см. точные строки в §7.4
   и §8). При ремастере — решить осознанно, включать ли расход ресурсов.
4. **`MP_DBAllianceMembers` — сравнение с `NULL` через `!=`**
   (`:77`, `:126`, `AND al.id_global_alliance != NULL`) — в SQL это
   условие никогда не истинно, то есть починка «альянс без лидера»
   фактически не запускается для локальных филиалов глобальных альянсов
   (хотя именно они чаще всего остаются без лидера — см. пункт 5).
5. **Локальные филиалы глобального альянса могут не иметь лидера.**
   При автосоздании локального альянса под глобальный
   (`InsertLocalAlliance` + `ME_AddUserToAlliance::Add`, §7.3/7.4) статус
   `LEADER` **не проставляется** ни создателю, ни кому-либо ещё — в отличие
   от обычного `UA_CreateAlliance`, где лидерство выдаётся явным `INSERT`
   на шаге создания (§4.1). Из-за бага в пункте 4 это может оставлять
   такие альянсы без лидера сколь угодно долго (влияет на §3 — все
   операции, требующие лидерства, окажутся никому не доступны в этом
   локальном альянсе, пока кто-то не станет лидером иным путём).
6. **`peace_duration` мира альянсов не валидируется на сервере**
   (`UA_AlliancePeace.class.php:75`, значение берётся из XML-атрибута
   `time` напрямую) — `ALLIANCE_PEACE_DURATION_MAX` используется только как
   подсказка клиенту (§5.1, §8). Теоретически клиент мог отправить любое
   значение.
7. **`UA_AlliancePeace::checkAction()` всегда возвращает `true`**
   (`:35-38`) — авторизация «только лидер может предлагать/принимать/
   расторгать мир» нигде не проверяется на сервере в этом классе; судя по
   всему, полагались на то, что кнопки в UI показываются только лидеру
   (`PN_PeaceAlliance.class.php:82`, `viewdata` = `IsUserLeader`). Это
   означает, что при прямом вызове action (не через штатный UI) рядовой
   участник мог, вероятно, инициировать/принимать мир от имени своего
   альянса — стоит закрыть на сервере в ремастере.
8. **Несимметричная проверка посольства при создании vs вступлении в
   глобальный альянс** — см. §7.3 (пункт про `_addLocalAlliances` vs
   `_joinUserToAlliance`).
9. **Дублирующиеся, слегка расходящиеся regex** для символов пароля
   вступления между `VD_AlliancePassword` и `UA_JoinAlliance`/
   `UA_ChangeAllianceJoinpassword` (см. §2) — не критично, но признак
   несинхронизированной валидации в разных точках входа.
10. **`DU_ControllerDeleteUserInstance` — мёртвый PHP-пайплайн `DU_Delete*`,
    включая `DU_DeleteAlliance`.** Массив `deleteCompanents`
    (`DU_ControllerDeleteUserInstance.class.php:23-36`) перечисляет отдельные
    PHP-классы очистки при полном удалении аккаунта (`DU_DeleteAlliance` и
    ещё десяток похожих), но `foreach`, который бы их выполнял, целиком
    закомментирован (`:59-68`). Реальное полное удаление игрового инстанса
    идёт через хранимую процедуру БД `drop_uiid()` (см. §4.7, §4.10) —
    независимую от PHP реализацию той же операции, причём не идентичную по
    поведению (`drop_from_aliance`, вызываемая изнутри `drop_uiid`,
    переназначает лидера при уходе лидера — то, чего мёртвый
    `DU_DeleteAlliance` не делал бы). Само по себе не баг — `drop_uiid`
    рабочая и даже более полная реализация, — но при ремастере ориентироваться
    стоит на неё, а не на `DU_Delete*`, несмотря на то, что PHP-классы
    выглядят как «текущий» код.

## 10. Открытые вопросы

- **Формат хранимых процедур `add_user_to_alliance`/`expel_alliance` —
  вопрос закрыт.** Тела найдены при последующей сверке с дампом схемы
  игровой БД (`pg_dump --schema-only`, вне `old-sphere`) — см. §4.10, где они
  разобраны построчно вместе с `drop_from_aliance` (третий, ранее не
  описанный путь выхода из альянса — используется только при полном удалении
  аккаунта) и триггером `insert_alliance_leader` (DB-уровневый инвариант
  «один лидер на альянс»). Предположение о простом `INSERT`/`DELETE` +
  пересчёте `members_amount` подтвердилось для `add_user_to_alliance`/
  `expel_alliance`; атомарной проверки лимита участников на уровне БД в
  них нет — лимит проверяется только на PHP-уровне, до вызова процедуры.
- **Реальная семантика «залога» с точки зрения геймдизайна** — код
  реализует его как симметричный «выкуп», который стороны предлагают друг
  другу при заключении мира (не обязательно поровну, суммы независимы для
  `_1`/`_2`), и как штраф при разрыве атакой. Не найдено явного
  ограничения «минимальный залог» или обязательности ненулевого залога —
  теоретически можно заключить мир с нулевым залогом по всем полям.
  Экономический смысл (зачем вообще платить залог, если можно и без него)
  не задокументирован нигде в коде — предположительно чисто
  антифрод/страховочный механизм, сдерживающий недобросовестное
  использование мира.
- **`ds_useralliancestatus`** — судя по структуре (`id_status`,
  `statusname`, `id_localizedstatus`), задумывалась как расширяемый
  справочник рангов с локализованными названиями, но фактически
  использована только запись `LEADER`. Не установлено, планировалась ли
  когда-либо реализация промежуточных рангов (та же гипотеза, что и с
  `ASSISTANT_CONTROL_PANEL` в глобальных альянсах, §7.2) — в текущем
  снэпшоте кода подтверждений нет, при ремастере это чистый лист.
  **Рекомендация для ремастера** (не факт из кода, а предложение): если
  нужны промежуточные роли — это придётся проектировать с нуля, готового
  паттерна в оригинале нет.
- **Как выбирается `id_comb` для залога** (`$this->comb` в
  `UA_AlliancePeace`, унаследовано из базового `UA_Action`) — не
  прослежено до конца, откуда конкретно берётся исполняющая сота
  (предположительно — сота, через здание `ALLIANCE_CONNECTOR` на которой
  открыта панель дипломатии, поскольку вся `PN_PeaceAlliance`/
  `UA_AlliancePeace` — вкладки этого здания); не подтверждено чтением
  `UA_Action`/`UA_GetBuildMenu`, эти базовые классы не входили в объём
  задания.
- **Судьба заявок в `ds_alliance_new_members` при удалении глобального
  альянса без явного роспуска** (например, если БД рассинхронизировалась)
  — отдельного каскада, кроме явного `DELETE ... WHERE id_global_alliance =
  ...` в `DeleteAlliance` (§7.4), не найдено; в остальных сценариях (не
  через штатный «Роспуск») заявки могут повиснуть.
- **Любопытная историческая находка, не факт о реализованной механике:**
  страница «Светлые и Тёмные» архивной вики игроков
  (`wiki.destinysphere.ru`, снимок web.archive.org 2012–2014 гг.) описывает
  предложенную игроками систему фракционной войны «Свет против Тьмы» — с
  общим рейтингом очков «славы» по стороне/альянсу/нейтралу, выборными
  лидерами каждой стороны, бонусными трофеями за убийство противоположной
  стороны и банами за «дружественный огонь» внутри своей стороны. Страница
  написана в повелительном/будущем наклонении («вести рейтинг», «выбрать
  лидера», «определить какие [трофеи]») — это похоже на неосуществлённое
  предложение сообщества, а не описание существующей функции. Подтверждения
  того, что подобная система альянсов/фракций «Свет/Тьма» когда-либо была
  реализована в PHP-коде `old-sphere/`, в ходе документирования этого файла
  не найдено — упоминается здесь только как курьёз для истории проекта, а
  не как факт о геймплее.
