## 1. Что это

**Реинкарнация** — сервис, доступный в **Храме** (постройка религии, см.
[mechanics-races-world-ranking.md](mechanics-races-world-ranking.md) §4),
позволяющий воскресить часть юнитов, погибших в бою, взамен на ресурсы
(либо на серебряные кредиты — отдельная вкладка с тем же интерфейсом, но
одним «ресурсом» вместо пяти). Принятие религии для этого **не
обязательно** — храма как постройки достаточно.

Условия доступности:
- Нет храма → пункта реинкарнации нет вообще.
- Есть храм и выбрана религия, но пункта реинкарнации всё равно нет →
  реинкарнация отключена в настройках конкретного мира (per-world флаг,
  аналогично шпионажу — см. `mechanics-combat.md` §12 и вращению колец).

## 2. Коэффициенты и формула лимита

На аккаунт ведутся (в продиумном эквиваленте, т.е. в суммарной
«стоимости» юнитов) три накопительных счётчика:

| Счётчик | Что туда попадает | Что НЕ попадает |
|---|---|---|
| «Построено» | юниты, построенные на заводах; юниты, полученные продажей армии (см. ниже) | юниты, реинкарнированные обратно; купленная (не построенная) армия |
| «Потеряно» | юниты, погибшие в бою; юниты купленной армии, когда она впоследствии гибнет; юниты, отправленные на реинкарнацию (см. п.3) | — |
| «Реинкарнировано» | юниты, восстановленные через реинкарнацию | — |

Особые случаи, прямо оговорённые источником:
- **Купленная армия** (не построенная, а приобретённая, видимо через
  биллинг/донат) — не увеличивает «Построено», но при её гибели в бою
  увеличивает «Потеряно».
- **Проданная армия** — увеличивает «Построено», но не увеличивает
  «Потеряно» (то есть продажа не считается «потерей»).

**Потенциал к реинкарнации** = **70% от МЕНЬШЕГО** из двух счётчиков
(«Построено» и «Потеряно») — то есть игрок, который много строил, но мало
терял, ограничен своим счётчиком потерь, и наоборот.

### 2.1 Что происходит при реинкарнации весом N (в продиуме)

```
Счётчик «Потеряно»  -= N / 0.7
Счётчик «Построено» -= N * 0.3 / 0.7
Счётчик «Реинкарнировано» += N
```

Оба знаменателя `0.7` соответствуют тем же 70%, что и в формуле потенциала
— конструкция выглядит как «обратное» применение той же формулы, чтобы
после реинкарнации новый потенциал (70% от нового меньшего счётчика)
корректно уменьшился ровно на N. Точная алгебраическая эквивалентность не
проверялась (это не код, а пересказ по игровому описанию) — для ремастера
стоит вывести формулу заново из требования "потенциал уменьшается ровно на
N" и свериться с этими двумя коэффициентами.

## 3. Ограничение по времени

Отправлять юнитов на реинкарнацию можно **не чаще одного раза в 48
часов** — после отправки все выбранные юниты возвращаются в домашнюю армию
целиком через 48 часов, и только тогда операция становится доступна снова.
Судя по формулировке, это похоже на очередь/таймер по аналогии с другими
отложенными операциями движка (`EH_*`-события, см.
[mechanics-events-turns.md](mechanics-events-turns.md)), но конкретный
класс-обработчик не идентифицирован.

## 4. Интерфейс выбора юнитов

Экран реинкарнации показывает:
- Текущие счётчики «Потеряно»/«Построено» в продиуме и вычисленный из них
  максимальный продовес к реинкарнации.
- Построчно по каждому типу юнита: стоимость производства единицы,
  стоимость выбранного количества, продовес единицы и выбранного
  количества, максимально возможное количество ЭТОГО юнита (если
  реинкарнировать только его одного, с учётом уже сделанного выбора по
  другим типам).
- Общую сумму по выбранным типам, сравнение с доступными на соте
  ресурсами.
- Групповые кнопки: сбросить всё, изменить количество сразу у всех типов
  на одинаковое число, либо регулировать каждый тип по отдельности.

Статистика подаётся также в виде понедельных/помесячных графиков потерь/
постройки/реинкарнации с всплывающими подсказками по конкретному дню —
чисто UI-фича, не влияющая на формулы выше.

## 5. Историческая деталь

Источник (пункт 5 в разделе «Особенности реинкарнации» `INFO_GAME_MAIN`,
отсутствует в варианте на `?p=reincarnation`) упоминает: «некоторое время
назад был запущен скрипт, который посчитал размер армий у игроков на
момент ноль и начал считать значения потерь в продиуме и постройки также в
продиуме. У новых игроков эти параметры уже стали считаться с момента
создания соты» — то есть это разовая миграция при введении фичи задним
числом (насчитала стартовые значения счётчиков по состоянию армии
существующих игроков на момент запуска), больше не актуальна для новых
аккаунтов. Возможный кандидат в коде — один из `TMP_*`/`DU_*`-скриптов
одноразовой миграции (не идентифицирован, не искался целенаправленно).

## Открытые вопросы

1. **Полностью не идентифицирован код**, реализующий реинкарнацию — ни
   класс(ы) `UA_*`/`EH_*`, ни имя настройки мира, которая её
   включает/выключает, ни таблицы БД, хранящие три счётчика. Это первая
   кандидатная задача, если потребуется превратить этот документ в
   код-подтверждённый (по аналогии с остальными `mechanics-*.md`).
2. **Алгебраическая эквивалентность формул** в §2 и §2.1 не проверена —
   не установлено, действительно ли применение формулы из §2.1 всегда
   уменьшает потенциал ровно на N (могут быть краевые случаи при смене
   того, какой из двух счётчиков минимальный).
3. **Разовый скрипт-миграция** (§5) не идентифицирован в кодовой базе.
4. **Название и код настройки** «реинкарнация включена/выключена для
   мира» — не найдено, только текстовое упоминание, что такая настройка
   существует.
5. **Влияние реинкарнации на общий рейтинг/статистику** (см.
   `mechanics-races-world-ranking.md` §6) — не упомянуто в источнике, не
   проверено.
