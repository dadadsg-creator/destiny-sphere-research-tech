# Каркас окон-меню клиента (`window.as`)

> **Источник.** `old-sphere/SPHERE_client/window.as` (5724 строки, прочитан
> полностью) — базовый класс `window extends MovieClip`, от которого
> наследуются практически все окна-меню игры. Дополнено целевыми (не
> построчными) проверками: `old-sphere/SPHERE_client/menuLibCode.as`
> (636 строк, прочитан полностью в предыдущем проходе) — фабрика
> `create_X_menu()` для ~40 конкретных окон; `old-sphere/SPHERE_client/
> tablecreate.as` (297 строк, прочитан полностью) — единственный
> **конкретный** наследник `window`, прочитанный целиком, использован как
> «эталонный пример» того, как реальное окно собирает методы базового
> класса вместе; `old-sphere/SPHERE_client/reqvestdata.as:399-416`
> (`call_tabs`) и `old-sphere/SPHERE_client/game.as:482-500`
> (`lock`/`unlock`/`init_decor_button`, точечно) — только для проверки
> конкретных гипотез о вкладках и блокировке экрана. Также точечно
> проверены: `old-sphere/SPHERE_client/quest_menu_class.as:305-331`
> (альтернативный локальный лок), `old-sphere/SPHERE_client/
> transfer_class.as:13-22` и другие переопределения `close_menu()`
> (`buildinfo.as`, `colonynavigate.as`, `logwindow.as`, `warstatistic.as`) —
> только сигнатуры/тела функции, не полные файлы.
>
> **Задача в контексте ремастера.** Цель отчёта — спроектировать по нему
> единый переиспользуемый HTML5/CSS компонент «окно с вкладками» без
> необходимости перечитывать AS2. Все находки категории «В» (реальная
> бизнес-логика, видимая только в исполняемом коде) отмечены явно.

## 0. Главный вывод

`window.as` — это не «одна функция создания окна», а **обширная библиотека
independent-виджетов** (скроллеры, комбобоксы, чекбоксы, вкладки,
календарь, дерево фильтров, попапы), объединённых в один класс, потому что
AS2 не имеет модулей — всё, что нужно любому окну, должно быть либо в
общем предке, либо в глобальном `game`. Реального «движка окон» с очередью/
менеджером окон нет: каждое конкретное меню (`tablecreate.as` и ~40 других
классов, прикреплённых из `menuLibCode.as`) **вручную** вызывает 5-6 методов
базового класса в правильном порядке и сама расставляет координаты. Порт на
HTML5 может (и должен) заменить это на декларативный компонент, но должен
воспроизвести:
- ровно один активный модальный слот (`game.lock(8500)`, §3);
- серверный (не локальный) переход между вкладками верхнего уровня (§2.2);
- семью самостоятельных confirm/buy-попапов, которые не участвуют в
  модальном слоте №1, а рисуют свой собственный оверлей (§6).

## 1. Каркас окна: `createWindow`/`createInnerWindow`/`resizeWindow`/`resizeInnerWindow`

### 1.1. Два слоя графики, вложенные друг в друга

Любое окно в этой системе визуально состоит из **двух независимо
создаваемых прямоугольных панелей**:

| Слой | Создаёт | Что рисует | Библиотечные ассеты (linkage) |
|---|---|---|---|
| Внешняя рамка (`win_back`/`winobj`) | `createWindow(name, obj)` (`window.as:595-628`) | Заголовок (опционально) + декоративная рамка окна: 4 угла + 4 стороны | `ugollu/ugolld/ugolru/ugolrd` (углы), `block/blocku/blockr/blockd/blockl` (заливки сторон) |
| Внутренняя панель (`win_fore`) | `createInnerWindow(obj)` (`:630-650`) | Внутренняя «утопленная» рамка контента (9-slice: центр + 4 стороны + 4 угла) | `center_/up_/down_/left_/right_/lu_/ld_/ru_/rd_` |

Оба — классический **9-slice / border-frame** паттерн (4 угла фиксированного
размера + растягиваемые полосы + растягиваемый центр), т.е. ровно то, что
в CSS решается `border-image` или явной раскладкой на grid из 9 ячеек.
`resizeWindow(wid, hei, winobj)` (`:666-709`) и `resizeInnerWindow(obj, wid,
hei)` (`:652-664`) пересчитывают позиции/размеры этих 9 кусков под заданные
`width`/`height` — **чистая геометрия, без верстки текста внутри**: сам
контент (таблица, список, форма) добавляется отдельно и вручную
центрируется вызывающим кодом (см. §1.4).

Важно: `createInnerWindow`/`resizeInnerWindow` дополнительно раскрашивают
инструментом `game.setColorMov(obj.XXX_mov)` пять из девяти кусков
(`ld_mov, rd_mov, down_mov, center_mov, left_mov, right_mov` — **не**
`up_mov/lu_mov/ru_mov`, т.е. верхняя грань внутренней панели остаётся
нетронутой заводским цветом ассета, а остальные тонируются программно) —
`game.setColorMov` не разбирался построчно (не входил в периметр задачи),
**не установлено**, что конкретно он делает с цветом (вероятно,
цветокоррекция под текущую расу/фракцию игрока, судя по паттерну похожих
вызовов `game.setColorMov` в `sota.as`/`add_second_tabs`, где он применяется
к активным/неактивным вкладкам).

### 1.2. Два режима вызова `createWindow` — «полный титлбар» vs «своя шапка»

```as
function createWindow (name, obj) {
    name_window = name;
    depth = start_layer + 20;
    if (obj == undefined) {
        var winobj = this.createEmptyMovieClip ("winobj_" + start_layer, start_layer++);
        var top_name = winobj.createEmptyMovieClip ("top_name", 1);
        createTop (top_name);          // <-- строит заголовок + кнопку закрытия
    } else {
        var winobj = obj;               // <-- вызывающий код сам передал контейнер
    }
    ...
    resizeWindow (300,200,winobj);
    return winobj;
}
```
(`window.as:595-628`)

Если `obj` **не передан** — метод сам создаёт контейнер и строит
стандартный титлбар (`createTop`, §1.3: три куска `caption_left/center/
right` + текстовое поле с именем окна аплкейсом + кнопка `close_but`,
привязанная к `close_menu()`).

Если `obj` **передан** (реальный пример — `tablecreate.as:170`:
`createWindow (this.getNameWin (tabs_array), win_back)`, где `win_back`
уже создан вызывающим кодом как `this.createEmptyMovieClip
("back_window", 10)`) — **`createTop` не вызывается вообще**, готового
титлбара и стандартной кнопки закрытия не будет. `tablecreate.as` в этом
случае строит собственную «шапку» руками: отдельный `close_button` и
`help_button`, прицепленные прямо к `this` (не к `winobj`), плюс декоративный
круглый медальон с иконкой здания (`decor_circle_window`/`pikto_build`,
`tablecreate.as:214-256`) — и вкладки (`tabs_mov`) в виде отдельного
элемента, торчащего *над* верхней гранью окна (`tabs_mov._y = win_back._y -
14`, т.е. на 14px выше рамки — визуальная метафора «закладок блокнота»).

**Для порта:** это ровно два предустановленных варианта шаблона —
`<WindowFrame title="..." withTitlebar>` (стандартный) и
`<WindowFrame withTitlebar={false}>` + слот для произвольной шапки
(кастомный). Второй вариант — не редкость: сам «эталонный» найденный
наследник (`tablecreate.as`) использует именно его, так что кастомная шапка
должна быть полноценным сценарием first-class, не хаком.

### 1.3. `createTop` — стандартный титлбар (когда он есть)

`window.as:572-593`. Состоит из `caption_left`/`caption_center`
(растягивается на всю ширину минус края)/`caption_right`, текстового поля
`text_name` (шрифт заголовка — `getCaptionStyle()`: Arial, bold, 11px,
`0xEEEEEE`, `embedFonts=true`) и кнопки `close_but`, которая всегда
находится в правом верхнем углу (`close_but._x = caption_left._width +
caption_center._width - close_but._width`). Обработчик кнопки:

```as
top_name.close_but.onRelease = function () {
    this._parent._parent._parent.close_menu ();
};
```

Три перехода `_parent` — от кнопки к `top_name`, от него к `winobj`, от
него к самому экземпляру окна — то есть `close_menu()` всегда вызывается
как метод **экземпляра-наследника window**, что подтверждает переопределимость
(§3.2).

### 1.4. `getNameWin`/`getIdWin` — имя и id окна берутся из `tabs_array`, не из отдельного поля

```as
function getNameWin (arr_tabs, text_) {
    if (text_ == undefined) text_ = "";
    for (var i = 0; i < arr_tabs.length; i++) {
        if (arr_tabs[i].cur == 1) text_ += arr_tabs[i].ln;
        if (arr_tabs[i].childarray != undefined) {
            text_ = getNameWin (arr_tabs[i].childarray, text_);   // рекурсия по вложенным вкладкам
        }
    }
    return text_.toUpperCase ();
}
static function getIdWin (arr_tabs) {
    for (var i = 0; i < arr_tabs.length; i++) {
        if ((arr_tabs[i].cur == 1) || (arr_tabs[i].cur == true)) return arr_tabs[i].id;
        if (arr_tabs[i].childarray != undefined) {
            for (var j = 0; j < arr_tabs[i].childarray.length; j++) {
                if ((arr_tabs[i].childarray[j].cur == 1) || (arr_tabs[i].childarray[j].cur == true)) {
                    return arr_tabs[i].id;      // возвращает id РОДИТЕЛЬСКОЙ вкладки, не дочерней!
                }
            }
        }
    }
    return "";
}
```
(`window.as:90-126`)

Важные, неочевидные по спецификации детали:
- **Название окна = название текущей активной вкладки** (в верхнем
  регистре), не отдельное поле «заголовок окна». Нет отдельного
  «title» — вкладка с `cur==1` целиком определяет заголовок (плюс
  дублируется рекурсивно, если есть `childarray` — на практике,
  скорее всего, конкатенация родителя и текущей дочерней вкладки).
- `getIdWin` при активной **дочерней** вкладке возвращает **id
  родительской**, а не дочерней — то есть двухуровневая структура вкладок
  (`childarray`) существует в модели данных, но `getIdWin`/`getNameWin`
  относятся к ней несимметрично: имя окна учитывает оба уровня, id —
  только верхний. **Не установлено**, баг это или осознанное поведение
  (в единственном прочитанном целиком примере, `tablecreate.as`,
  `childarray` не используется — реального пример с вложенными вкладками
  в периметре задачи не найден).
- И `createWindow`, и вызовы `add_icon_tabs` получают название/id именно
  через эти два метода, а не через отдельно переданный параметр
  «имя окна» — то есть **сервер определяет заголовок окна не текстом,
  а тем, какая вкладка помечена активной** (см. также §2, вкладки полностью
  управляются сервером).

## 2. `tabs_array` — точная форма и поведение

### 2.1. Форма одного элемента массива

Собрана по фактическому использованию полей в `add_icon_tabs`/
`add_icon_tabs2`/`add_second_tabs`/`createTabs`/`getNameWin`/`getIdWin`
(`window.as`, множество мест, см. ссылки по коду в §1.4 и ниже):

| Поле | Тип | Обязательно? | Смысл |
|---|---|---|---|
| `id` | string | да | Идентификатор вкладки, отправляется на сервер (`reqvestdata.call_tabs(id)`, см. §2.2) |
| `ln` | string | да | Локализованное название вкладки (уже готовый текст, не ключ локализации — устанавливается в текстовое поле как есть) |
| `cur` | `1`/`true`/falsy | да | Является ли вкладка активной. `1` и `true` оба валидны (сравнение `== 1 \|\| == true`) — **непоследовательный, но намеренно широкий** чек, вероятно из-за разнобоя в том, как сервер сериализует булевы значения в XML→объект (иногда `"1"`, иногда `true`) |
| `icon` | string (linkage) | да, для `add_icon_tabs*` | Имя библиотечного символа иконки вкладки, `attachMovie(array[i].icon, ...)`. Не используется в `add_second_tabs` (там иконок нет вообще, только текст) |
| `nc` | string (URL) | нет | Если задано — вкладка превращается в **внешнюю ссылку**: `notActive=true`, клик вызывает `reqvestdata.openUrl(this.url)` вместо `call_tabs`, `close_menu()` не вызывается |
| `childarray` | `Array<той же формы>` | нет | Вложенные под-вкладки — обрабатываются рекурсивно только в `getNameWin`/`getIdWin` (§1.4); ни один найденный `add_icon_tabs*`/`add_second_tabs` не рендерит `childarray` визуально как поддерево — **не установлено**, где (если вообще) `childarray` рисуется на экране; вероятно, только `createTree`/`addRadio`-подобные виджеты в конкретных менюшках-наследниках, вне периметра этой задачи |
| `act` | число/undefined | нет, только `add_second_tabs` | Если `<=0` — вкладка визуально серая и некликабельная (`window.as:3491-3510`) |
| `hint` | string | нет, только `add_second_tabs` | Текст тултипа для вкладки (`game.init_decor_button(obj,"ONLY_HINT",...)`) |

### 2.2. Клик по вкладке верхнего уровня — **запрос на сервер**, не локальное переключение

Все три обработчика клика по иконным вкладкам (`add_icon_tabs`,
`add_icon_tabs2`, обе `_WIDE`-версии, `createTabsCombo`) содержат
**идентичный** блок:

```as
obj_for_tabs.onRelease = function () {
    if (!this.notActive) {
        reqvestdata.call_tabs (this.ID);
        debug.link.temp_active_cell = debug.link.active_cell;   // бэкап состояния активной ячейки карты
        debug.link.temp_pointCell = ...                          // (копия объекта, поле в поле)
        this.menu_path.close_menu ();   // <-- окно ЗАКРЫВАЕТСЯ немедленно, до ответа сервера
    } else {
        reqvestdata.openUrl (this.url);
    }
};
```
(`window.as:2902-2925` и повторено ещё 3 раза почти буква в букву)

`reqvestdata.call_tabs` (`reqvestdata.as:399-416`) отправляет
`<getbuildmenu c="..." tab="TAB_ID"/>` на сервер (используя текущую
`debug.link.active_cell`, либо `c='warbase'`, если активной ячейки нет) —
**это полноценный сетевой запрос**, а не переключение видимости готового
контента. Окно **закрывается сразу после отправки запроса**, до получения
ответа — предположительно новое окно (той же или другой конкретной
менюшки) создаётся заново, когда сервер присылает следующий `<menu>`/
`<getbuildmenu>` ответ, тем же механизмом `create_X_menu()` из
`menuLibCode.as`, что и первое открытие.

**Важно для порта:** вкладки верхнего уровня в этой системе — это по сути
**серверная навигация с полной перерисовкой**, а не client-side tab-switch.
HTML5-аналог должен либо (а) воспроизвести это как отдельный запрос на
каждый клик по вкладке (проще, ближе к оригинальному таймингу и нагрузке
на сеть), либо (б) если ремастер меняет протокол — заранее продумать, что
контент всех вкладок одного окна в старой системе **никогда не был
известен клиенту одновременно** (сервер не присылает данные для неактивных
вкладок вообще), так что «мгновенное локальное переключение» потребует
либо префетча, либо смены протокола, а не только смены фронтенда.

### 2.3. Четыре варианта отрисовки — 2 семейства, каждое с обычным и `_WIDE` вариантом

| Функция | Отличие | Переключатель |
|---|---|---|
| `add_icon_tabs` (`:2792-2940`) | Активная вкладка — крупная плитка с иконкой+текстом слева, остальные — маленькие квадраты только с иконкой (текст только в тултипе) | по умолчанию |
| `add_icon_tabs_WIDE` (`:3111-3258`) | То же, но неактивные вкладки — `WIDE_BUT_TAB` с подписью `cap.text` под/рядом с иконкой (текст виден всегда, не только в тултипе) | `_level0.WIDETABS == true` (глобальный флаг) |
| `add_icon_tabs2` (`:2942-3107`) | Активная вкладка — на всю ширину окна (`BKG_TEXT_TAB._width = game.width_game`), похоже на «шапка с одной большой вкладкой + маленькие рядом» | по умолчанию |
| `add_icon_tabs2_WIDE` (`:3260-3430`) | Комбинация: широкая активная плитка (как в `2`) + подписанные неактивные плитки (как в `_WIDE`) | `_level0.WIDETABS == true` |

Каждая функция сама решает, звать ли `_WIDE`-версию, по одному и тому же
условию `if (!_level0.WIDETABS \|\| WIDE == false) {...} else {
add_icon_tabs_WIDE(...)}` — то есть это **глобальный переключатель раскладки
для всех окон игры одновременно** (вероятно, введён при переходе на более
широкое разрешение экрана — см. §7, `window_original.as` вообще не содержит
`_WIDE`-функций, то есть это более позднее добавление), с возможностью
точечно отключить его для конкретного вызова через явный параметр
`WIDE:false`.

Все четыре варианта используют один и тот же обработчик клика (§2.2,
серверный запрос) — разница чисто визуальная, не функциональная.

### 2.4. `add_second_tabs` — второй, **локальный**, механизм вкладок

`window.as:3438-3521`. Отдельная, гораздо более простая функция: текстовые
«таблетки» (активная — светлый фон, неактивная — тёмный), клик по которым
**не уходит на сервер**:

```as
obj.onRelease = function () {
    if (!this._parent.arr[this.num].cur) {
        this._parent.action (this.id,this.num);   // <-- локальный callback, метод самого меню
        for (var i = 0; i < this._parent.arr.length; i++) { _parent.arr[i].cur = false; }
        this._parent.arr[this.num].cur = true;
    }
}
```
(`:3493-3504`)

Здесь переключение активной вкладки — чисто клиентское (флаг `cur`
переставляется в JS-массиве на лету), а реакция делегируется методу
`action(id, num)`, который должен существовать на конкретном
наследнике-меню (не в базовом классе — `window.as` его не определяет).
**Не установлено**, что конкретно делает `action()` в реальных менюшках
(нет прочитанного целиком примера использования `add_second_tabs` в
периметре задачи) — по названию и месту в коде это, вероятно,
второстепенные вкладки *внутри* уже открытого окна (например, переключение
раздела списка без переоткрытия всего окна), в отличие от вкладок верхнего
уровня из §2.2, которые всегда идут на сервер.

**Для порта:** это два принципиально разных UI-паттерна с одинаковым
визуальным языком «вкладки», и путать их нельзя:
- вкладки верхнего уровня окна = **навигация**, требует похода на сервер;
- `add_second_tabs` = **локальный переключатель вида** внутри уже
  загруженных данных.

`window.as:2594-2784`. Альтернативная раскладка: одна кнопка с именем

более ранний/альтернативный дизайн вкладок для узких окон, вытесненный
иконными вкладками.

## 3. Жизненный цикл окна

### 3.1. `close_menu()` — три действия, всегда одинаковые в базовой реализации

```as
function close_menu (key) {
    /* Эта функция может переопределяться в менюшках */
    game.unlock (8500,true);
    game.show_hint ("NO");
    this.removeMovieClip ();
}
```
(`window.as:2571-2580`)

Три шага: (1) снять модальную блокировку экрана под конкретным ID `8500`
(жёстко закодированный номер, не параметр — **все** окна-меню в игре
делят один и тот же лок-слот, см. §4); (2) убрать текущий тултип, если
был; (3) удалить сам MovieClip окна.

### 3.2. Переопределения — то же самое действие + очистка модуль-специфичных глобалов

Комментарий в коде прямо говорит, что `close_menu` предназначен для
переопределения, и на практике так и происходит: `buildinfo.as`,
`colonynavigate.as`, `logwindow.as`, `warstatistic.as`, `transfer_class.as`
и другие определяют свой `close_menu()`. Пример (`transfer_class.as:13-22`):

```as
function close_menu() {
    delete debug.link.transfer_menu_path;
    delete debug.link.messageEvent;
    game.unlock(8500, true);
    game.show_hint("NO");
    delete debug.link.active_cell;
    delete debug.link.pointCell;
    this.removeMovieClip();
}
```

Переопределение **не меняет** базовую тройку действий — оно добавляет
`delete` для переменных, которые данное конкретное меню складывало в
общий глобальный объект `debug.link` (общая «сумка» переменных на таймлайне,
используемая как shared state между модулями — сама она не разбиралась в
периметре этой задачи). Общий паттерн для порта: закрытие окна = (а)
снять модальность, (б) убрать подсказку, (в) удалить DOM/компонент, (г)
опционально — специфичная для конкретного окна очистка стейта.

### 3.3. `game.lock`/`game.unlock` — делегируют дальше, дополнительно скрывают fullscreen-кнопку

```as
static function lock (depth, key_vis) {
    if (game.local ()) { key_vis = undefined; }
    debug.link.lock (depth,key_vis);
    _level0.hideFS()
}
static function unlock (depth, key_vis) {
    debug.link.unlock (depth, key_vis);
    _level0.showFS()
}
```
(`game.as:482-496`)

`game.lock`/`unlock` — тонкие обёртки: реальная работа (создание/удаление
затемняющего прямоугольника-оверлея по номеру `depth`) делегирована методам
`lock`/`unlock` объекта **`debug.link`** — эти методы **не найдены как
`.as`-исходник** в `SPHERE_client/` (вероятно, определены прямо на
таймлайне главного `.fla`, как нередко бывает в этой кодовой базе — см.
аналогичный паттерн `game.check_build_size()` в `docs/client-map-and-
grid.md` §9). **Не установлено**, как именно рисуется/анимируется сам
затемняющий прямоугольник для `depth=8500` — известно только, что для
других, самодостаточных попапов (§6) такой прямоугольник рисуется вручную
через `beginFill`/`lineTo` прямо в вызывающей функции, так что *по
аналогии* можно предположить, что и здесь это простой полупрозрачный
прямоугольник на весь экран с `onRelease = function(){}` (глушит клики).
Дополнительный, не задокументированный в других файлах эффект:
**при любом lock/unlock прячется/показывается кнопка полноэкранного
режима** (`_level0.hideFS()`/`showFS()`) — то есть модальное окно и в этом
отношении ведёт себя как настоящий системный диалог, не просто оверлей.

### 3.4. Идемпотентность открытия — не в `window.as`, а в `menuLibCode.as`

Сам базовый класс `window` не содержит защиты от повторного открытия —
это обязанность каждой конкретной `create_X_menu()`-функции
(`if (this.X_mov == undefined) {...} else {...updateX(...)}`,
задокументировано в предыдущем проходе по `menuLibCode.as`). `window.as`
предоставляет только строительные блоки, которыми конкретная функция
обновления (`updateX`) может воспользоваться (например, `resizeWindow`
для изменения размера уже существующего окна при изменении объёма данных).

### 3.5. Мёртвый код — `window.current`/`window.opened` никогда не используются

```as
static var current:Object;
static var opened:Number = 0;
...
function window () {
    ...
    //window.current = this;   // <-- закомментировано, единственное присвоение во всём файле
}
```
(`window.as:3-4, 74`)

Оба статических поля объявлены явно с намерением вести реестр «текущего
открытого окна» на уровне базового класса, но реальное присвоение
`window.current = this` **закомментировано** (единственное место в файле,
где это поле упоминается за пределами объявления), а `window.opened`
не инкрементируется/не читается вообще ни в одном файле `SPHERE_client/`
(проверено `grep`). То есть в какой-то момент разработчики начали делать
централизованный реестр открытых окон на уровне базового класса, но
отказались от этого в пользу ad-hoc проверки `this.X_mov != undefined` на
уровне каждой конкретной менюшки (§3.4, `menuLibCode.as`) — вывод согласуется
с уже задокументированным в `docs/client-map-and-grid.md` паттерном
брошенных/недоделанных фич (`rotate_sota`, `SWITHC`).

Аналогично мёртв параметр `type` у `addButton(x, y, width, height, text,
func, type)` (`window.as:902-908`): независимо от переданного значения,
код всегда устанавливает `type = 1` (`if (type==undefined){type=1} else
{type=1}` — оба branch делают одно и то же), то есть параметр `type`
никогда не влияет на результат — либо забытый рефакторинг, либо заготовка
под нереализованный второй тип кнопки.

## 4. Многооконность и z-order

### 4.1. Два несвязанных «пространства глубин» — не путать

В коде встречаются числа-глубины (`depth`) в двух совершенно разных
смыслах, и один из них легко спутать с другим:

1. **Глобальные слоты меню** (числа `8500`, `10`, `20`, `24`, `30`, `35`,
   `120`, `124`, встречающиеся в `menuLibCode.as`) — это глубина, на
   которую **целое окно-меню** (`attachMovie(linkageName, instanceName,
   depth, ...)`) прикрепляется на общий родительский клип-контейнер меню
   (вероятно, `debug.link.menu_mov` или аналог — сам контейнер не
   разбирался). Эти числа определяют z-order **между разными окнами**.
2. **Внутренний счётчик `depth`/`start_layer`** класса `window`
   (`window.as:598`: `depth = start_layer + 20`, инкрементируется в
   `addButton`/`addTextScroll`/`initCombo`/`addScroll` и т.п.) — это
   глубина отдельных виджетов **внутри уже созданного** одного окна
   (кнопок, скроллбаров, комбобоксов). Не имеет отношения к z-order между
   окнами, это чисто внутренняя бухгалтерия одного экземпляра.

### 4.2. Один модальный слот, а не стек окон

`close_menu()` всегда снимает лок по фиксированному номеру `8500`
(§3.1) — то есть **все** окна-меню в игре в модальном отношении
эквивалентны одному-единственному булеву флагу «модалка открыта/закрыта»,
а не независимому стеку. Подтверждается таблицей вызовов `game.lock(8500,
...)` из `menuLibCode.as` — почти каждая `create_X_menu()` вызывает
`game.lock(8500)` (или `game.lock(8500,"hide")` — разница между этими
двумя вариантами не разбиралась в периметре задачи, **не установлено**,
чем «hide» отличается от обычного лока; вероятно — скрывать ли фоновую
соту, судя по названию) непосредственно перед `attachMovie`.

Числа depth **среди самих окон** (10/20/24/30/35/120/124) в основном
переиспользуются между несвязанными менюшками (например, и `colony_menu_mov`,
и `war_plate_menu_mov` используют depth 30 — в разное время, никогда
одновременно) — это **не** параллельный набор слотов для одновременно
открытых окон, а просто исторически выбранный номер слота на общем
таймлайне для конкретной менюшки (постоянный per-menu-type, а не
динамически выделяемый).

### 4.3. Исключение №1 — «дочернее» окно, всплывающее НАД уже открытым, без своего лока

```as
function create_mail_client(array,maildata) {
    if (this.mail_menu == undefined) { game.lock(8500, "hide"); }
    var mail_menu = this.attachMovie ("mailmenu", "mail_menu", 24, {...});
}
function create_mail_new(type_array, tabs_array, quotemessage, subject, name) {
    var loopback_menu_mov = this.attachMovie ("create_mail_mov", "create_mail_mov", 35, {...});
    // Обратите внимание: НИКАКОГО game.lock(8500) здесь нет
}
```
(`menuLibCode.as:365-381`)

Окно «написать письмо» (depth 35, «Написать письмо» поверх списка почты)
не запрашивает лок сам — оно **рассчитывает, что почтовый клиент (depth
24) уже открыт и уже держит лок `8500`**. Это подтверждает, что
одновременно на экране *может* быть больше одного окна-меню, но только
в захардкоженных родитель-потомок парах, известных заранее авторам кода
(здесь: список писем → компоузер письма), а не как общий механизм
множественных независимых окон.

### 4.4. Исключение №2 — лог-окно с полностью отдельным, независимым локом

```as
function create_log_window(titletext,datatext,text_) {
    var MovForLock:MovieClip = this.createEmptyMovieClip("tempForLock",120);
    MovForLock.beginFill(0xFF0000,0);
    ... // прямоугольник на весь экран, useHandCursor=false, onRelease={}
    var scanner_menu:MovieClip = this.attachMovie("logwindowmenumain","logwindowmenumain",124,
        {title:titletext, titleData:datatext, textData:text_, lockMov:MovForLock});
}
```
(`menuLibCode.as:5-18`)

Лог-окно **не использует `game.lock(8500)` вообще** — оно рисует свой
собственный клик-блокирующий прозрачный прямоугольник на отдельном слоте
(`depth=120` для оверлея, `124` для самого окна) и передаёт этот
прямоугольник самому окну как параметр `lockMov` (управление его удалением,
по всей видимости, лежит на `logwindowmenumain`/`logwindow.as`, не
разбиралось построчно). Поскольку это полностью отдельный номер лока —
лог-окно **может быть открыто одновременно с обычным модальным окном**
(оба лока активны независимо), что и обосновывает пометку в постановке
задачи «always-on-top лог-оверлей». Это единственный найденный случай
настоящей параллельной модальности в системе.

### 4.5. Итог для порта

- Базовый случай — **один активный модальный слот** на все обычные
  окна-меню: открытие нового обычно подразумевает, что предыдущее уже
  закрыто (сервер, отправляя новый `<menu>`, ожидает этого).
  HTML5-аналог может смело реализовать это как один React/Vue
  komponent-слот `<ModalWindowHost>` с очередью из максимум одного
  элемента.
- Отдельно нужен **второй, независимый слот** для одного конкретного
  типа окна — лог/уведомления (`create_log_window`) — always-on-top,
  никогда не конфликтует с обычной модалкой.
- Отдельно нужна поддержка **дочернего попапа над родителем** (compose
  mail над mail client) — но это не общий механизм, а конкретный
  захардкоженный сценарий; в HTML5 естественно реализуется как
  вложенный компонент внутри родительского окна, а не как второе окно
  на верхнем уровне.
- Плюс полностью отдельная от всего этого **третья категория** —
  confirm/buy-попапы (§6), которые вообще не участвуют в системе
  `game.lock` и рисуются поверх *любого* текущего контекста (окна или
  даже без окна).

### 5.1. Три разные реализации скроллера — не унификация, а наслоение решений

`window.as` содержит **три параллельных, независимых механизма
скроллирования**, судя по всему написанных в разное время под разные
нужды:

1. **`addScroll`** — скроллирует произвольный `mov` внутри маски заданного
   размера, с полосами по X и/или Y по необходимости (сравнивает размер
   контента с размером маски), поддерживает колесо мыши (свой
   `Mouse.addListener`/`onMouseWheel` активируется только когда курсор
   физически находится над маской — `init_wheel`, `:1209-1250`).
   Используется, например, для выпадающего списка `initCombo` (§5,
   `this.mov_wnd.addScroll(list_combo_mov, ...)`, `:1845`).
2. **`addTextScroll`** — привязывается к одному конкретному `mov`
   (обычно текстовому полю) и двигает именно его через `scroll`/
   `maxscroll` числовые поля на самом `mov`, а не через маску с
   произвольным контентом — то есть это скорее «прокрутка длинного
   текста», чем «прокрутка списка виджетов».
3. **`addDiskretScroll`** — **не двигает** контент плавно, а
   **пересоздаёт** видимые элементы списка при каждом шаге
   (`createList()` удаляет и заново создаёт ровно `height_scroll_in_
   popugyah` штук через `attachMovie`) — то есть это virtualized list /
   виртуальный скролл, а не «двигаем большой контейнер под маской».
   Поддерживает колесо мыши через отдельный, **не связанный** с
   `addScroll` механизм — с явным гейтом `scrollerActive` (см. §5.2).

**Для порта**: с точки зрения HTML5 это ровно один паттерн (виртуализация
списка с фиксированной высотой строки) даёт лучшую производительность
для длинных списков (аукцион, армия, статистика построек), а маска+
перемещение контейнера (`addScroll`) достаточно для коротких/фиксированных
областей (комбобоксы, текстовые блоки). Разумно унифицировать все три в
один компонент с виртуализацией, а не переносить три раздельных
реализации как есть.

### 5.2. `scrollerActive` — гейт для колеса мыши при нескольких списках в одном окне

`window.as:4654-4698` (внутри `addDiskretScroll`). При прокрутке колесом
мыши обработчик проверяет:

```as
if ( (this.mov_rail._parent.scrollerActive) &&
     (курсор физически внутри границ этого конкретного списка) ) {
    ... // применить скролл именно к ЭТОМУ списку
}
```

`scrollerActive` — булево поле, которое выставляет **конкретное меню**
(не базовый класс) сразу после создания списка (пример:
`menuLibCode.as:176`, `battleoverview_menu.scrollerActive = true;` —
комментарий в коде: *«Разрешили скроллер в созданном окне»*) и переключает
на `true`/`false` при rollover/rollout контейнера, содержащего список
(`battleoverviewclass.as:102-107`). Смысл: когда в одном окне несколько
независимых прокручиваемых списков (или список внутри списка), колесо
мыши должно скроллить только тот список, над которым сейчас курсор —
`scrollerActive`, судя по всему, служит именно этим «текущий под курсором»
флагом-разрешением, а не глобальным включением/отключением скролла
вообще. **Не установлено** доподлинно, есть ли более общий механизм
(например, приоритет самого верхнего/самого внутреннего списка при
перекрытии) — из прочитанных фрагментов видно только точечное включение/
выключение per-instance.

## 6. Семейство confirm/buy/alert-попапов — самодостаточные, не через `game.lock(8500)`

Все шесть функций ниже создают попап **внутри контейнера, на котором их
вызвали** (`this.createEmptyMovieClip(...)`, где `this` — либо текущее
открытое окно, либо, для `createPopupWindow`/`createAlertWindow`, любой
уровень с доступом к базовому классу `window`), рисуют **собственный**
полноэкранный прямоугольник-блокиратор кликов (`beginFill`/`lineTo` от
`(0,0)` до `(game.width_game, game.height_game)`, `onRelease=function(){}`,
`useHandCursor=false`) и центрируют попап по экрану (`_x = game.width_game
/2 - width/2`). Они **не вызывают `game.lock`/`game.unlock`** — блокировка
кликов ограничена только их собственным локальным прямоугольником, который
удаляется вместе с попапом через `this._parent._parent.removeMovieClip()`.

| Функция | Кнопки | Назначение |
|---|---|---|
| `createPopupWindow` (`:4018-4057`) | Только `OK` | Простое информационное сообщение |
| `createConfirmWindow` (`:4280-4358`) | `Да`/`Нет` (`YES_BUT`/`NO_BUT`) | Обычное подтверждение, крупное окно |
| `createConfirmWindowTiny` (`:4360-4427`) | `Да`/`Нет` | То же, компактный ассет (`confirm_window_tiny`) — комментарий в коде: *«Такая же херь точно тока окно поменьше раз в 20»* |
| `createAlertWindow` (`:4429-4471`) | Только `OK` (кнопка `NO_BUT` скрыта: `_visible=false`) | Предупреждение без альтернативы — фактически переиспользует ассет `confirm_window`, но прячет вторую кнопку |
| `createBUYWindow` (`obj, desc, size)` (`:4059-4197`) | `OK`/закрыть | Покупка ресурсов за серебро: встроенный числовой степпер (свой, не через `initAmountScroll`) для количества «пакетов», живой пересчёт итоговой цены/ресурсов по вводу; `size=="SMALL"` переключает на ассет `buy_scientists` вместо `buy_window` |
| `createBUYBONUSWindow` (`obj, desc)` (`:4206-4272`) | `Купить`/закрыть | Упрощённая покупка (без количества — единичная покупка бонуса) |

Все шесть возвращают сам `win_confirm` MovieClip и оставляют
`win_confirm.func_y`/`func_n` **не определёнными** — вызывающий код обязан
сам присвоить эти callback'и после вызова (пример из `tablecreate.as:34-51`
— `win_conf.func_y = function(val, indx, type, desc){ ...
reqvestdata.getPayService(...); this._parent._parent.close_menu(); }`).
Это простой, но полностью ручной contract «фабрика создаёт форму, вызывающий
код навешивает поведение» — ближайший HTML5-аналог: модальный компонент,
принимающий `onConfirm`/`onCancel` как пропсы, а не Promise/async-await
(которых в AS2 разумеется нет).

Тот же паттерн «свой локальный прямоугольник-блокиратор, без `game.lock`»
встречается и в конкретных наследниках `window`, не только в базовом
классе — например, `quest_menu_class.as:305-331` (`lockMenu(lock:Boolean)`)
рисует идентичный прямоугольник на слоте `1012` для собственного
подокна деталей квеста. То есть это устоявшаяся, повторяемая по всей
кодовой базе идиома, а не разовое решение.

### 6.1. Находка категории «В»: покупка закрывает всё окно, не только попап

В `tablecreate.as:34-51`, callback `func_y` покупки вызывает
`this._parent._parent.close_menu()` — что закрывает не сам купленный
попап (он и так удаляется строкой ниже, внутри `createBUYWindow`), а
**всё родительское окно с таблицей**, из которого была инициирована
покупка. То есть бизнес-правило — «после покупки открывшее её окно
считается неактуальным и закрывается целиком», а не «обновить цифры на
месте». Согласуется с общей моделью §2.2 (сервер пересылает актуальные
данные заново, а не патчит существующее окно) — покупка, скорее всего,
тоже провоцирует новый ответ сервера с обновлённым состоянием, которое
откроет окно заново, если оно всё ещё нужно.

## 7. Категория «В» — прочие находки реальной логики

- **Формула вписывания иконки здания в круглый медальон**
  (`tablecreate.as:244-256`): диагональ бокса иконки приводится к
  фиксированному диаметру 56px через `Math.sqrt(w²+h²)`, затем позиция
  корректируется через `getBounds()` (компенсация смещения точки
  регистрации ассета от его видимого левого верхнего угла) — стандартный
  приём «вписать произвольно нарисованный спрайт в фиксированный круг»,
  такой же нужен и в HTML5-версии для build-иконок произвольных
  пропорций.
- **Акселерация зажатой кнопки степпера** (`initAmountScroll`/`2`,
  `:2003-2133` и похожие): удержание `+`/`-` не просто повторяет шаг
  каждый кадр — счётчик `count`/`maxcountframe` заставляет шаг ускоряться
  со временем зажатия (`maxcountframe` уменьшается, `delta` растёт после
  каждых 5 срабатываний) — то есть это не константный тик, а нарастающая
  скорость, которую нужно воспроизвести явно (не просто `setInterval`
  с фиксированным периодом).
- **`getIdWin` теряет id дочерней активной вкладки** (§1.4) — потенциальный
  источник несоответствия заголовка окна выбранной вкладке при
  многоуровневых вкладках, если они где-то реально используются.
- **`_level0.WIDETABS`** (§2.3) — глобальный флаг раскладки вкладок,
  переключающий поведение сразу всех окон в игре одновременно; в
  HTML5-аналоге это чистый CSS/layout-вариант компонента, не нужно
  переносить как «два разных виджета».

## 8. Версии файла — `window_original.as` (более старый снимок)

В `SPHERE_client/` присутствует `window_original.as` (4561 строка,
отличается от `window.as`, 5724 строки; полное построчное сравнение не
проводилось — только целевая проверка). Подтверждено: `window_original.as`
**не содержит** ни одной из четырёх `_WIDE`-функций вкладок (§2.3), ни
`createBUYWindow`/`createBUYBONUSWindow` (§6) — то есть это снимок клиента
до добавления широкоформатной раскладки вкладок и до появления встроенных
окон покупки ресурсов/бонусов за серебро внутри игровых менюшек. Такой же
паттерн «старый снимок без более позднего функционала» уже был
задокументирован для `Копия sota.as` в `docs/client-map-and-grid.md` §8 —
здесь он подтверждается второй раз на другом файле, что говорит в пользу
систематической практики оставлять `_original`/`Копия`-снимки в рабочей
директории при правке ключевых файлов, а не единичного случая.
