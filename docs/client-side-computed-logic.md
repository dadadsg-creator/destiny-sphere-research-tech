# Игровая логика, вычисляемая в клиенте (AS2/AS3, `SPHERE_client/`)

> **Контекст и цель документа.** Обсуждается перенос Flash-клиента (AS2) на
> HTML5/JS при неизменном PHP-бэкенде/протоколе/БД. На уровне транспорта
> перенос тривиален (см. [protocol-client-server.md](protocol-client-server.md),
> [client-engine-and-protocol.md](client-engine-and-protocol.md) — простой
> `POST xmldata=<xml>`, не AMF). Главный риск — игровая логика, посчитанная
> **прямо в клиенте**, а не только отрисованная из ответа сервера: если такая
> логика есть, её придётся переносить формула-в-формулу, а не просто
> "перерисовать" на новый стек.
>
> Разобраны **все** реальные (не декомпилированные) `.as`-файлы в
> `old-sphere/SPHERE_client/`, кроме SVN-метаданных (`.svn/`) и рекламных
> баннеров (`SD BANNER/calc/*.fla` — не относятся к игровой логике). Итого
> **128 файлов** (без учёта неигровых баннеров), включая известные дубликаты
> (см. §3).
>
> Этот документ пересекается по периметру с уже существующими
> [client-combat-ui.md](client-combat-ui.md) и
> [client-economy-social-ui.md](client-economy-social-ui.md) (оба разбирают
> те же файлы, но через призму "какие XML-поля/протокол видны в каждой
> панели"). Здесь используется **другая призма**: для каждого файла явно
> определяется, вычисляет ли клиент что-то игровое **сам**, и если да — что
> именно, по какой формуле и отправляется ли результат обратно на сервер.
> Там, где предыдущие документы уже разобрали файл подробно, здесь это
> используется как источник (со ссылкой), а не переписывается заново.
>
> Кодировка: `.as`-файлы читались как UTF-8 (часть содержит "двойную
> мойбаку" в кириллических комментариях — не мешает чтению кода/чисел).
> Правки применялись только байт-safe заменой отдельных строк (см. §7), без
> использования Edit-инструмента на файлах `old-sphere/`.

| Тип находки | Файлов |

| Коридор цены ордера (min/max, % от сервера) | 2 (те же файлы) |

| Конвертация валюты соцсети (VK/POP "голоса" ↔ игровая валюта) | 2 (`VKGATE.as`, `POPGATE.as`) |

**Ключевой вывод сразу**: ни в одном из найденных случаев клиентски
вычисленное число **не отправляется обратно на сервер как есть** — везде,
где дошло до реальной отправки команды (`reqvestdata.*`), полезная нагрузка
— это либо голые идентификаторы+количества (сервер сам считает цену/время),
либо значение, введённое игроком напрямую (например, цена лота на бирже).
Подробности — §5. Единственная область, где клиентски вычисленное число
**реально** участвует в денежной операции — это конвертер валюты соцсети
(VK/POP, §4.8) — но оно уходит не на игровой сервер, а во внешний платёжный
шлюз соцсети.

## 2. Категория (В) — детальный разбор всех находок

### 2.1. Прогрессивное ценообразование зондов — `zondcreateclass.as:11-51`

Единственная найденная во всём клиенте **геометрическая прогрессия**.
Полностью и независимо документирована также в
[client-combat-ui.md, §11](client-combat-ui.md) — здесь формула повторена
как ключевая находка категории (В):

```as2
function calculatePriceWithProgressiv(base_price, delta_price, current_ready, count_for_create, keyRound)
{
    if (delta_price == 1) {
        price = count_for_create * base_price                              // линейно
    } else {
        pricefull  = base_price * (1 - Math.pow(delta_price, current_ready + count_for_create)) / (1 - delta_price)
        priceready = base_price * (1 - Math.pow(delta_price, current_ready)) / (1 - delta_price)
        price = pricefull - priceready                                     // сумма геом. прогрессии на отрезке [ready, ready+count)
    }
    return keyRound ? Math.ceil(price) : price
}
```

Применяется отдельно к каждому виду цены зонда: ресурсам `K/N/S/F/P/W`,
времени постройки `C` (после — через `game.turnToTime(...)`) и **военному
рангу `WR`** (без округления, `keyRound=false`) — `zondcreateclass.as:59-111`.
Каждый следующий зонд дороже предыдущего в `delta_price` раз; `base_price`
и `delta_price` приходят с сервера (`<allowzond price="K:1,N:12,...,WR:2.2"
delta="K:1.04,...,WR:1.2" .../>`, живой пример — `client-combat-ui.md §11`).

**Отправка на сервер**: кнопка "Тренировать" (`zondcreateclass.as:262-283`)
шлёт `reqvestdata.trainzondunit(count, id)` — **только количество и id
типа зонда**, ни цена, ни промежуточные вычисления не передаются. Клиентская
формула — чисто предпросмотр ("сколько это будет стоить, если нажать
сейчас"); сервер обязан пересчитывать её сам при обработке команды.
**Риска читерства не найдено** — но при переносе в HTML5 саму формулу нужно
воспроизвести 1:1 (в т.ч. округление `Math.ceil` только для 6 ресурсов,
но не для `WR`), иначе предпросмотр разойдётся с тем, что реально спишет
сервер.

**Серверная сторона найдена и подтверждена кодом (2026-09-08,
`GL_SpyCountZondPrice.class.php`)** — формула алгебраически идентична
клиентской (см. подробный разбор и реальные значения роста цены на
живом мире в [client-combat-ui.md §11](client-combat-ui.md)). Заодно
исправлена неточность более раннего прохода: пример живого XML в том
разделе — не настоящий сетевой захват, а клиентский тестовый файл с
gibberish-заглушками.

### 2.2. Формула предпросмотра времени производства — 9 файлов, один и тот же паттерн

Один и тот же приём повторяется почти без изменений в 9 разных панелях:
клиент сам переводит "цену юнита в ходах" в реальное время через
`game.turnToTime()` (утилита форматирования из `game.as`, категория А —
сама по себе не формула, просто `ходы → "Дни Ч:М:С"`):

```
время = game.turnToTime( цена_в_ходах × turn_time × [Math.ceil(количество / число_фабрик)] [/ 2, если premium-ускорение] )
```

| Файл:строка | Контекст | Особенность |
|---|---|---|
| `warstatistic.as:201-205` | Пакетное производство юнитов на военной базе (несколько "фабрик" сразу) | `Math.ceil(amount/count_factory)`, делится на 2 при `speedUp=="1"` (премиум-ускорение x2) |
| `trainvarunitclass.as:282` | Детальная тренировка боевого юнита | `obj.price.time × count`, где `price.time = game.getLocalNames(id).C × xml.attributes.turn` (см. также `client-combat-ui.md §6`) |
| `archeology_class.as:173` | Наём археологов | `val × arch_price_menu.C × arch_price_menu.turn` |
| `researchmenu.as:193` | Наём учёных | `val × scencist_price_block.C × scencist_price_block.turn` |
| `spying_class.as:307` | Отправка зонда на задание | `val × object_list.turntime` |
| `powershieldclass.as:168` | Активация силового щита (кол-во ходов × цена) | `val × turn`, без /2, отдельная переменная не про "фабрики" |
| `army_overview_class.as:740` | Обзор армий, поле оставшегося времени | `num × turn_time` |
| `reincarnate.as:563`, `trade_menu_class.as:857` | Поле "время доставки" при выставлении лота на бирже/реинкарнации | `this.turn × timeTrade.getValue()` |

**Отправка на сервер**: во всех 9 местах submit-команда (`load_pack_war_factory`,
`trainWarUnit`, `trainScientist`/наём археологов, `send_zond`, `powershieldenabled`,
`sale`) несёт только количество/id/выбранное время в ходах — **не**
вычисленное клиентом человекочитаемое время. Вычисленное значение — это
именно и только текст в UI. Риска нет, но при переносе нужно воспроизвести
`turnToTime` идентично (формат "Д Ч:М:С"), иначе разойдётся с тем, что
покажет сервер после подтверждения.

### 2.3. Простые предпросмотры "цена_за_единицу × количество" — 7 файлов

Отдельная, более простая категория — просто умножение серверной цены на
введённое количество, без прогрессии и без пересчёта времени:

- `archeology_class.as:174-176` (`work_field`/`kad_field`/`food_field` = `val × arch_price_menu.{W,K,F}`)
- `researchmenu.as:194-196` (аналогично, наём учёных)
- `trainvarunitclass.as:285-297` (цена и **содержание** юнита × количество)
- `scannermenuclass.as:343-347,383-387` (стоимость пересканирования × `countScan`) + `:375` — деление общего лимита зондов на число выбранных записей (`maxAllowZond / countmax`, независимо подтверждено в `client-combat-ui.md §9`)
- `protectshieldclass.as:128,130` (`price_silver × val` — стоимость восстановления N% защитного поля колонии серебром; аналогичный цикл по 5 ресурсам, `xmlparsers.as`-подтверждено в `client-combat-ui.md §8`)
- `DS_Classes/MN_Menu/MN_Cabinet/artefact_shop/artefact_shop_engine.as:333-335,601-628,715` (магазин артефактов личного кабинета — `g_price`/`s_price × count`, реальные Gold/Silver Credit)
- `build_menu.as` (стоимость постройки в GC/SC — подтверждено `client-economy-social-ui.md §1.7`; см. также открытое противоречие с `mechanics-buildings.md` в §6 ниже)

**Отправка на сервер** — проверено для каждого: `trainzondunit`/`load_pack_war_factory`/
`requestScan`/`buyArtInShop`/`restoreProtectionShield` — всюду только
id+количество(+валюта gold/silver), не вычисленная сумма (для
`artefact_shop_engine.as` явно проверено: `requestDataCabinet.buyArtInShop(arr_for_buy)`
шлёт `{id, life, count, concurency}`, без `total_price`, —
`DS_Classes/MN_Menu/MN_Cabinet/artefact_shop/artefact_shop_engine.as:281-295`).

### 2.4. Налог при продаже и коридор цены — `trade_menu_class.as`, `reincarnate.as`

Оба файла содержат один и тот же код (буквально дублирован — см. §3):

```as2
this.nalog = data_allow.taks                         // ставка налога от сервера (%)
price_total = count - Math.ceil(count * nalog / 100)  // предпросмотр "что получу после налога"
nalog_value = Math.ceil(count * nalog / 100)          // предпросмотр суммы налога
```
(`trade_menu_class.as:1093-1094`, `reincarnate.as:813-814`, продублировано ещё в двух местах каждого файла)

и коридор допустимой цены ордера:

```as2
max_price = total_price + (total_price * data_allow.max_order / 100)
min_price = total_price - (total_price * data_allow.min_order / 100)
```
(`trade_menu_class.as:990,993`, `reincarnate.as:708,711`)

**Важно**: `client-economy-social-ui.md §1.1` независимо подтверждает, что
формула коридора цены **дословно совпадает** с серверной
`GL_TradeCountMinAndMaxPrices` — то есть это не "клиент выдумывает своё
правило", а корректное зеркалирование серверной формулы для мгновенной
подсказки игроку.

**Отправка на сервер** (`trade_menu_class.as:1121,1213`,
`reqvestdata.sale(...)`): переменная `price`, которая реально уходит в XML
(`<sell ... price="..." .../>`), берётся **не** из `price_total`
(результата вычисления с налогом), а напрямую из поля ввода
`this._parent.priceTrade.getValue()` — то есть это цена, которую игрок сам
ввёл как цену лота, а не производная величина. Налог и коридор — чисто
информационные подсказки поверх пользовательского ввода; сервер применяет
налог уже после продажи. **Риска читерства нет** — но НЕ факт, что сервер
всегда мог по‑старому пересчитать `min_order`/`max_order`; при переносе эту
формулу стоит явно свести к серверной (уже сведена, см. выше) как
единственный источник истины.

Реальные значения `tax`/коридора на конкретном живом мире (не выдуманный
пример, а числа из БД) — см.
[mechanics-economy-trade.md §5.6](mechanics-economy-trade.md) (добавлено
2026-09-08): на «Сфере Ориона» налог сейчас ненулевой только для части
сделок «артефакт → валюта» (до 30%), обмен ресурсов/юнитов беспошлинный.

### 2.5. Кросс-ресурсный калькулятор обмена с наценкой — `trade_menu_class.as:470-525` (`drawcalc`)

Более сложная находка внутри того же файла — при выборе "обменять юнит/ресурс
X на ресурс Y" клиент считает эквивалентную стоимость сразу во всех 5
базовых ресурсах:

```as2
B1..B6 = количество каждого ресурса на quant единиц (из локальной библиотеки юнита)
CT1..CT5 = B_i * (1 + obj.nds / 100)                          // "цена с наценкой" (nds = НДС-подобная надбавка, от сервера)
SUM1 = Σ ( CT_i / obj.i{prod,nano,kad,stat,food}_val )          // сумма, приведённая к общей единице через курсы обмена
rprod/rkad/rnano/rstat/rfood = SUM1 * курс_соответствующего_ресурса  // та же сумма, выраженная в каждом ресурсе отдельно
```

`obj.nds` (надбавка) и `obj.i*_val` (курсы/веса ресурсов) — оба приходят от
сервера как часть данных панели, клиент не изобретает числа сам, только
формулу агрегации. Это, по всей видимости, клиентское отражение системы
"курсов" (`RECOUNT_COURSES_IN_NANO` — модификатор мира, см.
[mechanics-races-world-ranking.md §2.8](mechanics-races-world-ranking.md))
— предположение, точное соответствие не проверялось (вне периметра этой
задачи). **Отправка на сервер**: как и в §2.4, реально уходит только
пользовательский ввод (`priceTrade`), эта формула — вспомогательный
предпросмотр в том же окне.

### 2.6. Калькулятор допустимого количества при реинкарнации — `reincarnate_menu_class.as:636-653,996-1013`

```as2
function calcAmount(src, dat, prod, weight) {
    minn = 900000000
    for (T = 0; T < src.length; T++) {
        tempAM = Math.floor(src[T] / dat.power[T])   // по каждому из 5(+1) ресурсов — сколько юнитов "по деньгам"
        if (tempAM < minn) minn = tempAM
    }
    tempProd = Math.floor(prod / weight)             // по остатку "квоты продиумного веса" — сколько юнитов "по квоте"
    if (tempProd < minn) minn = tempProd
    return (minn == 900000000 || minn < 0) ? 0 : minn
}
```

Клиент заранее (до отправки) считает верхнюю границу количества юнитов
каждого типа, которое можно выбрать для реинкарнации — минимум из
"хватает ли ресурсов" и "укладывается ли в оставшуюся квоту продиумного
веса" (`fork.targetProdium`). **Важная находка, закрывающая вопрос из
задания**: строка `reincarnate_menu_class.as:758,1119` содержит буквальный
комментарий разработчика:

```as2
arr_obj.prodQ = Math.floor( Number(fork.targetProdium) / Number(array_units[i].prodiumWeight) )
    // Макс кол-во юнитов до восстановления 70% продиумНого веса
```

Это **независимое клиентское подтверждение** формулы "70% от меньшего из
счётчиков", которую документ
[mechanics-reincarnation.md](mechanics-reincarnation.md) описывает как
**единственную механику без опоры на код** (написана только по официальным
справочным страницам сайта). Сам процент (70%) и то, ЧТО именно является
базой для него, в клиенте не вычисляются — `fork.targetProdium` приходит уже
готовым числом от сервера (клиент только делит на вес юнита) — то есть
формулы "70%" в самом клиентском коде нет, но **факт использования именно
такой формулы разработчиком подтверждён их же комментарием**, что заметно
повышает доверие к формуле из `mechanics-reincarnation.md`. Рекомендуется
добавить перекрёстную ссылку на этот комментарий в `mechanics-reincarnation.md`
при следующей правке того документа (см. также §6.1 «Открытые вопросы»
`client-economy-social-ui.md`, которая ждёт именно серверного подтверждения —
теперь есть хотя бы независимое клиентское).

**Отправка на сервер**: `reqvestdata.getReincarnate(tempLst, "Res"/"Sera")`
шлёт строку вида `"id:count,id:count,..."` — только выбранные id и
количества, не расчётный `calcAmount()`. Риска нет.

### 2.7. Автономный "калькулятор армии" — `armycalcclass.as` (весь файл)

Отдельный, самостоятельный экран (вкладка `CALCULATOR`, доступна только
премиум-аккаунтам, подтверждено `client-economy-social-ui.md §1.1` для
аналогичной калькуляторной вкладки биржи) — **не отправляет вообще ни одной
команды создания армии**. Единственный `reqvestdata`-вызов в файле —
`call_tabs()` (переключение вкладки). Вся "стоимость" считается локально:

```as2
Rkad_prcK = power[0] * quant       // сумма по ресурсу на quant юнитов
kad_prcK  = prodiumWeight * quant * koeff[0]   // тот же объём, выраженный через "продиумный вес" и общий коэффициент конвертации
```

`power[]` (цена юнита по ресурсам) и `koeff` (см. также §2.8 про `SC`)
приходят от сервера при открытии панели (`<armycalculator koeff="..." >`) —
клиент не сочиняет числа, только считает суммы по уже выбранному
количеству. Это классический "dry-run"-калькулятор: игрок может сколько
угодно "прикидывать" состав армии без единого запроса к серверу. Полностью
воспроизводим на HTML5/JS формула-в-формулу, без каких-либо рисков — сервер
никогда не видит эти вычисления.

**Источник `koeff` — найден и подтверждён числами из БД (2026-09-08)**:
`PN_WarCalculator.class.php:21-30` строит `koeff` циклом по
`GB_ResourcesList::$allResources = ['KADERIUM', 'NANO_CRYSTAL',
'STASIS_ENERGY', 'FOOD', 'PRODIUM']` (жёстко заданный порядок и состав —
без `WORKER`), каждый элемент — `PRODIUM.exchangerate /
<ресурс>.exchangerate` (глобальная, не per-world, таблица `ds_resource`,
кэш `GLOBAL_CACHE`). Реальные `exchangerate` (одинаковые для всех миров):
`PRODIUM=10, NANO_CRYSTAL=4, KADERIUM=2, FOOD=1, STASIS_ENERGY=1,
WORKER=0`. Отсюда реальный `koeff` = `[5, 2.5, 10, 10, 1]` (в порядке
KADERIUM/NANO/STASIS/FOOD/PRODIUM). `WORKER.exchangerate=0` заметен, но
**не является багом деления на ноль** — `WORKER` в `$allResources` не
входит, поэтому в знаменателе `koeff` никогда не встречается.

### 2.8. Резолвнутый открытый вопрос — семантика `SC`/`GC` в `<armycalculator>`

`docs/client-combat-ui.md`, раздел «Открытые вопросы», **пункт 12**, ставил
вопрос: атрибут `price` юнита в `<armycalculator>` (`xmlparsers.as:1715-1717`)
имеет формат `"KA:v;NA:v;ST:v;FO:v;PR:v;SC:v"` — шестой ключ `SC` на один
элемент длиннее пяти базовых ресурсов (Kaderium/Nano/Stasis/Food/Prodium),
и что он означает — "не установлено ни из кода, ни из литеральных дампов".

**Резолвится этим проходом.** `SC` = `SILVER_CREDIT`, `GC` = `GOLD_CREDIT`
(обе — реальные внутриигровые валюты, а не ресурсы производства). Цепочка
доказательств:

1. `armycalcclass.as:160` — `currentRes[5] = debug.link.resourse_player["SILVER_CREDIT"].current` —
   индекс `[5]` в массиве текущих ресурсов игрока **буквально совпадает**
   по позиции с `case "SC": obj.power[5] = ...` в парсере
   (`xmlparsers.as:1715-1717`, `armyCalc`) — то есть шестой слот цены юнита
   и шестой слот "текущего запаса игрока" — один и тот же ресурс.
2. Более широкий парсер той же группы (постройка армии/зданий,
   `xmlparsers.as:2182-2187`) читает ключи `SC`/`GC` рядом друг с другом:
   `case "SC": obj.power[5] = ...; case "GC": obj.power[6] = ...` —
   подтверждает, что `SC` и `GC` — два разных, соседних ключа одной системы
   обозначений, а не опечатка/дубль.
3. `build_menu.as:97,127,130,151-152` использует буквально те же
   двухбуквенные ключи как поля объекта постройки (`list_build_array[i]["GC"]`,
   `["SC"]`) и сравнивает их напрямую с
   `debug.link.resourse_player.GOLD_CREDIT.current` /
   `.SILVER_CREDIT.current` — то есть **тот же самый код** явно
   отождествляет `GC`↔`GOLD_CREDIT` и `SC`↔`SILVER_CREDIT` для соседнего,
   но однотипного экрана (стоимость постройки).
4. `xmlparsers.as:2616-2617` (парсер списка построек) делает то же сравнение
   ещё раз: `if (!isNaN(list_build[...].SC) && Number(list_build[...].SC) >
   Number(debug.link.resourse_player.SILVER_CREDIT.current)) ... allow = false`.

Итого: `SC`/`GC` в `<armycalculator>` — это не шестой "секретный" ресурс
производства, а стандартные премиум-валюты игры (Silver Credit — игровое
серебро, зарабатываемое; Gold Credit — донат-валюta), появляющиеся в
разбивке цены юнита ровно там же, где они появляются в разбивке цены
постройки. Рекомендуется отметить это как закрытый пункт 12 при следующей
правке `client-combat-ui.md`.

### 2.9. Конвертация валюты соцсети (VK/POP) — единственная находка, где вычисление реально денежное

`DS_KONTAKT_MODULE/VKGATE.as:407-412` и `DS_KONTAKT_MODULE/POPGATE.as:298-305`
— функция `calcVotes()`, вызывается при пополнении баланса Gold/Silver
Credit через соцсеть (кнопка "Пополнить"):

```as2
// VKGATE.as
function calcVotes(){
    return Math.round( GCR * (1/_level0.currencyrate) * 100 ) / 100
         + Math.floor( SCR * (1/_level0.currencyrate) ) / _level0.silvercourse
}
// POPGATE.as
function calcVotes(){
    return GCR * _level0.currencyrate + Math.floor( SCR * _level0.currencyrate / _level0.gc_course )
}
```

где `GCR`/`SCR` — запрошенное игроком количество Gold/Silver Credit, а
`_level0.currencyrate`/`_level0.silvercourse`/`_level0.gc_course` — курсы
обмена. Результат передаётся в `apiCon.showPaymentBox(сумма)` — то есть
**это число реально определяет, сколько "голосов"/внутренней валюты
платформы (VKontakte/POPMOG) откроется в платёжном окне соцсети для
оплаты**. Формально это **не** протокол `useraction.php` (не идёт через
`reqvestdata`/XML на игровой сервер) — отдельный канал, внешний платёжный
SDK соцсети — поэтому вопрос "перепроверяет ли сервер" здесь звучит иначе:
реальные деньги списывает сама соцсеть по её собственной цене, а игровой
сервер, по общей практике таких интеграций (см.
[billing-and-monetization.md](billing-and-monetization.md)), должен
доверять только асинхронному колбэку/вебхуку от соцсети о факте оплаты, а
не значению, вычисленному в этом клиенте — то есть корректность именно этой
формулы влияет только на UX (не ошибиться в сумме для игрока), а не на
безопасность начисления.

**Дополнительная находка**: `VKGATE.as:42` содержит захардкоженное значение
по умолчанию `var currencyrate = 5 // Курс - кол-во золотых за 1 голос` —
устанавливается до того, как (если) `_level0.currencyrate` будет
переопределён сервером/окружением; неясно, переопределяется ли оно всегда
на практике или это иногда живой fallback-курс (не проверялось — вне
периметра клиентского кода).

## 5. Что отправляется обратно на сервер — сводная проверка на читерство

Проверено **каждое** место категории (В) из §2 на предмет "уходит ли
вычисленное клиентом число в `reqvestdata`/XML команду без пересчёта на
сервере". Результат один и тот же везде:

| Формула (§) | Команда отправки | Что реально уходит |
|---|---|---|
| Прогрессивная цена зонда (2.1) | `trainzondunit(count, id)` | Только `count`+`id` |
| Время производства ×9 (2.2) | `load_pack_war_factory`/`trainWarUnit`/наём/`send_zond`/`powershieldenabled`/`sale` | `count`/`id`/выбранное игроком время в ходах — не готовое человекочитаемое время |
| Цена×количество ×7 (2.3) | `trainzondunit`/`load_pack_war_factory`/`requestScan`/`buyArtInShop`/`restoreProtectionShield`/постройка | `id`/`count`(/валюта), не сумма |
| Налог+коридор цены (2.4) | `sale(...)` | `price` = сырой пользовательский ввод (`priceTrade.getValue()`), не `price_total` |
| Кросс-ресурсный калькулятор (2.5) | (та же `sale`) | То же — вспомогательный предпросмотр в том же окне |
| Калькулятор реинкарнации (2.6) | `getReincarnate(list, mode)` | Список `id:count`, без стоимости |
| Калькулятор армии (2.7) | — | **Ничего не отправляется вообще** (только просмотр) |
| Конвертация валюты соцсети (2.9) | `apiCon.showPaymentBox(sum)` | Реальная денежная сумма — но это **внешний** платёжный SDK соцсети, не игровой протокол; фактическое списание/начисление, по общей практике таких интеграций, должно проверяться игровым сервером отдельно (асинхронный колбэк от соцсети), а не по этому клиентскому значению |

**Вывод: специфического вектора читерства через "клиент считает — сервер
слепо верит" в разобранных 128 файлах не найдено.** Единственное место,
где в XML реально уходит цена (`<sell price="...">`), — это прямой,
неизменённый пользовательский ввод, а не результат клиентской формулы; само
по себе это не уязвимость (игрок и так волен указать любую цену продажи —
вопрос в её последующей проверке сервером, что вне периметра клиентского
кода).

## 6. Прочие примечательные находки (вне схемы А/Б/В)

### 6.1. `DS_ANALYZER/analiz.as` — захардкоженная таблица баланса всех юнитов

Отдельный, не связанный с обычным игровым UI класс (AS3, `class analiz
extends MovieClip`) — целиком состоит из (а) статического массива
`all_unit[0..65]`, по одной строке на каждый из 66 юнитов игры, с
захардкоженными числами: стоимость по ресурсам, время, атака/защита,
несколько **уже посчитанных** производных коэффициентов эффективности
("эффективность юнита в атаке на ресурс", "эффективность защиты на 100%
сожжённого продиума" и т.п. — судя по русским подписям в
`primechanie_ar[]`, `analiz.as:36`, использующим тот же коэффициент
конверсии продиума `5-2.5-10-1-1`, что и `koeff` в `armycalcclass.as`,
§2.7); и (б) чисто UI-кода для сортируемой таблицы-браузера этих данных
(позиционирование строк по 47px, сортировка по клику на заголовок столбца).

Сами коэффициенты эффективности **не пересчитываются в этом файле** —
похоже, что они посчитаны один раз офлайн (разработчиком, в момент
балансировки игры) и просто вставлены как константы. То есть это не
"формула" в смысле категории (В) (нет живого вычисления по актуальным
данным сервера), а скорее **случайно попавший в клиентскую сборку
инструмент разработчика для анализа баланса юнитов** — судя по имени файла
и каталога (`DS_ANALYZER`), пути `analiz.as`, и по тому, что подобный экран
не встречается ни в одном игровом меню/панели из остальных 127 файлов.

**Ценность находки для ремастера**: это, по всей видимости, единственное
место во всём клиенте, где сведены воедино полные боевые/ресурсные
характеристики всех 66 юнитов игры одним снимком — потенциально ценный
источник калибровочных чисел для восстановления баланса в новом клиенте
(с оговоркой "предположительно" — не подтверждено, что это актуальный на
момент архивации набор чисел, а не более старый снимок баланса).

### 6.2. `build_menu.as` — расхождение с `mechanics-buildings.md`

Уже зафиксировано в `client-economy-social-ui.md §6` (открытый вопрос №4):
`build_menu.as` показывает GC/SC-стоимость постройки (см. §2.3, §2.8 выше),
но `mechanics-buildings.md §2.3` утверждает, что списание денег за постройку
не реализовано на сервере (`UA_ConstructBuilding` — заглушка). Этот проход
не добавляет новых данных к этому противоречию (вне периметра — требует
чтения PHP), но подтверждает, что клиентский код действительно и
безусловно ожидает возможность списания GC/SC за постройку — то есть либо
это мёртвая клиентская фича, либо списание реализовано где-то ещё, не
найденном при чтении `mechanics-buildings.md`.

### 6.3. `src/Main.as` не определяет `debug.link`

`docs/README.md`, раздел "Находки этой сессии, требующие доследования",
отмечал: `debug.link` используется по всему клиенту как глобальный
"бог-объект", но нигде не определяется в разобранных файлах, и что
`src/Main.as` "ни разу не открывался ни в одном из проходов" — наиболее
вероятный кандидат.

**Проверено в этом проходе — гипотеза не подтвердилась.**
`src/Main.as` — тривиальный пустой AS3 document-class stub (`class Main
extends Sprite`, метод `init()` буквально содержит только комментарий
`// entry point`, 26 строк всего). Он **не** определяет `debug.link` и
вообще не содержит ни одной строки логики. Более того, это AS3-код
(`import flash.display.Sprite`), тогда как весь остальной клиент — AS2
(`class X extends window` без `package`/`import`) — то есть `Main.as`,
похоже, принадлежит отдельному, не связанному с основным игровым SWF
эксперименту/заготовке (или более позднему недоделанному переходу на AS3),
а не является точкой входа игры. Источник `debug.link` по-прежнему не
найден нигде в переданном наборе файлов — вопрос в `docs/README.md`
остаётся открытым, но с одной проверенной и исключённой гипотезой.

## 8. Открытые вопросы

1. **Формула §2.5 (кросс-ресурсный калькулятор с `nds`/курсами) не сведена

## 9. Выводы для переноса на HTML5/JS

**Переносить формула-в-формулу (это реальная игровая математика, пусть и
только для предпросмотра):**
- Прогрессивная цена зондов (§2.1) — единственная нелинейная формула во
  всём клиенте, стоит реализовать как отдельную переиспользуемую функцию.
- `turnToTime`-паттерн (§2.2) — единственный формат времени, используемый в
  9 разных панелях; имеет смысл вынести в общий модуль один раз, а не
  копировать 9 раз, как это сделано в оригинале.
- Формулу коридора цены ордера (§2.4) — она **уже подтверждённо совпадает**
  с серверной `GL_TradeCountMinAndMaxPrices`
  (`client-economy-social-ui.md §1.1`), так что перенос сводится к тому,
  чтобы взять её из серверного описания, а не reverse-engineer'ить из
  клиента заново.
- Калькулятор допустимого количества при реинкарнации (§2.6) и
  "калькулятор армии" (§2.7) — не влияют на сервер, но являются заметной,
  ожидаемой игроками UX-функциональностью ("сколько я могу себе позволить
  прямо сейчас") — их отсутствие в ремастере будет заметным регрессом
  для опытных игроков.

**Можно упростить или переделать, поскольку сервер всё равно пересчитывает
всё заново (§5):**
- Все 7 находок "цена×количество" (§2.3) и налоговый предпросмотр (§2.4) —
  тривиальная арифметика для UX; в новом клиенте можно реализовать проще
  (например, единым переиспользуемым UI-компонентом "предпросмотр
  стоимости"), не обязательно копируя структуру кода 1:1, лишь бы конечный
  результат совпадал по числам с тем, что реально спишет сервер.
- Кросс-ресурсный калькулятор (§2.5) можно не переносить дословно, если
  цель ремастера — не 100% воспроизведение специфичного UX старой биржи, а
  разумный минимум (показ цены и остатка ресурсов); это самый сложный по
  формуле, но наименее критичный по геймплейному значению узел.
- Конвертер валюты соцсети (§2.9) в текущем виде не актуален для ремастера
  (другая платформа, другие партнёры) — формула пересчёта учит только
  общему паттерну "конвертация внешней валюты в игровую перед вызовом
  платёжного SDK", сам код переносить незачем.

**Не переносить вообще:**
- `DS_ANALYZER/analiz.as` (§6.1) — это инструмент разработчика, случайно
  попавший в клиентскую сборку, а не часть игры; его данные, впрочем, стоит
  сохранить как справочный материал для калибровки баланса нового клиента.
- Все находки категории (А) — UI-тулкит (`window.as`), рендеринг сетки
  (`sota.as`), позиционирование, анимации, цветовые градиенты чата — это
  прямая, тривиальная зона ответственности CSS/DOM/canvas в новом клиенте,
  без риска для игровой логики.

**Главный практический вывод для проекта**: объём реальной игровой
логики, встроенной в Flash-клиент, **оказался небольшим** — 20 файлов из
128, и ни одна из формул не является source-of-truth (сервер всюду
пересчитывает сам). Это заметно снижает риск переноса AS2 → HTML5/JS по
сравнению с пессимистичным сценарием "клиент считает бой/экономику сам,
сервер слепо доверяет" — такого нигде не найдено. Основная работа при
переносе — не в реверс-инжиниринге скрытых игровых правил, а в
аккуратном воспроизведении **UX-паттернов предпросмотра** (§9 выше), чтобы
у игроков не создавалось впечатление регресса привычного интерфейса.
