## 1. Главный вывод: `sota.as` рисует ОДНУ соту игрока, не карту мира

«Сота» (от рус. «соты» = пчелиные соты, honeycomb) — это, как и предполагало
название, гексагональная сетка. Но `sota.as` **не рисует карту мира со
множеством чужих колоний**. Он рисует **гексагональную сетку одной
конкретной соты** (домашней/центральной/нейтральной части владения одного
игрока) — экран строительства, на который смотрит сам владелец. Отдельная,
гораздо более простая функция в том же файле (`fillComplex`/`createComplex`,
§7) рисует «локальную карту» — 6 сот комплекса + врата между ними — но это
статичная художественная сцена без координатной геометрии.

`colonynavigate.as` — это third-party к сетке: **список окошком**, а не
карта. Он показывает список **своих** колоний (`colony_array`) с кнопками
«перейти»/«оставить»/«показать военную базу» и не содержит вообще никакой
координатной/пиксельной математики — см. §7.2. Формулировка задачи
ожидала, что это «навигация между колониями» в пространственном смысле —
по коду это не так: это просто модальное окно-меню.

## 2. Иерархия мира (сверка с сервером)

Подтверждено кодом сервера (`docs/mechanics-races-world-ranking.md` §1,
`WorldUtils.class.php`, `DS_Ring`/`DS_CombComplex`/`DS_Comb`/`DS_Cell`) и
буквально совпадает с параметром `location` в клиенте:

```
Мир (DS_World)
 └─ Кольцо (DS_Ring)                        — sota.as: ring
     └─ Комплекс сот (DS_CombComplex)       — sota.as: complex / комплекс = 6 сот + врата
         └─ Сота (DS_Comb, ровно 6 на комплекс, combnumber 1-6)
             └─ 3 "вида" ячеек (id_celltype), каждый — отдельная 217-слотовая сетка:
                 ├─ celltype=1 "HOME"     — sota.as: location=="HOME",     217 реальных ячеек
                 ├─ celltype=2 "CENTRAL"  — sota.as: location=="CENTRAL",  217 слотов, но только
                 │                          28 реально принадлежат этой соте (см. §6)
                 └─ celltype=3 "NEUTRAL"  — sota.as: location=="NEUTRAL",  217 реальных ячеек
```

Таким образом, у одного игрока-владельца соты **три отдельных гексагональных
поля** (HOME/CENTRAL/NEUTRAL), каждое — отдельный вызов `sota.create(addr,
location)`, и они не показываются одновременно на экране (переключение —
через открытие ворот, `debug.link.gate`, см. `parser.as:876`).

Адрес соты в протоколе — строка вида `"кольцо.комплекс.номер_соты"`
(например `"1.1.2"`, см. `colonynavigate.txt` — тестовая XML-заглушка,
атрибут `coords`, и `mov_data.SOTA_NUMBER.text = ring + "." + complex + "."
+ complexarr[i].num` в `sota.as:1259`). Этот же адрес — `id_comb`
(`addr` в `sota.as`).

## 3. Система координат ячеек внутри одной соты

### 3.1. Линейный индекс, не axial/offset-координаты

Клетки внутри одной 217-слотовой соты адресуются **единственным линейным
индексом `num`** (0..216). Никакой отдельной (q,r) / offset-структуры
координат **в клиенте не хранится** — `num` присваивается строго в порядке
двойного цикла построения сетки (`sota.as:407-491`, функция
`create_Sota`/`paintSota`), и именно этот порядок задаёт положение ячейки в
пространстве. Чтобы получить экранные координаты по `num`, нужно
воспроизвести тот же самый цикл (см. §3.3) — обратного словаря
"num → (row, col)" в коде нет, он неявный.

### 3.2. Форма сетки — правильный гексагон из 217 гексагональных ячеек

```as
static var h = 24;   // "Default weight cell (horizontal)"
static var v = 13;   // "Default height cell (vertical)"
```
(`sota.as:5-6`)

Сама ячейка рисуется как гексагон с вершинами (`sota.as:68-88`,
`createSample`, аргументы `sizeX=h`, `sizeY=v`):

```
(h,0) → (2h,0.5v) → (2h,1.5v) → (h,2v) → (0,1.5v) → (0,0.5v) → (h,0)
```

Т.е. **плоские левая/правая грани, острые вершины сверху и снизу**
(pointy-top гексагон в стандартной терминологии hex-grid). Bounding box
одной ячейки — `2h=48 × 2v=26` пикселей.

Полная сота строится вложенным циклом (`sota.as:425-488`) на `lengthSide=9`:
17 рядов (`i = 0..16`), с длиной ряда `lengthSide+NN`, где `NN` растёт
`0→8` для первых 9 рядов и убывает `8→0` для последних 9 (с общим рядом
`i=8`, `NN=8`, длина 17 — средний, самый широкий ряд). Суммарно
`9+10+…+17+…+10+9 = 217` ячеек — это классический «гексагон из гексагонов»
с радиусом (числом ячеек на сторону) = 9. Отсюда и захардкоженная проверка
длины строки грунта: `sota_str.length != 217` (`sota.as:578,633`) —
**217 — не произвольное число, это `3·9² − 3·9 + 1`** для радиуса 9.

### 3.3. Формула пиксельных координат ячейки (маска/грунт)

```as
var num=0, lengthSide=9, NN=0, dNN=1;
for (i = 0; i < lengthSide*2-1; i++) {        // i = 0..16 — ряд
    for (j = 0; j < lengthSide+NN; j++) {     // j = 0..(lengthSide+NN-1) — столбец в ряду
        obj_._x = (j*2 - NN + (lengthSide-1)) * h;
        obj_._y = (i*1.5) * v;
        // ... num++
    }
    if (i < lengthSide-1) dNN = 1; else dNN = -1;
    NN += dNN;
}
```
(`sota.as:434-487`, переменные названы как в оригинале)

Это стандартная раскладка pointy-top гексагонов рядами: по вертикали шаг
`1.5·v` на ряд, по горизонтали шаг `2·h` на ячейку с центрированием
`-NN+(lengthSide-1)` (более широкие средние ряды сдвинуты левее, чтобы
сетка была центрирована). **Без зума/масштаба** — это координаты в
локальном пространстве клипа `sota_mov` при масштабе 1:1; масштабирование
всей соты (если есть) — на уровне родительского клипа, не внутри этой
формулы.

Итоговый размер прямоугольника всей соты (`sota.as:431-432`):
```
width_movie  = (lengthSide-1 + lengthSide) * 2 * h   = 17*2*24 = 816
height_movie = (lengthSide*2-1) * 1.5*v + 0.5*v       = 17*1.5*13+6.5 = 338
```

### 3.4. Якорь построек — не то же самое, что якорь грунта

Для ячеек, где есть здания (`obj.build_mov != undefined`), координаты
здания **отдельно** пересчитываются со сдвигом от координат маски грунта
(`sota.as:465-471`):

```as
obj.coord[num].x = obj_._x + sota.h;       // горизонтальный центр гексагона
obj.coord[num].y = obj_._y + sota.v * 2;   // НИЖНЯЯ вершина гексагона (не центр!)
```

Т.е. здание позиционируется по **нижней точке своей ячейки** (типично для
спрайтов "ноги у основания"), а не по центру. При отрисовке в PixiJS нужно
либо ставить якорь спрайта здания в его нижнюю центральную точку, либо
явно вычитать половину высоты спрайта после позиционирования по этой
формуле.

Масштаб построек — динамический, не константа:
```as
buildRescale = game.check_build_size();   // sota.as:46, метод не в этих 2 файлах
...
building._xscale = building._yscale = buildRescale * 100;
building._y -= v - v*buildRescale;        // компенсация сдвига, чтобы низ остался на месте
```
(`sota.as:894-895`) — `game.check_build_size()` не разбирался в рамках этой
задачи (не в `sota.as`/`colonynavigate.as`); **не установлено**, от чего
зависит (вероятно — настройка «отдалённый вид»/пресет масштаба построек,
судя по названию).

### 3.5. Соседние «соты-заглушки» — фиксированные смещения, не формула

Вокруг домашней соты игрока `createsotasos` (`sota.as:286-405`) достраивает
**6 соседних сот-заглушек** (не настоящие данные соседей — статичный
декоративный фон, чтобы сота не «висела в пустоте», см. §6.3) со
захардкоженными пиксельными смещениями (не выводятся формулой в этих
файлах):

| `icount` | Смещение (`_x`,`_y`) | Направление (условно) |
|---|---|---|
| 0 | (-24, -333) | сверху |
| 1 | (-625, -157) | сверху-слева |
| 2 | (-601, 176) | снизу-слева |
| 3 | (24, 333) | снизу |
| 4 | (625, 157) | снизу-справа |
| 5 | (601, -176) | сверху-справа |

(`sota.as:379-403`) — образуют «розетку» из 7 больших гексагональных
блоков (центр + 6 соседей). Величины кратны примерно половине размеров
`width_movie`/`height_movie` из §3.3, но точная формула получения этих
констант в коде не приведена — **предположительно** подобраны вручную под
конкретные `h`/`v`/`lengthSide`, чтобы грани смежных сот визуально
стыковались.

## 4. Откуда берутся данные для отрисовки (сверка с протоколом)

Полностью подтверждено чтением `parser.as:872-1035` (`refresh_action`) —
это единственное место, которое строит `sota_str`/`build_arr`, передаваемые
в `sota.create()`. Дополняет (не противоречит) то, что уже кратко отмечено
в `docs/client-engine-and-protocol.md` §5 про mark `refresh`.

### 4.1. XML верхнего уровня — mark `refresh`

```xml
<refresh id_comb="ADDR" gate="0|1" location="HOME|NEUTRAL|CENTRAL">
    <sota>217-символьная строка типов грунта</sota>
    <build>сплиттер-разделённые поля построек</build>
</refresh>
```

- `id_comb` → `addr` (адрес соты)
- `gate` → флаг «врата открыты» (кэшируется в `setting`, читается
  `debug.link.gate`)
- `location` → `"HOME"`/`"NEUTRAL"`/`"CENTRAL"` (см. §2) **или** `"COMPLEX"`
  (отдельная ветка, §4.3) — если `location` не задан вовсе, это
  расценивается как ошибка сервера (`parser.as:924-926`)

Тот же самый разбор (`refresh_action`) переиспользуется для входящего mark
`combcomplex` внутри `xmldata` — код в `parser.as:1515-1520` просто
дописывает атрибут `location="COMPLEX"` в XML-строку и заново вызывает
`refresh_action` — то есть один парсер обслуживает два разных пути
доставки.

### 4.2. Грунт — `<sota>` — 217-символьная строка

Каждый символ — код первой буквы типа грунта (`sota.as:8`,
`array_names`), индекс символа = `num`:

| Символ | Линковочное имя (Flash) | Терраформируемый? (сервер, `ds_groundtype`/`ds_terraforming`) |
|---|---|---|
| `W` | `WATER` | да |
| `G` | `GRASS` | да |
| `S` | `SOIL` | да |
| `D` | `DESERT` | да |
| `E` | `E_FIELD` | **нет** — не ячейка ландшафта, см. §6 |
| `F` | `FROG` | **нет** — не ячейка ландшафта, см. §6 |
| `R` | `ROCK` | не найден в `ds_terraforming` (см. `mechanics-npc-terraforming.md`) |

Клиент валидирует длину: если `sota_str.length != 217` — ошибка
(`sota.as:578,584`, `parser.as:957` проверяет `> 216` перед сохранением в
кэш).

### 4.3. Постройки — `<build>` — плоский список через сплиттер

`parser.as:964-1025`: `xmlbuild` — строка, разбитая `split(spliter)` на
плоский массив полей. Каждая запись переменной длины (первое число —
`length_`, определяет сколько дальше полей читать):

```
length, num, id, art, [status], [beginbuild|endbuild упаковано через "|", date_end], [desc]
```

- `num` — индекс ячейки (совпадает с `num` из сетки грунта, 0-based)
- `id` — id типа здания
- `art` — предположительно арт/иконка (не используется в разборе `sota.as`
  напрямую под этим именем — используется `build[i].id`/`build_data_obj.A`)
- `status` — код состояния постройки (использует `sota.as:830-884`,
  таблица в §5.2 ниже)
- `beginbuild`/`endbuild` — таймстемпы для клиентского пересчёта процента
  строительства (см. §5.1, там же и в `parser.as:989-1011` — **этот же**
  расчёт процента уже выполняется один раз при разборе `parser.as`, но
  `sota.as` независимо пересчитывает его заново в реальном времени, см.
  ниже)
- `desc`/`desk` — опциональное текстовое описание

### 4.4. Комплекс (`location=="COMPLEX"`) — отдельная XML-структура

```xml
<refresh location="COMPLEX" ring=".." number=".." VKONTAKTE="..">
    <comb .../> ×6           <!-- атрибуты читаются как есть в fillComplex -->
    <rings><ring .../>...</rings>
</refresh>
```
(`parser.as:885-917`) — каждый дочерний `<comb>` даёт объект с полями,
реально прочитанными в `sota.as` (`fillComplex`, `sota.as:1013-1608`):
`num`, `home`, `samealliance`, `gate`, `sms`, `premic`, `league`, `cname`,
`uname`, `cscore`, `alliance`, `avatar`, `urlpic`, `race`, `cban`, `freez`,
`godpro`, `captured`, `npc`, `newbee`, `VKUID`, `warbase`. Кэшируется в
`setting` под ключом `"ring"+ring+"complex"+complex` (категория `"world"`).

## 5. Категория (В) — реальная логика/формулы в этих двух файлах

### 5.1. `MEGAPROGRESSBAR` — живой пересчёт процента стройки на клиенте

`sota.as:742-787`. Для каждой строящейся/активируемой/апгрейдящейся
постройки создаётся `onEnterFrame`-таймер (тикает не каждый кадр — раз в
25 кадров, `mov.CNT`), который **на клиенте** пересчитывает процент
готовности по времени сервера:

```as
var curr = game.getServerTime();
var proc = 100 - Math.floor( (end - curr.valueOf()) / (end - strt) * 10000 ) / 100;
```

где `strt`/`end` — это `build[i].beginbuild`/`build[i].endbuild`,
переданные сервером один раз при `refresh`. Это **второй, независимый**
расчёт того же самого процента, что уже один раз вычисляется в
`parser.as:989-1011` при разборе XML (там — статичное значение на момент
получения ответа) — здесь же значение **живое**, обновляется каждый тик,
без повторных запросов к серверу, чисто линейная интерполяция по времени.
Кандидат для `docs/client-side-computed-logic.md` — линейная интерполяция
прогресс-бара `(currentTime - begin) / (end - begin)`, не встречалась там
раньше именно в этой форме (для сравнения: `parser.as` уже содержит
почти идентичную формулу, но однократную, не тикающую).

Дополнительно строка `resproc` собирается вручную конкатенацией целой и
дробной части (`sota.as:759-768`) — не `toFixed()` (не факт, что был
доступен/использовался в этой версии AS2), просто ручная сборка через
`substr`.

### 5.2. Гексагональная геометрия (§3) — генерируемая, не табличная

Формулы §3.2-3.3 (позиции ячеек, размеры bounding box соты) — это
единственная в файле геометрическая логика, вычисляемая на клиенте, а не
присланная сервером. Это прямое совпадение с уже отмеченным в
`docs/client-side-computed-logic.md:497` пунктом «`sota.as` | А |
Отрисовка гексагональной сетки» — но в том документе это не было
расписано формулами; в этом отчёте (§3) — расписано полностью.

### 5.3. `c = num + 1` — конверсия индекса при отправке на сервер

`reqvestdata.as:167`: `cell_click(id_cell)` отправляет
`c="` + (Number(id_cell)+1) + `"` — то есть **внутренний 0-based индекс
`num` (0..216) конвертируется в 1-based номер ячейки `c` (1..217) только
в момент отправки**. Атрибут `c` уже был надёжно подтверждён в
`docs/client-combat-ui.md` §0.2 с другой стороны (через
`debug.link.active_cell`) — этот отчёт подтверждает его происхождение и
конвертацию индекса. **Важно для порта**: PixiJS-рендерер, скорее всего,
будет держать те же 0-based индексы внутри (совпадает с порядком разбора
строки грунта из §3.1), конвертация в 1-based нужна только на границе
с сетевым слоем.

Batch-версия `cell_click_m` (`reqvestdata.as:174-182`, множественная
стройка) отправляет `c` **без +1** — просто список номеров через запятую,
уже 1-based на входе (`amountSelectedstring()`, `sota.as:116-122`, тоже
делает `Number(SELT)+1`). Несогласованность в имени, но по факту оба пути
итогово шлют 1-based номера.

### 5.4. Мультивыбор ячеек (SHIFT/CTRL) — наполовину готовая премиум-фича

`sota.as:194-279` — при зажатом `SHIFT` клик добавляет ячейку (того же
типа грунта, что и первая выбранная, и не занятую постройкой) в массив
`select[]`, при `CTRL` — снимает выбор. По накоплении выбора кнопка
отправляет `reqvestdata.cell_click_m(amountSelectedstring())` — то есть
**один запрос на пакетную стройку сразу нескольких одинаковых по грунту
ячеек**. Вся ветка обёрнута условием `game.getPremium() && debug.link.SWITHC`
(`sota.as:199`) — `SWITHC`-флаг живёт на `debug.link`, а не как объявленное
статическое поле `sota` (само поле `static var SWITHC` закомментировано,
`sota.as:31`, с комментарием «Выключить до поры пока введем. Код-то уже
есть. А пока там все просрутся...») — то есть это признанный самими
разработчиками недоделанный/выключенный функционал. **Не установлено**,
включён ли `debug.link.SWITHC` где-либо в живом коде за пределами этих
двух файлов.

## 6. `E_FIELD` и `FROG` — разгадка (закрывает открытый вопрос из `CLIENT_PORTING_PLAN.md`)

Открытый вопрос плана (Фаза 0, «не установлено, что означают линковочные
имена `E_FIELD`/`FROG`») **закрыт с высокой уверенностью** — сходятся два
независимых источника:

**Клиент (`sota.as`).** Ячейки с грунтом `F` и `E` **никогда не получают
`init_cell`** (`sota.as:480`: `if ((ground.charAt(num) != "F") &&
(ground.charAt(num) != "E")) init_cell(...)`) — то есть они не кликабельны,
без hint, без возможности постройки. Плейсхолдер-строка для полностью
неизвестной соседней соты (`unknown_loopback`, `sota.as:22`) состоит **из
217 символов `F` целиком**. `center_loopback` (используется как заглушка
самого центра карты, `sota.as:19`) — преимущественно `F` с редкими
кластерами `E`/`S`/`R` — то есть художественно «в основном туман, местами
граница/скала».

**Сервер (`GB_CombCentralViewMask.class.php:12-24`, подтверждено дословно
в `docs/mechanics-races-world-ranking.md` §1.4).** Для **центрального**
вида соты (`celltype=2`, 28 реальных ячеек из 217 слотов мозаики) сервер
использует ровно эти три буквы как легенду маски:

- **`E`** — граница между секторами разных сот комплекса
- **`F`** — туман, скрывающий чужие соты комплекса (те 189 слотов, которые
  не принадлежат текущему игроку)
- **`Z`** — ячейка **своей** соты (ровно 28 штук) — на эти слоты сервер
  подставляет настоящий тип грунта (`W`/`G`/`S`/`D`/`R`), поэтому в
  `array_names` клиента буквы `Z` нет вообще — к моменту отрисовки `Z`-слоты
  уже заменены на обычный код грунта.

**Вывод:** `E_FIELD` и `FROG` — это не «типы ландшафта» в игровом смысле
(не терраформируются, отсутствуют в `ds_terraforming`, §4.2), а **два
служебных ассета-заливки**, которыми клиент рисует техническую разметку
мозаики центрального вида: `E_FIELD` — графика границы между секторами
соседних сот, `FROG` — графика тумана поверх чужой территории (и, отдельно,
общий приём для «неизвестной пока соты» в §3.5). Название `FROG`
(«лягушка») по смыслу не связано с туманом — **предположительно** это
исторический артефакт/внутренняя шутка нейминга ассета (аналогично другим
не-описательным именам в этом кодовой базе), а не игровой термин; смысл
устанавливается по функции, не по слову.

## 7. Что рисуют оба файла — сводно, для оценки объёма порта на PixiJS

### 7.1. `sota.as`

| Функция/область | Что делает | Формула/данные |
|---|---|---|
| `create()` (`:532-696`) | Точка входа: грузит/кэширует `sota_str`+`build_arr`, инициирует отрисовку | §4.1-4.3 |
| `create_Sota`/`paintSota` (`:407-491`) | Строит 217 гексагональных масок с грунтом + числовой дебаг-оверлей (`obj.number_mov`, только для разработки) | §3.2-3.3 |
| `createBuilds`/`cb` (`:713-1005`) | Расставляет спрайты построек по `coord[num]`, статус-оверлеи, тени, анимация "случайное здание раз в ~30 кадров" (`arr_anim`, `:956-980`) | §3.4, таблица статусов §5.1 |

геометрией. «Комплекс» (§3.5, `fillComplex`) — это просто набор из 6
именованных слотов с фиксированными экранными координатами (взять из
самого SWF/библиотеки при экспорте ассетов, не из этого `.as`) плюс логика
раскраски/иконок по данным.

### 7.2. `colonynavigate.as`

Полностью список-меню, без сетки:
- `colonynavigate()` (`:170-189`) — грузит библиотеку построек (для иконки

  `PN_ColonyNavigatePanel.class.php`)

## 8. Прочие находки

- **Отключённая загрузка `grounds.swf` извне.** `sota.as:500-519` — целый
  блок кода, который догружал бы текстуры грунта отдельным `.swf`-файлом
  через `loader`, закомментирован с явным комментарием «ЗАГРУЗКУ
  ПОВЕРХНОСТЕЙ ИЗ ВНЕШНЕГО СВФ-а отключаем НАХУЙ!!!!!!!!!!! и аттачим их
  из ds3.swf». То есть на момент этой версии клиента ассеты грунта уже
  встроены в основной `ds3.swf`, а не подгружаются отдельно — расходится с
  наивным предположением, что `grounds.swf` (найденный и разобранный в
  Фазе 0) обязательно используется рантаймом; возможно, это устаревший
  отдельный файл или ресурс для другого способа сборки. **Не установлено**,
  используется ли `grounds.swf` где-то ещё в актуальном пайплайне сборки.
- **`rotate_sota()` — мёртвый код, наполовину реализованный.**
  `sota.as:1673-1711`: функция для поворота 217-символьной строки грунта на
  60°×N нигде не вызывается (проверено `grep` по всему `SPHERE_client/`).
  Реализован только разворот на 180° (`angle==3`, простой реверс строки —
  математически корректно для этой симметричной гексагональной раскладки);
  для 60°/120°/240°/300° функция просто возвращает исходную строку без
  изменений — то есть заготовка под визуальный поворот соседних сот
  по стороне соты, где реализована только тривиальная часть.
- **`array_opened`** (`sota.as:10,612,715`) — статический массив, в который
  каждый вызов `create()`/`createBuilds()` добавляет ссылку на `mov` через
  `array_opened[array_opened.length] = mov`, но нигде не очищается/не
  удаляет старые записи — **предположительно** не критичная утечка (обычно
  ссылка на один и тот же переиспользуемый `debug.link.sota_main`), но
  массив растёт на каждое открытие соты за игровую сессию.
- **Дубликат `Копия sota.as`** — уже разобран в предыдущем проходе
  (`docs/client-engine-and-protocol.md` §8.4, `docs/client-side-computed-logic.md:381,496-497`):
  старый снимок (1455 строк) без VK-логина в `createComplex`, без
  динамического `buildRescale`, с ещё не отключённой загрузкой
  `grounds.swf` — подтверждает находку из этого отчёта (см. пункт выше)
  как реальное изменение между версиями, а не случайность. Повторно не
  переразбирался в этом проходе.
- **`colonynavigate.txt`** — это не дублирующий исходник, а
  захардкоженная тестовая XML-заглушка ответа сервера (`xmldata=<?xml…
  <colonynavigate><colony combname="test_000" coords="1.1.2" .../>…`,
  11 строк) — судя по всему, оставленный разработчиком фикстур для
  локального тестирования экрана без реального сервера. Полезен как
  живое подтверждение атрибутов `combname`/`coords`/`id_comb`/`allow`/
  `capture`/`disable`/`base` тега `<colony>`, но это не альтернативная
  версия кода.
- **Секреты.** Не найдено — оба файла не содержат паролей/ключей/URL с
  учётными данными. Единственные захардкоженные внешние URL —
  публичные ссылки ВКонтакте (`http://vkontakte.ru/id{ID}`,
  `http://vkontakte.ru/club16650349` как ссылка по умолчанию,
  `sota.as:1198,1205`) — не секреты, обычные публичные адреса профиля/паблика.
- **Не посторонний контент.** Интеграция с ВКонтакте в `fillComplex`
  (аватары, профили, `_level0.socialNet == "VK"`) — легитимная часть
  клиента для версии сайта `VERSION_NAME == 'VKONTAKTE'`, уже отмеченной в
  `docs/client-engine-and-protocol.md` §8.8/§8.9. Ничего похожего на
  инцидент с `fr/`/`securite/` в этих двух файлах не найдено.
- **Дублей вида `sota_old.as` нет** — в `SPHERE_client/` присутствуют
  только `sota.as` и `Копия sota.as` (плюс сопутствующие файлы `.svn`), для
  `colonynavigate` — только `colonynavigate.as` и тестовая заглушка
  `colonynavigate.txt`, разобранная выше.

## 9. Открытые вопросы

- **`game.check_build_size()`** (`sota.as:46`) — от чего зависит
  `buildRescale`, не разбирался (файл `game.as` не входил в эту задачу).
  Нужен для точного 1:1 воспроизведения масштаба построек в PixiJS.

  коде не выводится, только итоговые пиксельные значения. Для порта можно
  либо скопировать константы как есть (декоративный фон, не критично для
  геймплея), либо вывести формулу заново из `h`/`v`/`lengthSide`, если
  понадобится параметризация.
- **Используется ли `debug.link.SWITHC`** (мультивыбор ячеек, §5.4) где-то
  в продакшене — не установлено по этим двум файлам, нужна проверка вне их
  периметра (возможно, включается конфигом мира/премиум-пакетом).
- **Судьба `grounds.swf`** как отдельного ассета — не установлено, требуется
  ли он до сих пор где-либо в сборке или это исторический остаток (см. §8).

  предназначено на клиенте.
