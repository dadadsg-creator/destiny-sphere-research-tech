## Общее назначение

`ds/utils/` — это набор административных и обслуживающих скриптов игры
«Сфера Судьбы»: пересчёт рейтингов, зачистка неактивных аккаунтов и
устаревших данных, перенос игроков между игровыми мирами, пересчёт
экономических показателей, сверка версий и содержимого баз данных разных
миров, а также несколько диагностических/тестовых скриптов и разовых
патчей, оставленных в репозитории после использования. Общая идея — часть
операций должна выполняться регулярно (обслуживание живых игровых миров),
часть — это одноразовые ad hoc-инструменты для конкретной задачи
(перенос конкретных игроков, разовый патч данных, разовая сверка после
миграции), оставленные в коде «на память»/для повторного использования.

## Как эти скрипты запускаются

Прямых свидетельств (crontab-файлов, вызовов systemd-таймеров и т.п.) **в
самом репозитории не найдено** — поиск по `crontab`, `cron.d`, `*.sh` в
`old-sphere` не дал скриптов-обёрток для `ds/utils` (единственные `.sh`
файлы в дереве — служебные скрипты внутри вендорного phpMyAdmin). Прямо
утверждать, что где-то лежит crontab, нельзя — вероятно, он существовал на
проде вне этого репозитория. Но в самом коде есть несколько косвенных, но
довольно однозначных признаков:

1. **Двойной режим CLI/Apache почти в каждом скрипте.** Типовой шаблон
   (см., например, `ds/utils/DeleteDeadUsers.php`, `DeleteOldBattles.php`,
   `DeleteTrash.php`, `CalcArmyWeight.php`, `DropTemporaryArtefacts.php`):
   ```php
   $sapi = php_sapi_name();
   if ($sapi == "apache2handler") {
       // показать HTML-меню с выбором мира (dbid) для ручного запуска из браузера
   } else {
       // CLI-режим: $DBID = (int)$_SERVER['argv'][1];
       $delete = new SU_DeleteDeadUsers($DBID);
       $delete->Scan();
   }
   ```
   Это значит, что каждый такой скрипт можно запустить и вручную через
   браузер (с явным выбором мира по ссылке), и по расписанию через
   `php ScriptName.php <dbid>` из командной строки — вероятно, отдельным
   вызовом cron на каждый `dbid` из `$GLOBALS['dbWorldAccess']`.

2. **Скрипты, которые явно требуют CLI и отказываются работать из Apache.**
   `ds/utils/LockCollector.php`:
   ```php
   if ($sapi == "apache") { die("Only for command line mode!"); }
   ...
   SU_Locker::cronLockCollector();
   ```
   Само имя метода `cronLockCollector()` (реализован в
   `ds/classes/SU/SU_LockerStoreWorkFiles.class.php`) прямо указывает на
   происхождение из cron.

3. **Прямое упоминание расписания в комментарии разработчика.**
   `ds/utils/glstat.php` (несмотря на название, скрипт не про рейтинги, а
   про синхронизацию партнёрских/лидовых данных):
   ```php
   // в этом скрипте мы можем в 1 шаг сделать полное обновление данных партнёров
   // запускать по расписанию, чтобы вовремя обновлять партнёрские данные из XML
   ```

4. **Флаг-файлы техобслуживания в `/etc/cron.ds/` на сервере.** Функция
   `GameDown()` в `ds/include/GameDown.inc.php` проверяет существование
   файлов `/etc/cron.ds/*down_db<id>*` и `/etc/cron.ds/*down*` — то есть на
   проде существовал (вне этого репозитория) каталог `/etc/cron.ds/`,
   которым какой-то внешний процесс (по всей видимости, тот же cron)
   включал/выключал режим «мир закрыт на обслуживание» перед batch-операциями.

5. **HTTP-доступ защищён Basic Auth.** `ds/utils/.htaccess`:
   ```
   AuthType Basic
   AuthName "Destiny Sphere Admin and Developments restricted area. Only authorized access."
   AuthUserFile /etc/apache2/passwd
   require user developmer
   ```
   Это подтверждает, что веб-доступ к утилитам не публичный, а только для
   разработчиков/админов — то есть веб-режим этих скриптов используется как
   ручная «панель обслуживания», а не только как побочный эффект
   двойного sapi-режима. Есть и `ds/utils/index.php` — простая HTML-страница
   со списком ссылок на утилиты и их описанием на русском (по сути,
   самодельная admin-панель для ручного запуска).

6. **Отдельный случай — «демон», а не разовый cron-джоб.**
   `ds/utils/RefreshDemon.php` управляет процессом
   `RD_RefreshDemon::startScan()` (класс
   `ds/classes/RD/RD_RefreshDemon.class.php`), внутри которого — `while(true)`
   с несколькими `sleep(...)` (в т.ч. `sleep($this->downWaitQuant)`,
   `sleep($this->loadWaitQuant)`). Это не одноразовый скрипт, а
   долгоживущий процесс-демон («тикающий» движок игры — см. ниже отдельный
   раздел). Веб-панель `RefreshDemon.php` при обращении из Apache отслеживает
   его «живость» через heartbeat-файлы `ds/utils/files/RD_<dbid>_ALIVE_<n>`
   (считается живым, если `filemtime` свежее 3 минут) и позволяет
   вручную ставить STOP/BLOCK-флаги для конкретного мира/инстанса демона.

**Вывод:** прямых крон-конфигов в репозитории нет, но по совокупности признаков
(argv-driven CLI режим почти во всех скриптах, метод `cronLockCollector`,
явный комментарий про расписание, флаг-каталог `/etc/cron.ds/` на сервере)
можно уверенно утверждать, что подавляющее большинство этих скриптов
запускалось по cron на продакшн-сервере (отдельно для каждого игрового мира),
а веб-доступ через Basic Auth оставлен как ручной «аварийный» или
диагностический интерфейс для разработчиков.

## Мультимировая архитектура: `foreach ($GLOBALS['dbWorldAccess'])`

Значительная часть скриптов действительно проходит циклом по всем базам
миров из `$GLOBALS['dbWorldAccess']` (заданного в `ds/config/settings.php`),
агрегируя или последовательно обрабатывая данные по каждому миру. Примеры
с прямым циклом по всем базам сразу (без выбора конкретного `dbid`):

- `ArchiveRankings.php`, `ranking_csv.php` — обходят все базы/миры для сбора
  рейтингов.
- `DailyStat.php` — обходит все базы для агрегации показателей магазина/боёв.
- `CloseWar.php` — обходит все базы, чтобы закрыть/открыть войну и торговлю
  сразу во всех мирах.
- `ServerTimes.php` — обходит все базы, сверяя время сервера БД со временем
  HTTP-сервера (диагностика рассинхронизации часов).
- `ReplaceArts.php` — обходит все базы, заменяя ID артефактов по всем мирам.
- `RecieverWorld.php`, `FreeTransfer.php` — обходят все базы и все миры внутри
  каждой базы (`SELECT id_world FROM ds_world`), чтобы найти те, где включён
  соответствующий игровой модификатор (`WORLD_TRANSFER_ENABLE_AUTO_TRANSFER`,
  `FREE_RING_TRANSFER_ALLOWED`), и обработать только их.
- `CollectWorlds.php` — специально спроектирован для работы с подмножеством
  баз: список `dbid` можно передать через чекбоксы в вебе или через argv в
  CLI, а если не передан — берутся все базы из `dbWorldAccess`.

У других скриптов (`DeleteDeadUsers.php`, `DeleteOldBattles.php`,
`DeleteTrash.php`, `CalcArmyWeight.php`, `UpdateRanking.php`,
`DropTemporaryArtefacts.php`, `NPC_Update.php`, `RecountCourses.php`) цикл по
мирам, судя по всему, вынесен **наружу**, на уровень cron/оператора: сам
PHP-файл обрабатывает один `dbid`, переданный аргументом командной строки, а
перебор по всем `dbWorldAccess` эмулируется отдельными вызовами (по одному
cron-заданию на мир) либо явно предлагается веб-меню со ссылками на каждый
мир. Это довольно последовательный архитектурный паттерн для всей папки.

## Подробнее о ключевых группах

### 1. Рейтинги игроков

- `UpdateRanking.php` — пересчитывает рейтинговую таблицу для одного мира
  (`$DBID` из argv или из веб-меню), вызывая `SU_UpdateRanking::Update()`.
- `ArchiveRankings.php` — проходит по **всем** базам (`dbWorldAccess`),
  вставляет текущий срез рейтинга в `ds_ranking_archive` (общий балл,
  археология, здания, наука, бой, NPC) и параллельно вычисляет место
  каждого игрока в каждой категории, сохраняя их в
  `ds_ranking_archive_places`. Судя по всему — ежедневная архивация истории
  рейтинга.
- `ranking_csv.php` — содержит два класса, `RankingCSV` (старый формат) и
  `RankingCSVNew` (новый формат, с учётом battle XP и «открытых ворот»
  колонии), которые для каждого мира каждой базы выгружают текущий рейтинг
  в CSV-файл в `$_SERVER['DOCUMENT_ROOT'].'/ds/csv/ranking...'` — судя по
  всему, эти CSV затем отдаются на сайте/используются внешней страницей
  рейтингов.

### 2. Очистка / удаление устаревших данных

Общий шаблон — класс принимает `$DBID` одного мира и делает `->Scan()`/`->Exec()`:

- `DeleteDeadUsers.php` → `SU_DeleteDeadUsers` (`ds/classes/SU/SU_DeleteDeadUsers.class.php`).
  У класса есть `$noticePeriod = 7` (дней) — то есть перед удалением
  «мёртвым» пользователям, судя по всему, сперва отправляется уведомление,
  и лишь потом (при последующих запусках) происходит фактическое удаление.
  Критерии «мёртвости», судя по названиям игровых модификаторов в
  `files/set_data_storing.inc.php` (`DELETE_DEAD_NO_LOGIN_PERIOD` = 30,
  `DELETE_DEAD_NO_REFRESH_PERIOD` = 50, `DELETE_DEAD_NO_BUILDINGS_PERIOD` = 3) —
  настраиваются на уровне игровых модификаторов конкретного мира.
- `DeleteOldBattles.php` → `ME_DeleteOldBattles::ScanOneBase($DBID)`.
- `DeleteTrash.php` → `SU_DeleteTrash::Exec($DBID)`.
- `DropTemporaryArtefacts.php` → чистит временные (просроченные) артефакты
  на одном сервере (`$DBID` из argv или GET).
- `ClearBase.php` — полностью иная логика: **полностью очищает** (DELETE)
  все таблицы `ds_%` на хардкоженном `$dbId = 5`, кроме явного белого списка
  из ~150 «справочных»/конфигурационных таблиц (расы, здания, юниты,
  атрибуты и т.п.). Судя по всему — инструмент для «обнуления» игрового
  мира перед повторным использованием базы (например, для нового мира на
  старом сервере), запускаемый вручную с правкой `$dbId` под конкретный
  случай, а не по расписанию.
- `ClearWorld.php` — обёртка над `DU_ClearWorld::Clear($dbId, $worldId)` с
  захардкоженными параметрами (`Clear(1, 3)`) внутри блока
  `/* BEGIN WORK AREA */ ... /* END WORK AREA */` — судя по всему,
  разработчик руками правил параметры перед каждым запуском, то есть это
  тоже ручной инструмент точечной очистки конкретного мира, а не
  регулярный cron.

### 3. Трансферы игроков между мирами

- `RecieverWorld.php` обходит все базы/миры, находит те, где включён
  модификатор `WORLD_TRANSFER_ENABLE_AUTO_TRANSFER`, и для каждого такого
  мира вызывает `SU_RecieverWorldTransfers::Exec()` — похоже на приёмную
  сторону автоматического переноса игроков.
- `WorldTransfer.php` вызывает `SU_ExecWorldTransfer::Exec()` (класс
  `ds/classes/SU/SU_ExecWorldTransfer.class.php`) — судя по всему, основной
  обработчик очереди переносов между мирами/версиями игры.
- `FreeTransfer.php` обходит все базы и все миры внутри них и для каждого
  вызывает `SU_ExecFreeTransfer::Exec($db, $world)` — обработка «свободных»
  переносов колонии между кольцами. Проверка модификатора
  `FREE_RING_TRANSFER_ALLOWED` в коде закомментирована, то есть сейчас
  скрипт обрабатывает такие переносы для всех миров без разбора.
- `ValidateTransfer2.php` вызывает `SU_ValidateDoubleCombsControl::Exec()` —
  проверка на дублирование колоний после переноса.
- `TransferAllUser.php` — специфический разовый скрипт (класс `AddPremium`
  внутри самого файла) с захардкоженными ID баз/миров и датой (лето 2010) —
  это одноразовый инструмент для переноса конкретной группы игроков между
  конкретными мирами (похоже на слияние миров), а не регулярная утилита.
- `CollectWorlds.php` — собирает («коллекционирует») данные с выбранных
  игровых серверов; конкретно что собирается — по самому файлу не
  установлено (логика в `SU_CollectWorlds`, класс не читался).

### 4. Экономика и баланс

- `RecountCourses.php` (41 КБ, самый крупный файл группы) — пересчитывает
  торговые курсы (обменные курсы ресурсов/валют) для выбранных миров;
  поддерживает и веб-форму с чекбоксами миров, и CLI-режим со списком
  `dbid_idworld` через запятую.
- `RecountCombScore.php` — обходит все базы, пересчитывает
  `ds_comb.combscore` как сумму `building_score` всех построек в комбе.
- `CalcArmyWeight.php` — пересчитывает «вес армии» для одного мира/сервера.
- `calcResAvg.php` — тонкая обёртка над `SU_CalcWorldAverageResources::Calc()`.
- `MoneyAccountCheck.php` — сверка денежных счетов (`MU_CheckAccountsMainController`),
  довольно тяжёлый скрипт (лимит выполнения ~59 минут, 512 МБ памяти),
  принимает список названий миров через запятую в CLI-режиме.
- `ReplaceArts.php` — обходит все базы, заменяя одни ID артефактов на
  другие по жёстко заданной таблице соответствий — разовый патч данных
  (не параметризован извне).

### 5. Демон обновления состояния игры (RefreshDemon)

Это не обычный «утилитарный скрипт», а управляющая консоль для
долгоживущего фонового процесса `RD_RefreshDemon`
(`ds/classes/RD/RD_RefreshDemon.class.php`), который выполняет собственно
игровую логику реального времени — судя по названию и структуре, «тики»
игры (обновление состояния пользователей/построек по времени). Ключевые
детали:

- `RD_RefreshDemon::startScan()` содержит `while(true)` с несколькими
  `sleep(...)` — то есть один запуск процесса живёт бесконечно (пока его не
  остановят), в отличие от прочих утилит с однократным выполнением.
- Для каждого игрового сервера (`dbid`) поддерживается до 10 параллельных
  «демонов» (`MAX_DB_DEMONS = 10`), каждый со своим ID.
- Каждый демон периодически обновляет heartbeat-файл
  `ds/utils/files/RD_<dbid>_ALIVE_<demonId>`; веб-панель `RefreshDemon.php`
  считает демон «живым», если файл обновлялся менее 3 минут назад — это
  почти наверняка использовалось внешним cron-скриптом (не найденным в
  репозитории) для автоматического перезапуска упавших демонов.
- Через файлы `RD_<dbid>_STOP[_<demonId>]` и `RD_<dbid>_BLOCK[_<demonId>]`
  (создаются/удаляются кнопками в веб-панели) можно поставить конкретный
  демон конкретного мира на паузу/блокировку без остановки процесса целиком.
- `test_RD.php` — ручной отладочный скрипт, который напрямую вызывает
  `(new RD_RefreshDemon(0))->refreshUser(631)` для одного захардкоженного
  пользователя — использовался для точечной отладки логики обновления.

### 6. Сверка версий и содержимого БД

- `DBCompare.php` — сравнивает внешние ключи (foreign keys) между
  «мастер»-базой и конкретной «BIG_ALPHA»-базой через `pg_constraint`;
  генерирует SQL для приведения ключей в соответствие. Файл переопределяет
  `$GLOBALS['dbWorldAccess']` локально, с захардкоженными хостами и
  учётными данными для этих двух конкретных серверов (см. замечание по
  безопасности ниже) — то есть это разовый инструмент для конкретной сверки
  после миграции/копирования базы, а не для регулярного использования.
- `CompareTableData.php` — интерактивный веб-инструмент (форма выбора
  master/slave баз, пошаговое сравнение через `SU_CompareDataController`) для
  сверки данных таблиц между базами; использует конфиг
  `ds/utils/files/compare_tables_data.conf`.
- `ComparisonVersion.php` — веб-форма сравнения версий (`SU_CompareVersion`,
  `ds/classes/SU/SU_CompareVersion.class.php`) — вероятно, версий кода/схемы
  между окружениями.
- `VersionUpdate.php` — управление версиями Flash-клиента
  (`SU_FlashVersionsUpdate`): checkout, обновление локализации
  (`touch .../ds/flash/localdata`), просмотр и точечное обновление
  отдельных файлов клиента.

### 7. Тестовые / отладочные скрипты

Явно не предназначены для расписания — как правило, содержат
захардкоженные тестовые данные и закомментированные варианты вызовов:

- `Lottery_test.php` — напрямую вызывает `addPrizeToUser(35073, 'r', 1, 1)`
  для конкретного тестового пользователя.
- `test_RD.php` — см. выше, тестирует один вызов RefreshDemon для
  пользователя 631.
- `TestDBIntegrity.php`, `TestSystemFunction.php`, `TestClassesVersions.php` —
  веб-панели с ручным запуском проверок целостности БД / версий классов /
  общей работоспособности системных функций.
- `TestFolder.php` — несмотря на название, содержит класс `CheckSecurity`,
  который, похоже, проверяет доступность/защищённость директорий сайта
  через HTTP-запросы (наличие `.htaccess`, листинг директорий и т.п.), а не
  тестирует «папку» в смысле файловой системы.
- `DecodeView.php` — веб-форма для декодирования (`decode()`) закодированных
  строк клиент-серверного протокола — отладочный инструмент для разбора
  трафика Flash-клиента.

### 8. Отчётность и мониторинг

- `DailyStat.php` — самый содержательный отчётный скрипт: считает
  логины/регистрации/оплаты/бои за день/неделю/месяц (с сравнением к
  предыдущему периоду), обходит все базы (`dbWorldAccess`) для
  мультимировых метрик, дополнительно запрашивает внешний биллинговый
  сервис (`https://billing.destinysphere.ru/gate/paymentNum.php`) для
  расчёта ARPU/ARPPU, сохраняет снимок в `ds_daily_stat` и рассылает
  готовый HTML-отчёт по email нескольким адресам разработчиков
  (захардкожены в файле — не воспроизведены в этом документе).
- `LogFilesSize.php` — обходит пути из `$GLOBALS['LOGING_DEBUG_LOGS_PATH']`,
  считает количество/размер файлов и свободное место на диске; при менее
  чем ~200 МБ свободного места отправляет предупреждение по email (в
  CLI-режиме) — явный сторож дискового пространства.
- `ServerTimes.php`, `RequestStat.php`, `DataBaseStat.php`, `ServerLoad.php`,
  `UnicArtsStat.php` — набор веб-дашбордов для админов (текущее время БД по
  всем серверам, статистика запросов, статистика по БД, нагрузка сервера,
  статистика уникальных артефактов).

## Открытые вопросы / замечания

- **Реальный механизм запуска (crontab) не найден.** В репозитории нет ни
  crontab-файлов, ни shell-обёрток для `ds/utils/*.php` (кроме служебных
  `.sh` внутри вендорного phpMyAdmin). Расписание запуска, вероятно,
  задавалось прямо в системном crontab продакшн-сервера, который не входит
  в этот репозиторий — установить точную периодичность каждой задачи
  («раз в час», «раз в сутки» и т.п.) по коду невозможно.
- **`glstat.php`** — имя предполагает статистику, но фактическое содержимое
  (`MP_GameLeads`, `MP_PartnerData`) относится к синхронизации партнёрских
  данных из внешнего XML. Возможно, файл когда-то переименовали/
  переиспользовали не сменив имя — назначение по коду понятно, но само имя
  файла вводит в заблуждение.
- **`ViewBattleSystemLogs.php`** выглядит как незавершённый/сломанный
  фрагмент кода (несколько строк с обращением к необъявленным переменным
  `$dbId`, `$query`, закомментированный вызов статического метода) — по
  всей видимости, нерабочий файл, оставленный в процессе разработки.
- **`CollectWorlds.php`** — по имени и структуре ясно, что скрипт собирает
  данные с выбранных игровых серверов, но что именно собирается и куда,
  по самому файлу `ds/utils/CollectWorlds.php` не установлено (логика — в
  не прочитанном в рамках этой задачи классе `SU_CollectWorlds`).
- **`patternAdder.php` / `SU_PatternAdder`** — назначение («паттерны» чего
  именно — вероятно, шаблоны ячеек/комплексов карты мира) по этому файлу
  однозначно не установлено, класс не читался.
- **`ReplaceString.php`** — прочитанный фрагмент содержит класс
  `SU_GetFolderTree`, что не соответствует ожиданию по имени файла
  («замена строки»); похоже, файл выполняет вспомогательную функцию для
  построения дерева файлов клиента (используется, видимо, вместе с
  `VersionUpdate.php`), а не простую замену строк. Точное назначение по
  файлу не установлено полностью.
- **Замечания по безопасности (не для действия, только к сведению):**
  `ds/utils/DBCompare.php` содержит захардкоженные учётные данные (хост,
  логин, пароль) для конкретного legacy-сервера сравнения баз — реальный
  пароль не редактирован (в отличие от большинства мест в кодовой базе) и
  намеренно не скопирован в этот документ. `ds/utils/LogFilesSize.php` и
  `ds/utils/DailyStat.php` содержат захардкоженные e-mail-адреса
  сотрудников для оповещений — также не воспроизведены здесь дословно.
- **Точная периодичность демона `RefreshDemon`** (сколько экземпляров
  реально держали в проде на игровой мир, кто и как их перезапускал при
  падении) по коду репозитория не установлена — видна только сама
  инфраструктура heartbeat/stop/block-файлов, а не внешний supervisor.
